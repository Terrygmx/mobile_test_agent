## 3. 发现

### P2-1 `upsert_graph` 的 DELETE 硬编码 `source_of=RUNTIME`，与其 docstring 承诺的「按 source_of 整体替换」不符 —— 写入 SOURCE 图会静默删掉同 scope 的 RUNTIME 图

- `graph/storage.py:60` 的 docstring 写的是「把一张图写进库（按 `(app_id, app_build, source_of)` **整体替换**）」，但 `:68-75` 的两条 DELETE 把 `source_of` 写死成常量 `RUNTIME`：

  ```python
  "DELETE FROM screen_nodes WHERE app_id=? AND app_build=? AND source_of=?",
  (graph.app_id, graph.app_build, RUNTIME),        # ← 硬编码，不看 graph 自己的 source_of
  ```

- 于是传入一张 `source_of=SOURCE` 的图时，执行顺序是「**先删掉 runtime 行** → 再插入 source 行」。探针实测（真 `GraphStore` + 真 SQLite）：

  | 步骤 | `load_graph(RUNTIME)` 行数 | `load_graph(SOURCE)` 行数 |
  |---|---|---|
  | `upsert_graph(gA)`（runtime 图，A/B 两节点） | 2 | 0 |
  | `upsert_graph(src)`（SOURCE 图，Declared 一节点） | **0** | 1 |

  即：写声明面把观察面**静默清空**。这不是「覆盖了另一个范围」，是数据丢失。
- **为什么现在报**：现有唯一调用方 `build_and_store` 只传 runtime 图，所以当前**不可达**；但 plan **Task 5.2（P2-12 Source Graph，下一个任务）** 的交付物正是「metadata 的 screens/导航信息 → `screen_nodes(source_of='source')`」，而 `graph/models.py` 的 `ScreenNode.source_of` 与 `RuntimeGraph` 本就是为两个来源设计的同结构值——复用 `upsert_graph` 是最自然的落法，而 docstring 还主动写着「按 source_of 整体替换」，等于**邀请复用**。复用即踩雷。
- 修法（二选一，都只需一行）：DELETE 的 `source_of` 改传**图自身的来源**（`graph.nodes[0].source_of`，或给 `RuntimeGraph` 加一个 `source_of` 属性单点导出），或拆出 `upsert_source_graph` 并让两者共用同一段替换逻辑。无论哪种，docstring 与实现必须对齐。

### P3-2 同一步产生两类证据（同屏）时 `visit_count` 累加 2，且测试名说「dedupe」而断言是 2

- `graph/builder.py:126-137`：对一步的**每一条**观测都执行 `slot["count"] += 1`。一个 `wait_for screen:X`（成功）+ 其 `detail.recovery.stages` 里 `screen:X/FOUND` 的步骤，会为 X 贡献 **2** 次访问。
- 探针：单步两类证据（同屏 LoginView）→ `visit_count=2`、`evidence=('recovery_observed','wait_screen')`。
- 而 `tests/unit/test_graph_builder.py:250` 的测试名为 `test_recovery_and_wait_on_the_same_step_dedupe`，断言却是 `visit_count == 2` 并注释「两条观测都算访问（证据不同）」——**名字与断言相反**（dedupe 的是节点，不是计数）。
- 影响有限（`visit_count` 只进 `summary()["visits"]`，暂不参与任何判据），但它是**未定义口径**：一次逻辑访问记 2 次。设计 §12 没定义 `visit_count`，需要要么在 docstring 里把它定义成「观测条数」并改名，要么真去重（同一步同屏只记 1）。

### P3-3 一步观测到两个**不同**屏时，会凭空生成一条转移（`trigger` 为空串）

- 若某步同时给出 `wait_screen A` 与 `recovery_observed B`（A≠B），`observations` 里就并排出现 A、B，`zip` 会据此产出一条 `A→B` 转移，且因该步是 run 内首个观测步，`_trigger_of(prev=None) == ""`。
- 探针：单步 `wait_for screen:A` + stage `screen:B/FOUND` → 节点 `('A','B')`、转移 `[('A','B','')]`（trigger 空串）。
- 这是 §3 的口径边界：设计 §12.2 的 `CHANGED` 用 `trigger` 做连接键，一条 `trigger=""` 的转移既进不了 CHANGED（无从连接），又是「一次动作产出两个屏」的伪导航。可达性低（需要 wait 成功且恢复期识别出**另一个**屏），故 P3——但建议在 `observed_screens` 或建图处加一条纪律（同一步多屏时以 `wait_screen` 为准，或跳过无 `trigger` 的转移）。

## 5. 值得肯定

- **「什么算到达一个屏」这个问题被正面回答，而不是含糊地「有 target 就算」**：模块 docstring 用一张表把两类证据的**为什么**写清（`wait_screen`——wait 引擎校验过 marker；`recovery_observed`——引擎当场用 marker 识别），并**主动点名排除** `Screen.element`（元数据声明）。这个排除不是顺手做的：真机 trace 里恰好有 `wait_for LoginView.password_field` 这一形态，作者给了专测把它钉死，并在 docstring 里写清「若将来需要，应作为第三类证据单独加入**并同步 diff 口径**，而不是悄悄并进现有两类」——这是在保护 §12.2 的 diff 语义不被侵蚀。
- **「不做自动探索」落成了可测的底线**：没有任何观测 → **空图**（不是「推测出登录页」），有专测。E12 在别处容易写成口号，这里是一个断言。
- **时间精度的处理是诚实的**：`steps` 表没有时间戳（P1 schema），于是取所属 `testcase_run` 的 `end_time`，并在 docstring 里明写「不假装更细」。宁可让同一 run 内所有观测共享一个时刻，也不伪造精度。
