## 3. 发现

### P3-1 「空列表不入缓存」是文档化行为但没有测试钉住
- 探针验证行为正确（`put(key, [])` 后 `get` 仍 miss），但测试文件没有这条——而它恰恰是最容易被后人「顺手修好」（把空列表也缓存上）然后悄悄变成负缓存黑洞的行为：Store 后增候选、本进程永远看不见，且没有任何报错。本项目纪律「文档化行为要有测试」，补三行。

### P3-2 「validated_builds 自然裁决」的机制未实现也未定档——接线前必须拍板
- 设计 7.3 的失效叙述是「app_build 变化不整体清空，而是让 **Guard 的 validated_builds 检查**自然决定是否需要重新执行验证」；cache docstring 进一步解释为「用不了就是一次 Guard BLOCK，记一条失败样本」。但：①当前 `guard_candidate` 链**没有任何 build/validated_builds 检查步骤**（Task 2.2 的设计里也没有）；②若照 docstring 解释实现（build 不在 validated_builds → BLOCK），每次 build 变化后每条 Experience 首用都会记**失败样本**——直接污染滑动窗口（E6）与成功率统计，与「自然裁决、代价有界」的意图相反。③当前实际行为是「不检查、EXECUTE 照常、成功后追 build」（E7 记账语义）——这自洽，但与设计/docstring 的措辞对不上。
- 建议：Task 4.2 接线定档时三选一并回填 §7.3 修订记录——(a) 不检查（现状，E7 只记账，把 docstring 改掉）；(b) 检查 + BLOCK 不计样本（4.7 表加一行）；(c) 检查 + 放行但不追加 validated_builds 之外的信任语义。这是 M3 剩余工作里唯一可能产生**语义分歧**的点，提前拍板比接线时拍便宜。

### P3-3 put 侧深拷贝隔离无测试
- 提交的测试只测 get 侧（拿到副本改不污染缓存）；put 侧（调用方 put 后继续改源列表）同样靠 `model_copy(deep=True)` 保证——探针补验通过。补一条对称测试，防止有人「优化掉」put 侧拷贝。

### P3-4 杂项
- `hits/misses` 计数器在锁外读（CPython int 原子，实践无害）——加一行注释防「好心加锁」。
- `cache_key` 的 None→'' 细化使 `app_id=None` 与 `app_id=""` 同 key——已登记且语义等价（缺段=空段），仅记录。

## 4. 值得肯定

- **「E1 延伸」做进了类型而不是注释**：缓存里不存在「已验证/可执行」标记，`get` 返回裸列表——「绕过 Guard」在 API 上不可表达。这是本轮 P2 到目前为止把设计红线翻译成代码形状的最干净一例（比「调用方记得先过 Guard」的约定强一个量级）。
- **空列表不缓存的黑洞论证**：负缓存是最常见的缓存陷阱（miss 也缓存 → Store 侧新增数据进程内永久失明），docstring 把危害机制写透并拒绝实现——「加速层不能反向变成黑洞」这句话值得进设计文档。
- **入出皆拷贝的完整性推理**：缓存的正本一旦被运行时引用改写，下次命中就是被悄悄篡改的历史——「不是权威数据 ≠ 可以被污染」。成本几十字节，换推理简单，划算。
- **接线定档提前登记在 plan**：归 Task 4.2 + 两条红线（命中/未命中共用同段 Guard+记账代码；缓存不得改变 ranker 输入集语义——上一轮 review 的提醒原文入账），并且给出了理由（指标延迟梯度需要缓存真实进执行路径）。任务边界与红线同步落纸，M3 收口时不会出现「谁接线」的悬案。
