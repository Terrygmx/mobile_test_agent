## 二、发现

### P3-1 名为「screen wait polarity」的测试实际改的是 **assertion** 步——`_screen_tokens` 的 wait 条件分支**零覆盖**（测试空转 + 名实不符）

**位置**：`tests/unit/test_test_fingerprint.py:102-109`（测试）、`candidates/fingerprint.py:70-79`（被测分支）

`test_screen_wait_polarity_changes_fingerprint` 的 docstring 写「`screen:X exists` 与 `screen:X not_exists` 是不同用例」，但它改的是 **`b.steps[6]`**——`_case()` 的第 7 步是 `{"assertion": {"target": "screen:HomeView", ...}}`（**AssertionStep**），不是 `steps[5]` 的 `{"wait_for": {"target": "screen:HomeView", ...}}`（**WaitStep**）。于是它钉住的是 `_screen_tokens` 的 **assertion** 分支（`:83`），而 **wait** 分支（`:79` 的 `w.condition`）**零测试**。

**复现命令**（把 screen-wait token 的 condition 换成常量——`_screen_tokens` 的唯一被测行为被抹掉）：

```bash
cd /Users/terrygmx/PycharmProjects/Mobile_test_agent
python3 - <<'PY'
import pathlib
p = pathlib.Path("candidates/fingerprint.py"); s = p.read_text(encoding="utf-8")
old = 'out.append(repr(("wait", w.target.id, w.condition)))'
new = 'out.append(repr(("wait", w.target.id, "")))'
assert s.count(old) == 1
p.write_text(s.replace(old, new), encoding="utf-8")
PY
find . -name __pycache__ -exec rm -rf {} + 2>/dev/null
env PYTHONPATH=. .venv/bin/python -m pytest tests/unit/test_test_fingerprint.py -p no:cacheprovider
```

**实测**：`19 passed`（全量 `pytest tests` → **1688 passed**）。即 `screen:X exists` 与 `screen:X not_exists` 的 **wait** 形态**如今会被算成同一指纹**，而没有任何测试会发现。

**为什么是 P3**：代码本身**是对的**（`w.condition` 在 token 里），坏的是**测试的覆盖面声称**——本仓口径（MEMORY §3.7）把「测试空转 / 名实不符」列为 P3。`candidates/fingerprint.py:72-73` 的 docstring 明确声称「条件参与 token：`screen:X exists` 与 `screen:X not_exists` 是**不同**的用例」——这是**声称宽于守卫**（守卫只覆盖 assertion 形态）。**当前无生产消费者**（`test_fingerprint` 唯一调用者仍是单测，见 §三 P3-4 的接线说明），故按 P3；**Task 3.4 接线后升级为 P2**：那时丢 wait 条件会让「等 Home 出现」与「等 Home 消失」两条语义相反的候选被判重复 → SKIP 掉一条真用例。

**建议修法（建议，未动手）**：把 `test_screen_wait_polarity_changes_fingerprint` 改到 `steps[5]`（WaitStep）上，或**另补**一条真正改 wait 条件的测试（例如 `screen:HomeView active` vs `screen:HomeView exists`）。补一条即可让探针 E2 真红。

### P3-2 「每个步骤恰好落入一个分量」为**假**——带 `postcondition` 的 `ActionStep` 同时落两个分量

**位置**：`candidates/fingerprint.py:23`（docstring）、`docs/p3_data_audit.md:1993-1995`（决策 #2）

docstring 与审计决策 #2 都写「**每个步骤恰好落入一个分量**」。但 `_screen_tokens`（`:84-87`）与 `_assertion_tokens`（`:117-120`）都对 `ActionStep.postcondition` 追加 token，而 `_action_tokens`（`:95-97`）**同时**为同一个 `ActionStep` 追加动作 token。所以一个带 postcondition 的动作步**落 2 个分量**。

**复现命令**：

```bash
env PYTHONPATH=. .venv/bin/python - <<'EOF'
from candidates.fingerprint import _screen_tokens, _action_tokens, _assertion_tokens
from testcase.schema import parse_testcase_dict as P
tc = P({"schema_version":"0.2","id":"x","name":"x","steps":[
    {"action":"tap","target":"LoginView.login_button",
     "postcondition":{"target":"screen:HomeView","condition":"active","timeout":5}}]})
print("screens=", _screen_tokens(tc))    # ['(\'post\', \'HomeView\', \'active\')']
print("actions=", _action_tokens(tc))    # ['(\'tap\', \'element:LoginView.login_button\', \'\', \'\')']
print("assertions=", _assertion_tokens(tc))   # []
EOF
```

**实测**：`screens` 与 `actions` **同一 step 各出 1 条** → 「恰好落一个分量」被证伪（真语料 `suites/smoke/logout_001.yaml:38`、`suites/account/login_again_001.yaml:37` 正是这种形态，共 2 处）。

**为什么是 P3**：指纹**仍是确定性的、仍按内容区分**——这不是行为 bug；坏的是**声称的不变量**（夸大文档 / 名实不符，MEMORY §3.7 明列）。若 Task 3.4 照这句不变量写去重逻辑（例如按分量做「一步一 token」的配对），会踩空。

**建议修法（建议，未动手）**：docstring 与审计决策 #2 改写为「每个步骤的**动作**落 `actions`；其 `postcondition`（若有）按目标类型落 `screens`/`assertions`——一个带后置条件的动作步贡献 2 个 token」。

### P3-3 真语料 20 例已有 **2 对同指纹**；其中一对**仅 precondition 不同**（`LOGOUT` vs `RELAUNCH`）→ Task 3.4 去重会 SKIP 一条语义不同的真用例

**位置**：`candidates/fingerprint.py:35-39`（不进指纹的字段，含 `precondition`）、`docs/p3_data_audit.md` 决策 #4

**建议修法（建议，未动手）**：Task 3.4 开工前拍板——`precondition.reset`（至少）是否入指纹。若维持排除，需在 docstring 明写「不同 reset 策略的同一步骤序列会撞指纹，去重侧需人工复核」；若纳入，改 `test_fingerprint` 的 `screens:` 前追加一个 `reset:` 分量即可（一行 + 一测）。
