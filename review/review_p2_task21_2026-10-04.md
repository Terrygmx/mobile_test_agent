## 3. 发现

### P3-1 lookup 排除 REJECTED 是超出设计 §7.1 的语义增项（合理，但需回填设计修订记录）
- 设计 7.1 的 lookup 无任何排除语义；§5.1 的 rank_experiences 也没说 REJECTED 不进候选。实现的理由（人工判定不可用的策略不该被消费路径看见）成立且方向安全，但它是接口契约的单方面收紧——M2 Task 2.4 把 Guard/引擎接到这个 Store 时，`rank_experiences` 的设计语义（逐个尝试**全部**候选）与实现（REJECTED 根本不出现在候选里）会有一个未记录的分叉。建议在设计 7.1 或 5.1 补一条修订记录：「REJECTED 由 Store 层排除，rank 只见可用候选」。

### P3-2 busy_timeout 双重配置不一致
- `_connect` 先 `sqlite3.connect(timeout=30)`（隐式 busy_timeout=30s）再 `PRAGMA busy_timeout=5000`（后设者胜，实际 5s）。两处意图不同（30s vs 5s），生效值靠阅读顺序。建议删一处：留 PRAGMA（显式可读），把 connect 的 timeout 也设 5 或直接省略。

### P3-3 引擎过渡债的两处落点要在 Task 2.4 一次清掉
- ①`agent/recovery.py:362` 的调用形态仍是旧签名 `lookup(ctx.app_build, ctx.screen_id, ctx.element_id)`，与新 Protocol 的 `lookup(app_id, screen_id, target_id)` 键语义不同（build ≠ bundle）——Task 2.4 接真 Store 时必须**连调用点带键来源**一起改（`RecoveryContext` 目前只有 `app_build="local"`，没有 app_id/screen 的可靠来源），这是 2.4 的隐性工作量，建议提前记入 task。②同处注释仍写「20 节预留位」——commit 声称「旧稿『设计 20 节』引用更正」，context.py 改了，recovery.py:362（和 :138）漏了。

### P3-4 `record_run` 对 `run.experience_id` 与参数不一致时静默吞掉
- `record_run(exp_id, run)` 落库用参数 `exp_id`，`run.experience_id` 若填了别的值被无声覆盖（DB 一致，但调用方 bug 不可见）。一行断言（`run.experience_id in (None, experience_id)`——或要求相等）即可让错误显形。

### P3-5 杂项
- `test_same_key_two_candidates_coexist` 里的 `_seed(strategy_value := None) if False else _seed()`——死 walrus 表达式（`if False` 永走 else），应为裸 `_seed()`。
- 并发测试的 reader 线程对 `errors` 列表无锁 append——CPython 下 `list.append` 原子，实践无害；写一行注释免得后人「修复」。

## 4. 值得肯定

- **E5 双层闸的可达性是真的**：我没有只看代码——专门做了「构造后变异字段」的旁路探针（pydantic 模型默认可变，这是真实的绕过面），Store 层闸接住了。防御纵深里每一层都被证明独立有效，这在 review 里不常见。
- **并发测试钉的是业务属性**：「8 线程 ×10 写全部落账 + `sample == success+failure` 恒成立 + 读者并发安全」——不是 sleep/计时装饰，是「不丢账」这个 E9 的存在理由本身。我用独立探针复现同参数，结果一致。
- **`_write_tx` 上下文管理器**：commit/rollback/close/release 四件事一处收口，注释明写「曾致 database is locked 连坐后续操作」——从踩坑到机制化的完整闭环，任何早退路径（包括 LookupError 的 rollback 分支）都有测试踩过。
- **两个视角都照顾到了**：REJECTED 在消费路径（lookup）隐身、在审计路径（list/get_runs）全量可见——「不干扰运行」与「不丢审计」没有互相牺牲。
