## 3. 发现

### P3-1 新近度代理的文档语义不准——`updated_at` 是「最后一次写」不是「最后一次样本」
- docstring 说代理含义是「最后一次**样本**时刻（不分成败）」，但 `updated_at` 实际被三方推进：`record_run`、`update_status`、`record_success_build`。探针实锤：同档同率的两条 VERIFIED，最近一次写是**状态跳变**（非样本）的排在前。对排序的影响仅限同分候选先后（Guard 兜底），但文档宣称的语义与字段真实语义不符——要么 docstring 改成「最后一次写时刻」，要么后续 Schema 变更点补 `last_success_at` 列（设计 5.1 原义的「最近一次成功」），把登记偏离的圆画完。

### P3-2 DEGRADED 档位决策只登记在代码/测试，设计 §5.1 未回填
- DEGRADED 排 CANDIDATE 之前意味着「刚被 E6 滑动窗口判连续失败的候选」仍先于「零失败但未验证的候选」被尝试——理由（有真实历史 > 零证据，Guard+执行兜底）成立且测试 docstring 写透了，但这是排障时「为什么先试了它」的高频问题，值得在设计 §5.1 补一条修订记录（与 7.1 的 REJECTED 回填同格式）。

### P3-3 杂项
- 零样本 VERIFIED（人工 Promotion 路径，9.5 跳过自动验证）会以档位 0 排最前且零证据——与「人工判断 > 统计」的语义自洽，但「无样本排尾」规则实际是**档位内**排尾；plan 原文没写档位限定词，建议在测试 docstring 或设计修订里点一句（已有行为正确，只是语义边界值得留痕）。
- `-exp.updated_at.timestamp()` 对 naive datetime 会 TypeError——fail-loud 可接受（store 写入恒带 +00:00），无需改动，记录而已。

## 4. 值得肯定

- **五级排序键一次成型**：`(tier, has_sample, -rate, -recency, id)` 每个维度都有出处（设计明文 / plan step 1 / 登记决策 / 排障可复现），没有隐藏的第四规则——排序这种最容易长出「再加一条 if」的地方被压成了一个纯元组。
- **experience_id 确定性兜底的理由是产品级的**：「报告里『逐候选尝试顺序』是排障证据，不能依赖 Python stable sort 的输入顺序」——把可复现性当作交付物而不是实现细节。
- **ranker 不做资格判定**：REJECTED 排尾是防御性的而非过滤——资格归 Guard（E1）、排序归 ranker、保留归 Store（11.2），三个职责在三个模块里各守各的边界，这是 M2 以来「单一规则体」纪律的延续。
- **偏离登记文化稳定运转**：两处偏离（DEGRADED 档位 / updated_at 代理）都有双侧登记与可复核理由——上一轮 review 提的「回填设计」做了（7.1），这一轮的 §5.1 回填是同一动作的重复（P3-2），属于流程惯性而非遗漏。
