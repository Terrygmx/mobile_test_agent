## 三、发现

### P2-1 `GUARDED_TOOLS` 是**手抄**且**无逐字钉** —— 等长替换后 1412 条全绿

**现象.** `agents/tools.py:77-81` 的 `GUARDED_TOOLS` 是**手写的 10 个名字字面量**；它决定
`AgentToolkit.call` 里 `if tool in GUARDED_TOOLS` 这一行是否构造 `GuardContext` 并调
`guard.check`——也就是说，**「Guard 到底跑不跑」完全由这张表决定**。

而 `agents/__init__.py:7-9` 把它写成**包级纪律**：

> **任何会碰 App 的动作都经 `tools.AgentToolkit` → Executor+Guard**（F1/F12，唯一分发层）：
> 执行类工具先过 `Guard.check`，BLOCK 写 `agent_trace` …

**探针（A/B，真改文件后还原）.** 把 `"assert_text"` 换成只读的 `"get_logs"`（**长度仍为 10**、
仍是 `ALLOWED_TOOLS` 的子集）：

```
改后 GUARDED_TOOLS = 10 ['assert_exists','back','get_logs','input',
                          'run_candidate_test','run_testcase','screenshot',
                          'swipe','tap','wait']
门禁 + 工具层测试：69 passed
全量：1412 passed in 32.70s          ← 一条都没红
```

此时：① `assert_text`（带 target、风险由元素推导）**不再过 Guard**——对 CRITICAL 元素做文本断言
会直接执行；② `get_logs`（纯只读，设计归「只读」组）**反而过 Guard**，违反设计 §10.1 的分组，
也违反模块 docstring 自己的边界声明（「只读组与候选创建组**不经 Guard**」）。

对照组：**摘掉**一个（`assert_text` 删掉不加）→ `test_guarded_tools_are_a_subset_of_the_allowlist`
红——但红的原因是 `len(GUARDED_TOOLS) == 10` 这个**计数**断言，不是「与设计对账」。

**为什么是 P2（而不是 P3）.** 三条理由：

1. 这是**安全不变量的声称**（F1 的落点），写在**包级 docstring**里，却**没有落点**——
   正是 `MEMORY.md` 里记了两次的那一课（`--agent-db` 那一次、`_check_autonomous_env` 的
   `args.policy` 那一次）的第三次。
2. 修法**方向明确、体量很小**：门禁文件里把 10 个名字**重新打一遍**（`DESIGN_10_1_GUARDED`），
   加一条 `set(GUARDED_TOOLS) == set(DESIGN_10_1_GUARDED)`，约 8 行。
3. **同一文件里对「禁用名」做了这件事，对「Guard 名单」没做**——`BANNED_TOOLS` 有
   `DESIGN_10_1_BANNED` 逐字重打 + `test_banned_set_matches_the_design_verbatim`（这正是我上一轮
   建议的形状），而 `GUARDED_TOOLS` 在门禁文件里**出现 0 次**（实测 `src.count('GUARDED') == 0`）。
   即：防住了「给 Agent 加上危险工具」，没防住「让 Guard 不再跑」。

> 附：模块 docstring 的小节标题「三张表（键集都是「单一真值源」的**派生**，不是手抄）」对
> `GUARDED_TOOLS` / `BANNED_TOOLS` **不成立**——它们是照着设计原文手抄的（这本身合理，
> 设计是散文；但「派生」这个词把三张表说成同一性质）。一并修掉即可。

**修法建议.**

```python
# tests/unit/test_tool_allowlist_gate.py —— 与 DESIGN_10_1_BANNED 同一手法
DESIGN_10_1_GUARDED = (                      # 设计 §10.1「执行（仍经 Guard）」组逐字
    "tap", "input", "swipe", "back", "wait",
    "assert_exists", "assert_text", "screenshot",
    "run_testcase", "run_candidate_test",
)

def test_guarded_set_matches_the_design_group_verbatim():
    assert set(GUARDED_TOOLS) == set(DESIGN_10_1_GUARDED)
```

（`GUARDED_TOOLS` 应从 `agents/tools.py` import；`DESIGN_10_1_GUARDED` **显式列出**，不从
`GUARDED_TOOLS` 反推——理由与 `DESIGN_10_1_BANNED` 的注释完全相同。）

### P3-1 「与 `steps.failure_type` 对齐的失败分类」有**两个落点**，docstring 只说了外层

**现象（探针）.**

```
wait 超时     : ToolResult.failure_type=None  value['failure_type']='WAIT_TIMEOUT'
assert 值不符 : ToolResult.failure_type=None  value['failure_type']='ASSERTION_VALUE_MISMATCH'
元素找不到    : ToolResult.failure_type='ELEMENT_NOT_FOUND'   value=None
```

`ToolResult.failure_type` 的 docstring（`agents/tools.py:180-182`）写的是
「与 P1 同名的失败分类 … 便于与 trace 的 `steps.failure_type` 对齐」——但**等待超时**与
**断言不过**这两类最常发生的失败，分类**不在这个字段上**，而在 `value["failure_type"]`。

同时 `create_promotion_proposal` 走的是第三套词汇：`value["ok"]`（内层）与外层
`ToolResult.ok` 同现——探针：`ToolResult.ok=True` 而 `value={'ok': False, 'failure_type':
'EXPERIENCE_NOT_FOUND'}`。而 `assert_*` 路径内层用的是 `passed` 而不是 `ok`（同一文件两套词汇）。

**为什么现在提.** M2 的 Agent 循环要把「工具结论」映射到 `agent_trace` / 与 `run_step` 比对时，
必须知道「**两处查找**」这条规则——目前**无处写明**。F1 的「同一 Guard 下结论一致」在
BLOCK/ELEMENT_NOT_FOUND 上已经钉住，但 WAIT_TIMEOUT / ASSERTION_* 这两类会静默漏掉。

**修法（二选一，都不大）.** ① 在 `ToolResult` docstring 里写明两处规则；或
② 加一个只读属性把两处合并：

```python
@property
def step_failure_type(self) -> str | None:
    """与 `steps.failure_type` 对齐的**唯一**读取口（两处落点在此合并）。"""
    return self.failure_type or (self.value or {}).get("failure_type")
```

### P3-2 `failure_type` 由**异常消息字符串**派生，而异常类型本身已携带该信息

`agents/tools.py:508`：`"failure_type": str(e).split(":", 1)[0]`。探针：

```
str(e) = "ASSERTION_VALUE_MISMATCH: target='t' condition='text_equals' expected='a' actual='b'"
split(':',1)[0] = 'ASSERTION_VALUE_MISMATCH'
异常上有结构化的 failure_type 属性吗: []
```

能工作，但**结论依赖于另一个模块的消息格式**。已有一层保护
（`test_assert_text_mismatch_keeps_the_p1_classification` 用**真**异常类，改文案会红），
所以**不是空转**；但改成类→名映射（2 条 dict 项）就不必让「文案」承担「分类」的职责：

```python
_MISMATCH_TYPES = {AssertionValueMismatch: "ASSERTION_VALUE_MISMATCH",
                   AssertionTargetDrift: "ASSERTION_TARGET_DRIFT"}
```

### P3-3 一处断言过宽：`pytest.raises(Exception)`

`tests/unit/test_agent_tools.py:499`：

```python
# `WaitSpec` 的 condition 也是 Literal——非法值必须炸，不是返回 ok=False
with pytest.raises(Exception):
```

docstring 的意图是「非法值必须**炸**」，而 `Exception` 会把 `ToolDependencyError`、
`TypeError` 之类**无关**的异常也算通过。**不是空转**（真返回 `ok=False` 时仍会红），
但收紧成 `pytest.raises(ValidationError)`（或至少 `ValueError`）才与 docstring 等义。

### 小观察（不建议单独立项）

- **门禁 C 的「三张面」实际是 2 个独立面**：`ALLOWED_TOOLS` 由 `TOOL_ASSET_TIER` 派生，
  且门禁 A 已钉住两者相等 → `banned not in ALLOWED_TOOLS` 与 `banned not in TOOL_ASSET_TIER`
  是同一个断言。无害（多一条便宜），但「少查一张就等于留一条注册通道」的说法略夸。
- **门禁 E 的扫描范围是 `agents/**`**：将来若在 `cli/` 或别的包注册工具名，本门禁看不见。
  当前工具层只在 `agents/`，可以接受；M2 装配 `AgentToolkit` 时值得复看一眼。
- **门禁 F 的自证下界偏松**：`len(files) >= 4`（实测 5）、`total > 50`（实测 393）。
  它确实能抓「范围写错成空」，但抓不到「漏掉一个文件」。
- **`_tool_*` 方法是公开可访问属性**：`tk._tool_tap(target=…)` 会**绕过 Guard**。
  当前威胁模型下没问题（Agent 是 LLM，只能经 `call(tool, **kw)`），但 M2 起若有
  **Python 侧**调用者，这条要重新评估（拆私有内部类 / 名字改写）。
- **`screenshot_dir` 默认 `"out/screenshots"` 是 CWD 相对**（与 `DEFAULT_POLICY_PATH` 同款）。
  `policy_config` 已把这个事实写进 docstring，这里没写——一句话即可。

## 六、正面项
