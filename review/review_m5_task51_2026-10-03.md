## 3. 发现

### P3-1 「正式 50 轮」的组成与文档叙述不符——50 轮 = 冒烟 3 + 正式 47
- 实锤：CSV round 1-3 的时间戳（01:44-01:52）是冒烟时段；round 4 起（01:54）才是正式段。断点续跑按「CSV 最大轮号 +1」续，冒烟 3 轮被并入 50 轮的数据集——这本身是续跑设计的合理结果（同 build/设备/套件，间隔 2 分钟，数据质量无虞），且 47 轮 × 153.7s ≈ 2h0m 与文档「01:54-03:54」自洽。
- 问题在文档表述：「基线结论（正式 50 轮，01:54-03:54 UTC）：200 次 run / 1000 条用例」——该窗口实际只有 47 轮 / 188 run / 940 用例；「冒烟 60/60 PASS」也不是独立阶段，而是最终 998/1000 的子集。M6+ 回看基线文档会误读数据构成。
- 修复建议：baseline doc 一段话说清「50 轮 = 冒烟 3 + 正式 47（断点续跑并入），同 build 无重编」即可，数据不用动。

### P3-2 归因在共享边界秒上整体移位一格——总数恰好正确，逐窗归属 ~22% 错位
- 实锤：`invocations_with_runs=155` vs 200 个真实调用。机制：相邻调用共享边界秒（前一窗的 end == 后一窗的 start，秒精度 `Z` 格式 + 两端都含），而 mta run 的 run 行起始恰在本调用 start 的同一秒 → 该 run 落**两窗**，first-window-wins 去重把它归到**前一窗**，级联使 45 个窗空、45 个 run 错挂。
- 兜住了的部分：run_id 去重保证全局总数精确（runs=200 / tc=1000 / flaky / WDA / llm 全部实查正确）；`_suite` 标签（错挂时标错）当前无消费方；CSV 行级 hygiene 列由 shell 独立计算（同一边界形态会把下一调用的 run 计进本行窗——本次全 0 未暴露）。
- 代码层面：`_in_window` 助手（含「字符串比较够用」的 docstring）是**死代码**——aggregate 直接用 SQL 比较，docstring 里许诺的语义没有执行者。
- 修复建议：窗改半开区间 `[start, end)`（与下一窗 start 错开），删 `_in_window` 或让它真正生效；补一个「run 起始恰在边界秒 → 归属本窗而非前窗」的单测（现有 `test_aggregate_dedup_boundary_second` 只断 runs==2，没断归属）。

### P3-3 WDA 泄漏检查未实现为「计数」，残留结论靠 Appium 有界性 + 手动核销
- plan 明文「无 WDA session 泄漏（`xcrun simctl listapps` + **Appium session 计数**）」；脚本里 listapps 输出直接丢弃（`>/dev/null`），只验证命令能跑。基线文档 Gate 第 1 项「残留恰 1 个最后一轮 WDA runner（无累积），已手动清理」没有脚本化证据，依据是 Appium `--session-override` 的有界性（服务端启动参数，仓库内不可复核）。
- 修复建议：每轮把 WDA runner 进程计数（`pgrep -f WebDriverAgentRunner` 或 listapps 过滤）落成 CSV 新列，campaign 末尾断言无累积——把「有界」从口头保证变成每轮数据。

### P3-4 人工 triage 走了 trace db 直接 UPDATE（无审计痕迹）
- 实锤：两条 FAIL 的 failure_attribution 与 detail_json 是事后补写（triage 注释自述「原始 detail 经 steps 记录缺口未落 error 文本」——诚实，且文档披露了「事后补写」）。但 in-place UPDATE 让「trace 是原始记录」的可信度靠纪律不靠机制：补写的行与原始写入的行在库里不可区分。设计 R14-4 说归因由人工 triage 写入、`mta review` 消费——review 只覆盖 recovery 流，归因没有工具通道，这次是直接 SQL。
- 修复建议：加一条最小工具入口（如 `mta report triage <tc_run_id> --attribution ENVIRONMENT_DEFECT --note ...`：UPDATE + 在 detail_json 里结构化记 `{"triage": {..., "tool": "mta", "ts": ...}}`），或 triage 写独立表不动原始行。

### P3-5 杂项
- `preflight()` 的 `xcrun simctl` 依赖调用方 shell 已有 `DEVELOPER_DIR`（M1 的老坑）——环境不齐时 simctl 静默失败 → 误报「无 booted 模拟器」exit 3。脚本开头显式 `export DEVELOPER_DIR=${DEVELOPER_DIR:-/Applications/Xcode.app/Contents/Developer}` 更稳（与 Appium 的启动要求对齐）。
- `render()`（人读报表）无单测——聚合字段全测了，渲染层字段名拼错不会被发现。低价值，顺手补一行快照断言即可。

## 4. 值得肯定

- **Gate 又咬到真东西了**：「Trace 无丢失」判据在 50 轮里现形了两个记录缺口（失败 aux 步骤无 steps 行、FAIL 用例 detail_json 恒空）——当场修复 + fi_13 断言扩展钉住 + 设计意义上这正好补齐 4.2 review P3-2 拍板的「aux 步骤症状留痕」的最后一块。基线跑出了修复，这正是 M5「先跑基线再定指标」的设计意图。
- **披露文化**：steps 缺口、事后补写 triage、 runner 缺旗标的 exit-3 实锤，全都写进基线文档而不是粉饰成「全绿无异常」——这份 baseline 可以当作可信底账用。
- **口径钉在单测里**：8.3（RECOVERED 不进分子）、flaky（含 RECOVERED→PASS）、hygiene 违规 exit 2，全部合成 db 离设备可回归（H18 纯函数纪律延续）。
- **防垃圾数据的设计**：连续 3 次 exit 3 自动终止 + preflight fail-loud + 冒烟先行——本轮实际触发过一次（缺 `--bundle-id`），机制被证明不是摆设。
- **flaky 归因证据链可复核**：两条单发 WAIT_TIMEOUT 的「同转换 49/50、无 WDA 重启、同 build」我实查成立——归因是数据支撑的判断，不是拍脑袋。
