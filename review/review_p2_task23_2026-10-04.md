## 3. 发现

### P2-1 审计脚本改用包内导入后，「脚本路径」调用方式失效（收口前必修）
- 三连实锤：① `.venv/bin/python scripts/p2_audit_recoveries.py --db out/trace.db` → `ModuleNotFoundError: No module named 'tracer'`（第 18 行新增 `from tracer.storage import SEED_SELECT`；以路径运行时 `sys.path[0]=scripts/`）；② 同文件 `-m scripts.p2_audit_recoveries` 正常（`runs=102 … seed_ready=1`）；③ `HEAD~1` 的旧版以脚本路径运行**正常**（旧版只 import stdlib）。
- 影响面：`scripts/p2_seed_recoveries.sh:225` 收尾打印的复核命令、`review/review_p2_task11` 记录的实跑方式、以及任何照抄文档的人，都会直接报错。`tests/unit/test_p2_audit.py` 用包路径导入（`from scripts.p2_audit_recoveries import ...`），天然测不到这条调用面。
- 建议（二选一，都很便宜）：① 脚本顶部加 `sys.path.insert(0, str(Path(__file__).resolve().parents[1]))`，保持「脚本可直跑」的既有惯例（`p1_stability_report.py` 也只用 stdlib）；或 ② 统一改 `-m scripts.p2_audit_recoveries` 并同步 shell 脚本与文档。顺手在 `test_p2_audit.py` 加一条 subprocess 冒烟（exit 0）钉住调用面。

### P3-1「先校验后改状态」只覆盖种子闸门，`create_candidate` 自身失败仍留半状态
- 探针 A：把 `create_candidate` 打成抛 `RuntimeError` → review 已落 ACCEPT、Candidate 0 条、二次 accept 被「不可二次决策」挡死；唯一出路是直呼 `seed_candidate()`（**无 CLI 出口**）。
- 这不推翻顺序纪律（它确实把最高频的失败形态——种子不全——挡在状态变更之前，方向正确），但 docstring 的「顺序不可颠倒」读起来像保证了原子性，实际只是缩小了窗口。建议：CLI 加 `mta review reseed <id>`，或让 accept 对「已 ACCEPT 且无 Candidate」放行补种，把补种做成产品能力。

### P3-2 两个消费闸门字段集不一致 → 部分成功（seed 放行 / export 拒绝）
- `_resolve_seed_fields` 必填 {app_id, 三件套, screen, target_id, candidate_target}；`export_overrides_patch` 必填 {candidate_target, screen, candidate_type}。探针 F（`candidate_type=NULL`）：seed **放行**（Candidate 入库、review ACCEPT），紧接着 export 抛 `ReviewError` → CLI exit 3，但副作用已落、补丁再也导不出来（除非直呼 export）。
- 这是 P2-04「两套校验合一」纪律的反例：同一条 ACCEPT 的两个消费入口各有一套必填集，且 seed 排在 export 之前。建议把「ACCEPT 的全部消费前置条件」合并为单一校验函数，在状态变更前一次跑完（fail-fast、零副作用）。真实数据里 `candidate_type` 有值（"button"），故这是防御性问题而非现网问题。

### P3-3 幂等是「过滤读的涌现属性」，不是构造保证
- 探针 B：seed 出 Candidate 后置 REJECTED，再 `seed_candidate` → 库内 **2 行**、同 `seed_recovery_review_id=1` 两行并存（`lookup` 有意不返回 REJECTED，判重看不见）。当前只有直呼 `seed_candidate` 可达（`decide_review` 二次 accept 被挡），影响有限；但幂等不该依赖「恰好能读见」。建议改 `WHERE seed_recovery_review_id=?` 直查，或对 `experiences.seed_recovery_review_id` 加唯一索引（需与「REJECTED 后可重新学习」的语义边界对齐）。

### P3-4 `origin="experience"` 不在 `loader.ORIGINS` 白名单（Task 4.1 显性债）
- 探针 E：`LocatorStrategy(origin="experience")` 模型接受，但 `repository.loader.ORIGINS=("source","manual")` 判定 False。当前无路径把 Candidate.strategy 喂给 loader，不构成拦截；但 Task 4.1（Promotion 写 overrides，设计 9.2「记录 origin: experience」）落地前必须先扩 ORIGINS，否则一上线就 fail-loud。建议与 Task 2.4 的三条接线地雷并列写进 plan。

### P3-5 审计机器可读产物字段面已变，`docs/p2_data_audit.json` 未重生成
- 实跑逐键比对：`seedable_accepts` 每行新增 `note` / `recovery_id` / `review_status` / `seed_tc_run_id` 四键（markdown 表列确实不变）。Task 2.3 记录的「签名与输出列不变」只对 markdown 成立；json 是 M2 消费 CandidateSeed 的输入，建议重跑刷新，并把该句限定为「markdown 列不变；json 增 4 键」。

### P3-6 失败路径留下空 `experience.db`
- 探针 G：悬空链 exit 3 时 `out/experience.db` 已被创建（`SQLiteExperienceStore(args.exp_db)` 在 `decide_review` 之前构造并触发 migrate）。空库无害，但「失败却产生新文件」违反最小副作用；构造可挪到校验通过之后或惰性化。

### P3-7 杂项
- `decide_review` 中 `_resolve_seed_fields` 被调用两次（预校验 + `seed_candidate` 内重复），重复查库；可给 `seed_candidate` 加内部参数跳过（记录备查，非必须）。
- `_resolve_seed_fields` 的 `seed_step_id == 0` 分支与 `not row.get(k)` 语义重叠（0 本就 falsy）——显式化的冗余，保留可读性即可。
- Experience 不携带 element type（`candidate_type`）：与 Promotion 写完整 override 的需求相关（设计 9.2 未提），Task 4.x 需回查 recovery 行或另存。

## 4. 值得肯定

- **顺序纪律是「先想清楚失败形态再写代码」的范例**：没有把校验塞进 `create_candidate` 了事，而是意识到「状态已 ACCEPT → 二次 accept 被挡」会让失败**不可恢复**，于是把校验前移。探针 A 证明推理方向正确（窗口显著缩小），剩余窗口是同一思路的下一步，而不是反例。
- **SEED_SELECT 的单一真值源是跨任务的纪律延续**：审计（Task 1.1）与消费（Task 2.3）共用同一 join 片段，且审计脚本是「改为消费既有真值源」而不是复制一份——P2-04「两套校验合一」没有停在 Guard 一处。
- **事件名 fail-loud 且 12/12 逐字对齐**：`EXPERIENCE_EVENT_TYPES` 与设计差集双向为空；`action_taken` 留空以免污染 P1 稳定性报告的 `RESTART_WDA` 判据——对 P1 判据的副作用是被显式考虑过的，不是碰巧躲开。
- **P1 回归碰撞的处理方式值得留档**：不删弱 H15 断言，而是补全测试替身的数据缺口（`bundle_id`）+ 显式 `--exp-db` 隔离，并顺手加一条 Candidate 正向断言——测试因此变强；全仓 grep 实证无任何测试写 `out/experience.db`。
- **E5 三层闸门（消费侧 / 模型 / Store）**：不靠单点自觉，审计暴露缺口与消费方拒绝消费是同一判据的两侧。
