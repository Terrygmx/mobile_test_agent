## 3. 发现

### P2-1 Promotion Rate 的分子未限定 VERIFIED —— 报告能渲染出 `300.0%`

- 设计 §17 的定义是 `Verified 中被 Promote 的比例`，即 `promoted ∧ status==VERIFIED / VERIFIED`；实现是 `sum(e.promoted) / status_counts["VERIFIED"]`（`experience_metrics.py:162`、`:214`）。
- 二者在 §9.4 明文场景下必然分叉：**「Promotion 后 DEGRADED 不自动撤销已进 Git 的策略」**——一条 promoted 的经验被滑动窗口降级后，仍在分子里、却不在分母里。
- 探针（真跑纯函数）：

  | 库内容 | promoted | VERIFIED | `promotion_rate` | 渲染 |
  |---|---|---|---|---|
  | 1 VERIFIED(promoted) + 1 DEGRADED(promoted) | 2 | 1 | **2.0** | `200.0%` |
  | + 1 REJECTED(promoted) | 3 | 1 | **3.0** | **`300.0%`** |

- 一个「比例」指标报出 300% 是**可见的错误**，而设计 §17 把它列为观察 Promotion 健康度的三项之一。修复是一行：`promoted = sum(1 for e in experiences if e.promoted and e.status is ExperienceStatus.VERIFIED)`。
- 建议：顺手把 `promoted` 字段的语义在 dataclass 注释里写明（是「曾被 promote 的条数」还是「VERIFIED 中已 promote 的条数」）——现在两者同名，是这类口径错的高发形态。

### P2-2 Resolution Rate 的分子用「上下文编码的分类标签」，整类漏计被 Experience 救回的断言目标漂移

- 定义（本模块 docstring 与 commit 都写明）：分子 = 「由 Experience 解决的 Recovery」，实现取 `recovered_kind == "RECOVERED_EXPERIENCE"`（`:152`）。
- 但 `recovered_kind` 是**设计 §10 的分类标签**，它对「断言目标漂移」这一上下文**压过机制名**（`runner/result.py:128-147`，原文理由：「对使用者有意义的问题是『改的是定位还是期望值』」）。所以 `recovered_kind("experience", context="assertion_target")` = `"RECOVERED_ASSERTION_TARGET"`。
- 而这条路径**是活的**：`cli/pipeline.py:447` 正是 `context="assertion_target"`，`_aux_recover` 的 docstring 明确「断言目标漂移（矩阵 #15）……经引擎取回已校验的候选策略」，矩阵 #15 就是「aux 路径的 Experience 命中」。探针（真实 detail 形状）：

  ```
  {"recovery_kind": "experience", "recovered_kind": "RECOVERED_ASSERTION_TARGET",
   "recovery_context": "assertion_target", "recovery": {...}}
  → recovery_attempts=1  experience_resolved=0  rate=0.0
  对照（同机制、非断言上下文）: experience_resolved=1
  ```

- 后果：设计 §17 的**核心指标**对整整一类 Experience 恢复记 0——分母算了、分子不认。这不是「另一种口径」，是**定义与实现不一致**：要么改实现（推荐），要么改 docstring 与 §17 的定义，二者不能同时成立。
- 修复同样是一行，且**数据已经在 detail 里**（`_record_aux_recovered` 同时写 `recovery_kind` 与 `recovered_kind`）。建议判据改为「机制名」：

  ```python
  resolved = sum(1 for d in attempts
                 if d.get("recovery_kind") == "experience"
                 and "recovered_kind" in d)   # 有分类标签 = 该步真的恢复成功
  ```

  探针逐形状验证过（六种真实形状全部正确，**只有**「aux 断言·Experience 成功」由 0 变 1）：

  | 管线真实形状 | 现状分子 | 建议分子 |
  |---|---|---|
  | 动作步·Experience 成功 | 1 | 1 |
  | 动作步·LLM 成功 | 0 | 0 |
  | 动作步·未恢复 | 0 | 0 |
  | **aux 断言·Experience 成功** | **0** | **1** |
  | aux wait·Experience 成功 | 1 | 1 |
  | aux 重跑失败（`recovery_kind` 有、`recovered_kind` 无） | 0 | 0 |

  第二个条件（`"recovered_kind" in d`）是必需的：`_aux_rerun_failed` 会在**失败**步骤上写 `recovery_kind`（那是事实），只用机制名会把失败也算成解决。

### P3-1 `revalidation_attempts` 被非跳变标记污染：真降级 1 次会报成 2 次

- 判据是 `to_status == "DEGRADED"`（`:191`），而 `mark_revalidation_required`（E8 的 `REVALIDATION_REQUIRED`）**刻意**写 `from == to` 的同值行——若该条 Experience 当前正是 DEGRADED，这条标记就被当成一次「降级尝试」。
- 探针：`[VERIFIED→DEGRADED(SLIDING_WINDOW), DEGRADED→DEGRADED(REVALIDATION_REQUIRED), DEGRADED→VERIFIED(REVALIDATED)]` → `attempts=2, successes=1, rate=0.5`；真实语义应是 **1/1 = 100%**。降级越频繁、指纹变化越多，这个偏差越大（方向恒为「低估重验证成功率」）。
- 修复：判据加「真跳变」条件 —— `ev.get("to_status") == "DEGRADED" and ev.get("from_status") != "DEGRADED"`。`collect_experience_metrics` 已经把 `from_status` 一并取出（`:257`），数据已就位。
- 附带：`has_state_event_since_transition` 早已用「`from_status IS NULL OR from_status != to_status`」界定跳变——**同一个概念在本仓已有权威判据**，这里没用它是典型的「两套实现」。

### P3-2 `latency_ms` 用 `int()` 毫秒截断 —— cache 段恒为 0，设计 §17 的梯度验证目的落空

- `agent/recovery.py` 三处计时都是 `int((time.monotonic() - t) * 1000)`（cache / store / llm）。
- 探针（各 200 次）：进程内 `dict.get` 的 int-ms 样本集 = `{0}`；**内存** sqlite 点查的样本集也 = `{0}`（均值 0.000ms）。即亚毫秒操作**一律记 0**。
- 后果直接印在产物上：`out/p2_m2_gate/experience_metrics_demo.html` 的 run2 `store` 段就是 **`0.0ms`**（1 个样本）——而本模块 docstring 自己写着「`deterministic` …标 N/A 而不是填 0——**填 0 会被读成『快到测不出』，那是另一种谎**」。同一份文件里，一处按这条纪律办了、另一处（计时精度）没办。
- 而设计 §17 给延迟指标的目的正是「验证『确定性 < Promoted < Cache < Store < LLM』的速度梯度」——cache 恒 0、store 常 0，这条梯度在 ms 粒度上**不可验证**（`cache < store` 会退化成 `0 < 0`）。
- 建议（择一，都在 5 行内）：① 记 `round(x * 1000, 3)` 或直接记微秒（`int(x * 1_000_000)`，渲染时再换算）；② 计时用 `time.perf_counter()`（单调高分辨率）。顺带把「cache 段可能为 0」写进渲染说明，避免读者把它读成「快到测不出」。

### P3-3 测试文件有 56 行逐行重复块 + 2 个被遮蔽的同名测试

- `tests/unit/test_report_experience_metrics.py` 的 413–468 与 471–526 **逐行相同**（56 行 × 2，含 `# --- CLI 端到端…` 分节注释），`test_cli_run_html_includes_metrics_when_exp_db_exists` 与 `test_cli_run_html_omits_metrics_when_exp_db_absent` 各定义两次。

### P3-4 渲染层不转义：`recovered_kind` 的值原样进 HTML

- `render_experience_metrics_section` 把 `m.by_recovered_kind` 的**键**直接插进 `<code>{k}</code>`，把 `ev.get(...)` 的计数插进文本——全程无转义；而 `report/html.py` 里就有 `_esc`（同一包、已被同文件的标题使用）。
- 探针：构造 `recovered_kind = "<script>alert(1)</script>"` 的 step detail → 渲染结果里 `<script>alert(1)</script>` **原样存在**。
- 实际风险低（值来自引擎的固定枚举或 `RECOVERED_<大写机制名>`），但 trace 库是**可写的外部输入**，而报告会被打开在浏览器里。建议：给渲染的每个插值点套 `_esc`（与 `html.py` 同款），或把渲染函数搬进 `report/html.py` 复用其转义设施。

### P3-5 事件采集面用 `LIKE 'experience_%'`：漏 4 个事件类型 + `_` 是 LIKE 通配符

- `collect_experience_metrics` 取 `WHERE event_type LIKE 'experience_%'`。实测 `EXPERIENCE_EVENT_TYPES` 12 个里只有 8 个带该前缀；漏掉的是 `candidate_created` / `candidate_verified` / `promotion_proposed` / `promotion_approved`。
- **当前无影响**（Promotion Rate 走 experience 库的 `promoted` 列，不读事件），但这是**隐式白名单**：将来任何一个指标想用 `promotion_*` 事件，都会静默取到 0 而不是报错——正是本项目「静默的 0 比报错更难查」的形态。
- 顺带一个 SQL 坑：`LIKE` 里 `_` 是**单字符通配符**，`'experience_%'` 也会匹配 `'experienceXlookup'`（本仓无此事件名，属潜在坑）。建议改 `event_type IN (...)` 显式列举，或 `GLOB 'experience_*'`。

### P3-6 `test_latency_unmeasurable_segments_are_absent_not_zero` 的 docstring 与断言互相矛盾，且验证不了梯度

- 测试名与 docstring 说「不可测的段**不出现**在 dict 里」，断言却是 `m.latency == {"cache": None, "store": None, "llm": None}`——键**都在**，值才是 `None`。「absent」的是 `deterministic` / `promoted`（由渲染层硬编码行提供），不是这三个键。名字该改成 `..._are_none_not_zero`，或断言改准。
- 同族的 `test_latency_gradient_splits_cache_and_store` 断言 `cache < store < llm`——那**是测试自己注入的数据**（1/3ms vs 10/30ms vs 400ms），不是系统行为。纯函数测试无法验证「系统真的满足该梯度」，这个事实应在测试 docstring 里写明，否则下一位读者会把它当成就绪的梯度证据（结合 P3-2，真实系统里恰恰不成立）。

## 4. 未验证 / 存疑

1. **Gate M4 本次未复跑**：环境无 booted 模拟器 / Appium / LLM 网关。只核对 `out/p2_m2_gate/summary.json` 与 `experience_metrics_demo.html`（后者已逐字段解析，见 §1 表 13）。Gate M4 的判据证据在 `06f6ea6` 与审计里。
2. **`promoted_but_recovering` 的假阳性面**：判据是「promoted=True ∧ 本期有成功的 execution」。若一条经验被 promote 后**又**因指纹/屏变化重新进入恢复并成功，也会被算成「疑似 revert」。当前实现已在报告里标注「推断」，可接受；但基线建起来后若这个数长期不为 0，需要区分「revert」与「策略在链尾但更前面的策略失效」两种成因。
3. **`collect_experience_metrics` 读全表 `steps` 的规模**：指标是累积口径（有意），但读的是**全部历史 run** 的全部步骤。当前数据量下无问题；若 trace 长期不清，这里会成为报告生成的耗时点。未做压测。
4. **`status_counts` 对未知状态的静默处理**：`status_counts[exp.status.value] = ... + 1` 会把四态之外的键也加进去，而渲染只列四态 → 未知状态静默消失。当前 `ExperienceStatus` 是四值枚举，不可达；仅登记。

## 5. 值得肯定

- **分母的选择是本任务最有价值的一处判断，而且理由是可证伪的**：没有照 plan 字面用「`experience_*` 事件数」，而是先确认「`no_store` / `incomplete_key` / `no_page_source` / `no_find_all` 四类**根本没尝试**」（`agent/recovery.py` 四处 `return` 都在 `_emit` 之前），再据此换到 `steps` 的步骤级标记。方向是**避免系统性高估**——这是 E11 的同一条纪律换了个面。探针逐条复核，四处 return 位置全部属实。
- **「没跑过」与「跑了全失败」在整条链路上都被分开**：`_rate` 返回 `None`、渲染 `N/A`、`0 / 0` 双值展示、`deterministic`/`promoted` 标 N/A 并写清原因而不是填 0。这个一致性是刻意做出来的（docstring 里专门写了「填 0 会被读成『快到测不出』，那是另一种谎」），比数字本身更有价值。
- **缓存接线的两条红线不是靠注释声明的，是靠专测钉住的**：「命中与未命中共用同一段 Guard+记账」用「缓存有候选但这次 Guard 判 0 匹配 → 照样记 FAILURE 样本」来证明——这比「断言 guard 被调用」强得多，它同时证明了记账路径没有被缓存绕开。红线②（缓存存的是 ranker 的**输入候选集**）用「命中/未命中时首条被评估候选 id 一致」证明，也正是 E1 的正确落法。
- **`validated_builds` 三选一的拍板是从矩阵 #6 自身推出来的**，而不是挑一个「看起来最安全」的：指出 (b) 的硬闸门会让「新 build 首用走一次完整验证」**永远无法发生**（首用即被拦 → 集合永远学不到新 build，死锁），且该 reason 在 4.7 表里没有位置（强行加会污染 E6 滑动窗口）。这是把一个「安全保守」选项证伪的论证，比选它更有价值。
- **`_collect_metrics_if_any` 的「库文件不存在就不构造 Store」**：报告生成是只读动作，不该顺手在磁盘上建出一个空库——与 review_p2_task23 P3-6 同族的最小副作用纪律，且有专测断言 `not exp_db.exists()`。
- **G10 的实证是真产物**：用 Gate M2 两次真实 run 的 trace 算出 `0.0% → 100.0%`（run1 由 LLM 救、`llm` 段 18004.0ms；run2 由 Experience 救、`llm` 段 N/A），而不是手写一张示意表。设计 §17 说「先建基线」，这里给出了基线的起点。
- **`06f6ea6` 的 P2-1 修法是手术而不是重写**：行级插入 + `assert before in after`（全文逐字节保留）——上一版评审的 P2 是「人的注释被静默抹掉」，这一版把「不可静默覆盖」落到了字节级。
