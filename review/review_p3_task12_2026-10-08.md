## 3. 发现

### P2-1 「shipped yaml ↔ 内置默认值」的守卫**空转**：`config/policy.yaml` 不在了它照样全绿

**现象**（`tests/unit/test_policy_config.py:28-32, 76-86`）：

```python
def test_shipped_policy_yaml_loads():
    policy = load_policy(Path("config/policy.yaml"))     # ← 相对路径
    assert policy.autonomous.enabled is True             # ← 恰好等于内置默认值
    assert policy.exploration.max_steps == 100           # ← 恰好等于内置默认值

def test_shipped_policy_yaml_equals_builtin_defaults():
    assert DEFAULT_POLICY_PATH == Path("config/policy.yaml")   # ← 对常量自身取等，恒真
    assert load_policy(DEFAULT_POLICY_PATH) == PolicyConfig()
```

两条测试的**断言目标**（`enabled=True`、`max_steps=100`、`== PolicyConfig()`）**正是 `load_policy` 在「路径不存在」时返回的东西**（`agents/policy_config.py:200-204`：`if not p.is_file(): return PolicyConfig()`）。于是**文件在不在，结果一样**。

**探针证据**（探针⑨，非破坏性：只 monkeypatch 模块属性 + 换 CWD，未动任何项目文件）：

```
⑨ DEFAULT_POLICY_PATH = config/policy.yaml  存在 = True
  文件缺失时 test_shipped_policy_yaml_equals_builtin_defaults → **仍然绿**
  文件缺失时 test_shipped_policy_yaml_loads 的断言 → enabled=True max_steps=100 → 也**绿**

⑩ CWD = /private/tmp | config/policy.yaml 存在 = False
  test_shipped_policy_yaml_loads:                enabled is True → True / max_steps == 100 → True
  test_shipped_policy_yaml_equals_builtin_defaults: 两条断言 → True
```

也就是说：这两条测试**既不能发现文件被删/改名，也不能发现 CWD 不对**——而「文件缺失 → 默认值」的**唯一**守卫就是它们。

**为什么是 P2 而不是 P3**：提交信息「关键决策 6」把这条测试写成**保证**——

> 「以后校准初版值时**必须两处一起改**，本测试会拦住只改一处。」

审计文档 `p3_data_audit.md:336-338` 同样这么说。**声称的能力 > 实际能力**，而修法一行。这正是本项目 `MEMORY.md` 记下的那类错（「『固化』必须是一条会自动失败的测试」），且与上一轮 P3-3（「声称两条实为 3 条」）同源：**对守卫强度的描述必须能被实测支持**。

**为什么现在报**：Task 1.2 交付的**不是功能，是安全网**。一个空转的网比没有网更糟——它会让「校准初版值」这个**下一步动作**（plan 里明说「初版需校准」）在没有护栏的情况下进行，而「文件缺失」与「文件在」给出两套配置这件事，恰恰是回归底线要防的。

**修法**（把「文件必须在」变成断言，并锚定仓库根，别依赖 CWD）：

```python
_REPO = Path(__file__).resolve().parents[2]        # tests/unit/ → repo root

def test_shipped_policy_yaml_equals_builtin_defaults():
    path = _REPO / DEFAULT_POLICY_PATH
    assert path.is_file(), (
        f"入库的 {DEFAULT_POLICY_PATH} 不在了——本测试其余断言会因此**空转**"
        f"（load_policy 对缺失路径返回默认值，与期望值恰好相等）")
    assert load_policy(path) == PolicyConfig()
```

（`test_shipped_policy_yaml_loads` 同样改成 `_REPO / ...` + 先 `is_file()`。附带建议：给 `load_policy` 加
`strict=True` 或「显式传参但文件不存在 → fail-loud」的开关，见 P3-2。）

### P3-1 两张权重表的**值**没有任何值域闸门：负权重静默接受

**现象**：`PolicyConfig` 的两个权重字段是裸 `dict[str, int]`，`field_validator` **只校键集**，不校值：

```python
planner_weights: dict[str, int] = Field(default_factory=lambda: dict(PLANNER_WEIGHTS))
...
@field_validator("planner_weights")
def _planner_weights_keys(cls, v): _require_exact_keys(...); return v      # ← 只看键
```

而同文件**所有标量段**都有 `ge=0`（`ExplorationPolicy` 四字段 / `EvidencePolicy` / `EscalationPolicy`）。

**探针证据**（探针⑪）：

```
  evidence 全 6 键，crash=-1   → **接受** {'crash_detected': -1, ...}
  evidence 全 6 键，llm=-99    → **接受** {'llm_hypothesis_only': -99, ...}
  planner  全 3 键，impact=-1  → **接受** {'impact': -1, 'history': 2, 'risk': 5}
  planner  全 3 键，risk=-100  → **接受** {'impact': 3, 'history': 2, 'risk': -100}
  ── 对照（同一次探针）──
  exploration.max_steps=-1              → PolicyConfigError ✓
  evidence.attribution_threshold=-1     → PolicyConfigError ✓
  escalation.guard_blocks_before_escalate=-1 → PolicyConfigError ✓
```

**口径不符**：模块 docstring（`policy_config.py:14`）与 `config/policy.yaml` 头注释都写

> 「加载器对**未知键 / 错型 / 负预算** fail-loud——拼错的键不会静默生效。」

负值在标量上被拦、在**权重表上漏掉**。而这两张表的消费者（`score_evidence` / `priority_score`，M2/M5）拿到负权重会算出**负分**，直接污染「归因是否达标」（F10）与「先做哪个」（§5.2）——即 P3 的定档理由是「现在还没有消费者」，一旦 M2 接线就升级为 P2。

**修法**（一行量级，两处）：

```python
_NonNegInt = Annotated[int, Field(ge=0)]

planner_weights: dict[str, _NonNegInt] = Field(default_factory=lambda: dict(PLANNER_WEIGHTS))
diagnosis_evidence_weights: dict[str, _NonNegInt] = Field(
    default_factory=lambda: dict(DIAGNOSIS_EVIDENCE_WEIGHTS))
```

或把值域检查并进已有的两个 `field_validator`（与键集检查同一个报错出口，消息里点名坏键）。**建议同时把 yaml 头注释的「负预算」改成「负值」**，让声称与覆盖面一致。

### P3-2 `load_policy` 无法区分「文件缺失」与「路径拼错」，且默认路径是 **CWD 相对**

**现象**（`agents/policy_config.py:61, 200-204`）：

```python
DEFAULT_POLICY_PATH = Path("config/policy.yaml")     # ← 相对路径，按 CWD 解析
...
if not p.is_file():
    return PolicyConfig()                            # ← 缺失、拼错、是目录、None 全走这一条
```

**探针证据**（探针③）：

```
  None                    → 静默返回默认值（max_steps=100, enabled=True）
  <tmp>/definitely_missing.yaml → 静默返回默认值
  config/polcy.yaml（拼错）      → 静默返回默认值   ← 与上面**长得一模一样**
  config/policy.yaml（正确）     → 静默返回默认值
  <tmp>（目录）                  → 静默返回默认值
```

**两个后果**：

1. **生产侧**：`mta plan` 从仓库外的目录跑（或 `DEFAULT_POLICY_PATH` 被当成相对路径用），**静默拿到内置默认值**——用户的 policy.yaml 被无声忽略。这**不是**「文件缺失 → 默认」那条回归底线（那是设计要求的），而是「**你以为你在用配置文件，其实没有**」。
2. **将来**：一旦加 `--policy <path>`（`_check_autonomous_env` 的 docstring 已经在用 `args.policy`，见 P3-3），一个拼错的路径会**静默退回默认值**，而 `--policy` 的全部意义就是「我指定了配置」。

**为什么现在报**：模块的定位是「启动期唯一配置入口」，且 F7 的原文就是「**启动时**校验而不是运行时才拦」。一个在启动期**静默忽略用户输入**的入口，与这条 F7 精神相反；而它的行为差异只在「文件真的坏了」时可见——正是最难查的一类。

**修法**（不破坏回归底线）：把「**调用方没给**」与「**给了但不存在**」用哨兵分开（与 `experience/knowledge.py::_UNSET` 同一手法，`MEMORY.md` 有记录）：

```python
_UNSET = object()

def load_policy(path: str | Path | None | object = _UNSET) -> PolicyConfig:
    if path is _UNSET or path is None:      # 调用方没给 → 默认值（回归底线）
        return PolicyConfig()
    p = Path(path)
    if not p.is_file():                     # 显式给了却不在 → fail-loud
        raise PolicyConfigError(f"policy 文件不存在：{p}（显式指定的路径必须存在；"
                                f"想用内置默认值请传 None）")
```

并把 `DEFAULT_POLICY_PATH` 的解析锚到仓库根（例如 `Path(__file__).resolve().parents[1] / "config/policy.yaml"`），或在 docstring 明写「**相对 CWD**」这个事实。

### P3-4 「错型 fail-loud」的实际覆盖面比声称的窄：pydantic lax 强转 + `EnvKind(bad)` 抛 `ValueError`

**现象 A —— pydantic 默认 lax 模式**（`_Frozen` 未设 `strict=True`）。探针② 十例：

```
  max_steps: "100"（数字字符串）  → **静默接受** 100
  max_steps: 3.0（浮点整）        → **静默接受** 3
  enabled: "true"（字符串布尔）   → **静默接受** True
  enabled: yes（YAML 布尔）       → **静默接受** True
  max_steps: true（布尔当整数）   → **静默接受** 1        ← 预算从 100 静默变成 1
  weights: {impact: "3", ...}     → **静默接受** {'impact': 3, ...}
  weights: {impact: true, ...}    → **静默接受** {'impact': 1, ...}
  weights: {impact: 3.0, ...}     → **静默接受** {'impact': 3, ...}
  ── 只有真坏值才拒 ──
  max_steps: 3.7 / max_steps: abc → PolicyConfigError ✓
```

`max_steps: true → 1` 是最尖的一例：F11 规定超预算即 `*_BUDGET_EXCEEDED` 并停止，一个静默变成 **1 步**的预算会让探索在第一步就停——**配置错误表现为功能退化，而不是报错**。而 `tests/unit/test_policy_config.py:55-59` 的 `test_wrong_type_fails_loud` 用的是 `"abc"`（唯一会被拒的那种），所以「错型 fail-loud」的**实际覆盖面**没有被测试暴露。

**现象 B —— 前置函数的第三种出口**。`_check_autonomous_env` 的 docstring 说「两条判据，**任一不过即 `SystemExit`**」，但探针⑤：

```
  EnvKind 成员 = ['sandbox', 'staging', 'production']
  'PRODUCTION' → ValueError: 'PRODUCTION' is not a valid EnvKind
  'Prod' / 'prod' / '' / None / 'sandbox '  → ValueError（同上）
```

即 **`EnvKind(env_kind)` 是第三个出口，抛的是 `ValueError` 而不是 `SystemExit`**。后果：CLI 上会打一整段 traceback（而不是那句带 `F7` 的干净消息）；更重要的是——**任何用 `except Exception` 兜底的调用方都会把 production 否决一起吞掉**。当前没有生产调用者，所以是 P3；接线时它会变成 P2 级的口子。`test_gate_accepts_env_kind_enum` 只测了合法枚举与合法字符串，**没有任何测试覆盖非法 `env_kind`**。

**修法**：① `_Frozen` 加 `model_config = ConfigDict(extra="forbid", frozen=True, strict=True)`（一行；若担心 `strict=True` 连带影响别处，至少在 `ExplorationPolicy` / `EvidencePolicy` / `EscalationPolicy` 的 int 字段上用 `StrictInt`）；② `_check_autonomous_env` 里把 `EnvKind(env_kind)` 包起来，坏值也走 `SystemExit` 并给出同样的 F7 指引（`try: kind = EnvKind(env_kind) except ValueError: raise SystemExit(f"F7: 未知环境 {env_kind!r}…")`），并补一条 `test_gate_rejects_unknown_env_kind`。
