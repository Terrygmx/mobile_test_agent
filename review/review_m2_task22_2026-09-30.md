## 2. 问题清单

### R12-1（P2）assertion `_judge` 无 stale 防护——R11-3 同源洞在新代码重现

wait.py 的 R11-3 修法是 `_check` 内把属性读取的驱动异常转成「本轮不满足」继续轮询（wait.py:150-157）。但 assertion.py 的 `check()` 循环里 `_judge(spec, el)` 直接读 `el.text` / `el.is_enabled()`，**没有同款防护**——转场期 find 成功后读属性抛 stale，直接冒泡 → 步骤 FAILED，且既不是 ValueMismatch 也不是 TargetDrift，不在 recovery 白名单。断言恰恰最常发生在转场之后，这是 R11-3 描述的同一场景。修法照抄 wait.py：`_judge` 外包 try/except（保留 ValueError fail-loud），当作「本轮不满足」继续轮询至 deadline。

### R12-2（P2）element_count expected=0 且元素确实不存在 → 应 PASS 却抛 ValueMismatch

schema 的 validator 只拦 `expected is None`（schema.py:155-158），**expected=0 是合法值**（断言「元素已从列表消失」）。但 `check()` 的 ElementNotFound 分支无条件走 `_mismatch(0)`（assertion.py:144-145），不判断 expected==0。实测探针：

```
AssertionSpec(condition='element_count', expected=0)，find 抛 ElementNotFound
→ BUG confirmed -> ValueMismatch raised: expected=0 actual=0
```

expected=0、actual=0、却判 FAIL——语义自相矛盾（docstring 自己写了「找不到意味着 count=0，是值判定」，值判定就该比对 expected）。修法一行：ElementNotFound 分支先判 `spec.expected == 0 → return passed 结果`。或与 not_exists 统一口径。补 2 条测试（expected=0 找不到 → PASS；expected=0 找到 → mismatch）。

### R12-3（P3）`detail.kind="assertion_target"` 全库无消费点

设计 7.3 要求步骤带 `detail.kind = "assertion_target"`，实现里它只存在于 runner:125 的注释——trace 落库的是异常字符串前缀 `ASSERTION_TARGET_DRIFT:`，结构化 `result`（expected/actual/timeout）不落库。事后分析无法区分「值不符」与「漂移」之外更细的维度。Task 2.4 schema 迁移加 warning/detail 列时一并消费，现在记账即可。

### R12-4（P3）断言漂移恢复 = tap，恢复后不重验断言

`_try_recovery` 对 AssertionStep 统一给 `action="tap"`（注释已说明）。这与设计一致（故障矩阵 #15 的验收就是步骤 RECOVERED），**但注意语义**：text_contains 类断言漂移恢复后，断言值从未对新元素验证——RECOVERED 状态本身承担了「此步未真正断言」的信号。建议 M4 漂移 build 验收时把「RECOVERED ≠ PASS」写进报告口径，避免被误读为断言通过。

### R12-5（P3）`AssertionValueMismatch.result` 结构化结果仅存在于异常属性

同 R12-3：结构化结果没进 trace，error 字段只有格式化字符串。与 2.4 一起处理。
