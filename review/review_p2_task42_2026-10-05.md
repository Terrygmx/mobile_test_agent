## 3. 发现

### P2-1 同 id 并入用 `yaml.safe_dump_all` 整文件重序列化——手写 overrides 的注释全部丢失（探针实锤）
- 用**真实手写**的 `repository/overrides/elements/LoginView.yaml`（4 行头注释 + 行内注释，含 H7 幂等性理由）做并入实验：合并后 **头注释与全部行内注释消失**（`before.splitlines()[0] in after` = False）；git diff 从「+4 行策略」变成整文件重排（58→69 行、重排序/引号风格全变）——docstring 宣称的「git diff 可审计」被实质削弱，且每次对该 screen 的 promote 都会再剥一层。
- 功能无损（4 docs 解析正确、ids 对、strategy 落链尾），但 overrides 是「人的策略判断」层（设计 5.1），注释承载出处与理由（M1 手写起点、M3 行号语义、幂等声明）——静默抹掉属于人的数据丢失。
- 修复建议：①文本手术式插入——定位匹配 doc 的 `strategies:` 块尾插一行，其余字节不动（该文件结构稳定，行级插入可靠）；或 ②换 ruamel.yaml 保留注释；至少 ③docstring 把「git diff 可审计」改准并登记注释损耗。倾向 ①—— promoter 的写入对象是固定结构的手写文件，手术式插入比 YAML 重序列化更符合「不可静默覆盖」的同族纪律。

### P3-1 工作提交的身份是 gate 脚本身份（authorship 断裂）
- `8dea8bb` 的 author/committer 是 `gate_m4 <m4@gate>`——verify_p2_m4.py 的 `_git()` 注入 `GIT_AUTHOR_NAME=gate_m4`，工作提交在同一环境下做出，env 泄漏进了 authorship。后果：这条交付提交无法追溯到开发者本人（`git log`/blame 全断）。建议：①本条可 `git rebase --root` 改写或至少在记账注明；②流程约定——gate 脚本跑完后 `unset GIT_AUTHOR_*` 或工作提交永远在干净 shell 做（与 P1 的「宣称≠存在」同族：提交者身份也是 trace 的一部分）。

### P3-2 revert 后的稳定态值得在报告里解释一句
- G5 显示 revert 后 run = RECOVERED_EXPERIENCE（经验命中走恢复路径）——语义正确（overrides 的 u_v2 被 revert，normal find 失败 → recovery 捞回），但意味着 revert 后的**每个**后续 run 都稳定多付一次失败 find + 恢复样本记账，直到重新 promote 或 Strategy 语义改变。这不是缺陷（正是 Store 记账原样的价值：下一次 promote 的证据还在），但基线报告读者会把这种 run 的 FAIL/RECOVERED 波动当成新问题——建议 verify 脚本或记账里一句话点破。

### P3-3 杂项
- `_merge_experience_strategy` 的重复检测按 `(origin, value)` 对——同 id 不同 value 的二次 promote 会再追加一条（多条 experience 策略并存是合法形态，resolver 排序处理）；行为对，值得在 docstring 点一句「多次漂移转正 = 多条回落策略并存」。
- fi_support 的 `run_matrix` 本轮加 `bundle_id`/experience_store 接线参数——接口在长，注意别让它变成第二个 `**kwargs` 垃圾场（当前还好）。
