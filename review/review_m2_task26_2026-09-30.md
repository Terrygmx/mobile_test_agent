## 4. 问题清单

### R16-1（P1）7.4「取更严格」被 or 链违反——探针实锤，安全级

`cli/pipeline.py::_run_action_step`：

```python
idem = step.idempotency or meta_idem
risk = step.risk or meta_risk
```

设计 7.4-1：`declared` = step 与 element 已声明值中**更严格**的一个；`effective_risk = max(step, element, screen, env)`。探针实测（FakeRepo 元数据 HIGH/NON_IDEMPOTENT + step 声明 LOW/IDEMPOTENT）：

```
effective_risk = Risk.LOW            | element metadata = HIGH
effective_idempotency = IDEMPOTENT   | element metadata = NON_IDEMPOTENT
```

**安全影响**：用例层一行 `risk: LOW` 可把元素 metadata 声明的 HIGH/CRITICAL 压掉 → Guard 按 LOW 放行一个 metadata 判定为高危的动作；H7 非幂等重试保护同样可被 `idempotency: IDEMPOTENT` 一行绕过。这正是 10.1 Guard "不可被 testcase 绕过"想防的事，但绕过点在 Guard 上游的推导层。讽刺的是 `policy.effective_risk/effective_idempotency` 就是为多声明源取严设计的（Task 2.5 已测），pipeline 没用它们。schema ActionStep 确实有这两个字段（非死路径）。

**修法**（一行级）：`risk = max(filter(None, (step.risk, meta_risk)), key=...)`、idem 用 `policy._IDEMPOTENCY_STRICTNESS` 取严——或直接把两个声明都传给 policy 纯函数；补 2 条"step 压不掉 metadata"的测试。**进 2.7 前必修。**

### R16-2（P1）真机模式 fail-quiet：配置缺失伪装成 5 条 FAIL + exit 1

真机分支 `runner = None`（装配留 2.7）→ 实测 `mta run --suite smoke`（无 --fake-driver）：

```
login_001: FAIL (AttributeError) -- AttributeError: 'NoneType' object has no attribute 'run_step'
... 5 条全 FAIL，run: exit 1
```

且 5 条假 FAIL + runs FAIL 终态**写进了 trace.db**。按 8.4 这是前置配置错误应 **exit 3**；按 8.2 纪律（不得把编程/配置错误伪装成测试失败）和本代码库自己反复强调的 fail-loud 原则，这是明确的反模式。**修法**：非 fake-driver 且 runner 未装配 → `PreflightError("真机组件未装配（Task 2.7）")` exit 3，一行守卫。2.7 真机接线时这个坑直接挡路。

### R16-3（P2）`--allow-metadata-mismatch` / `--no-llm` 零消费

argparse 接受，全库无任何消费点。`--no-llm` 尤其误导：**新管线根本没有 Recovery 接线**（StepRunner 失败直接 FAIL，无 RecoveryEngine 调用）——`mta run` 里 RECOVERED 不可达、exit 5 不可达，`--no-llm` 与默认行为无差别。而 2.7 Gate 要求 "`--no-llm` 连续 3 轮全绿（PASS=100%，LLM 调用 0）"。建议：要么本 task 就消费（--no-llm 断言 LLM 调用数为 0 且 report 如实渲染；metadata-mismatch 接 lint 预检），要么 argparse 层标注 experimental/暂不接受，别留"参数存在=功能存在"的假象。

### R16-4（P2）precondition/cleanup/postcondition 在生产管线零消费——2.7 硬前置

`pipeline.py` 对 `tc.precondition`、`cleanup` **零处理**（grep 实证）；`run_all` import 了 SuiteRunner 却未使用、内联重写了 abort 循环；`PipelineDeps` 没有 EnvironmentManager。影响链：

- 2.7 真机 Gate 时 5 条 smoke 的 `precondition: RELAUNCH` 不会执行 → 登录态残留 → 连锁假失败（旧 TestcaseRunner 是有 `reset_state` 的，新管线反而是回归）；
- cleanup/postcondition 继续是死配置（R10-2 老账），H7 的 postcondition 分支（`RECOVERED(kind=postcondition)`）在 StepRunner 只有 decision 没有 check 执行；
- R13-2 的"收口"（suite.py 模块级闭环）在生产路径被绕开——不是退步，但 2.6 记账的"R15-2 核销"只完成了 TraceStore 落库这一半，**套件语义/环境钩子这半必须进 2.7 验收清单**。
