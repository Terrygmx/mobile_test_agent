## 三、发现

### P3-1 `priority_score` 的入参闸门只做了一半：`risk` 完全没闸门，`history` 的闸门被 `Risk`（IntEnum）绕过

**现象**（探针实测）：

```text
priority_score(m, set(), 0.0, "CRITICAL")   -> 0     ← 不报错，floor 静默不生效
priority_score(m, set(), 0.0, "critical")   -> 0
priority_score(m, set(), 0.0, None)         -> 0
priority_score(m, set(), Risk.LOW, Risk.LOW)-> 30    ← Risk 是 int 枚举，被当成失败率 1.0
priority_score(m, set(), 0.0, 4)            -> 90    ← IntEnum 与 int 同哈希，裸 4 反而能用
```

`history` 的闸门挡住了 `bool`/`str`/`None`/`list`（有专测、6 条参数化），唯独挡不住 `Risk`——
`class Risk(int, enum.Enum)` 使 `isinstance(Risk.LOW, (int, float))` 为真。
而 `risk` **没有任何闸门**：`RISK_FLOOR.get("CRITICAL")` 返回 `None` → 走 `if floor is not None` 的
另一支 → 静默不加 floor。

**为什么现在修**：今天 `case_risk` 只可能产出 `Risk`，两个洞都走不通。但 **Task 2.3 的编排层是第一个会把
「外部来的值」喂进打分的地方**（LLM 输出 / policy.yaml / CLI 参数 —— 全仓的 `strict=True` 教训说明
「外部值错型」在这个项目里是真实发生过的），而失败的形态是**分数偏低 → CRITICAL 用例在 Plan 里沉底**，
错误方向恰好是「看不见」那一侧——**正是本 commit 自己在两处写下的同一条理由**：

- `case_risk` docstring：「一个 CRITICAL 元素因漂移而解析失败时，静默按 LOW 计会让它在 Plan 里沉底——
  错误的方向恰好是『看不见』那一侧」；
- `screen_id`：「静默接受一个过滤不了的键，等于把『想过滤没过滤』伪装成『结果恰好都对』——
  同一个道理不能对自己网开一面」。

「传了一个用不了的 `risk` 却静默按无 floor 计」，与上面两句是**同一个道理**。

**修法**（各一行，不阻塞 M2 其余任务）：

```python
if not isinstance(risk, Risk):
    raise ValueError(f"risk 必须是 Risk，got {risk!r}")
# history 的判定里补一条（Risk 是 int 枚举，不能被当成失败率）
if isinstance(history, Risk) or not isinstance(history, (int, float)) or isinstance(history, bool):
    raise ValueError(...)
```

### P3-2 `case_risk` 的 `getattr(tc_meta, "element_ids", ())` 让「传错对象」与「属性名拼错」**静默降级为 LOW**

**现象**（探针实测）：

```text
case_risk(<没有 element_ids 属性的对象>, repo, build="local")  -> Risk.LOW   （不报错）
case_risk(<属性名写成 element_id 的对象>, repo, build="local") -> Risk.LOW   （不报错）
```

两例都**没有**调用 `repository.resolve`（探针的替身 repo 一被调用就抛 `AssertionError`，实测未被调用）。

**与 P3-1 同形**：本函数 docstring 明写「解析不到的元素**照原样上抛**，不跳过、不当 LOW」，
但对**自己的入参**恰恰留了一个静默兜底——`getattr` 的默认值把「用例根本没有/拼错了元素字段」
和「用例确实不涉及任何元素」压成了同一个返回值，而后者的 `LOW` 是**有意为之**（docstring 已说明）。
两种语义混在一个 `Risk.LOW` 里，正是上面那句「不能对自己网开一面」。

**修法**（一行）：`for element_id in tc_meta.element_ids:`（`TestCaseMeta` 必有该字段）；
若确实要容纳测试替身，改成显式 `isinstance(tc_meta, TestCaseMeta)` 校验，而不是靠 `getattr` 默认值。

### 小观察（不建议单独立项）

1. **`round()` 用银行家舍入**：`30×rate` 落在 `.5` 上时方向不一致——`rate=0.05→2`（1.5 进）、
   `0.15→4`（4.5 舍）、`0.25→8`（7.5 进）、`0.35→10`（10.5 舍）。确定性不受影响，
   只是「失败率的 k 倍 ≠ 得分的 k 倍」。要「半分一律进位」用 `math.floor(score + 0.5)`。
2. **提交信息里的数字口径**：自述「P2 回归（`-k "graph or knowledge or impact"`）**126 passed**」，
   但在 **HEAD 上照抄这条命令得到 144**（= 126 既有 + 15 `test_knowledge_retrieval` + 3 `test_prioritizer`）。
   126 是**父提交上的数**，不是 HEAD 上的数——建议写明「126 既有 + 18 新增」。
3. **`build_knowledge(cases: Any = ())`**：`app_build` 有精确标注、`cases` 却是 `Any`——
   传错形态只能等到 `impact_of` 时才炸，而那时已经装配完了。
4. **`RISK_FLOOR` 是模块级可变 `dict` 且被 `planner/__init__` re-export**：任何调用方
   `planner.RISK_FLOOR[Risk.HIGH] = 0` 都会全局生效。plan 说权重「待真实数据校准」，
   校准入口最好只有常量定义处（`types.MappingProxyType` 即可，`RISK_FLOOR.items()` 不受影响）。
5. **`priority_score` 每次调用都 `frozenset(impact)`**：Task 2.3 的编排层会按用例循环调用 →
   O(N×|impact|)，而调用方无从避免（入参是 `Iterable[str]`）。可在签名处收 `frozenset` 或在
   docstring 写明「调用方预先去重」。
