## 3. 问题清单

### R7-1（P1）CLI 文件级错误：裸 traceback + 退出码 1，违背 8.4 语义

实测（真实退出码）：

| 场景 | 行为 | 应然（8.4） |
|---|---|---|
| `mta lint no_such.yaml` | FileNotFoundError traceback，**exit 1** | 前置配置错误 → **exit 3** |
| YAML 语法错误 | yaml.YAMLError traceback，**exit 1** | 同上 → **exit 3** |

`cmd_lint` 对 `Path(path).read_text()` / `yaml.safe_load` 无任何异常处理。设计 8.4 的退出码表是 CI 判读契约（G10）：exit 1 = 「存在 FAIL」，加载失败被归入 FAIL 语义，CI 会把「配置错了」当「用例挂了」报警。修法很小：读文件 + safe_load 包 try/except（FileNotFoundError/YAMLError）→ 打印一行错误 → return 3，并补 2 条 CLI 测试。建议进 Task 1.4 前收掉——Task 1.6 的 Gate 脚本就要消费这个退出码。

### R7-2（P2）`idempotency: UNKNOWN` 的步骤跳过 postcondition 警告

`_check_postcondition` 只对 `declared == "NON_IDEMPOTENT"` 告警；显式声明 `UNKNOWN` 且缺 postcondition 的步骤无任何提示。而设计 7.4 明确「**`UNKNOWN` 一律按 `NON_IDEMPOTENT` 处理**」——运行时 Executor 会把它当非幂等对待，lint 却静默放行。声明 UNKNOWN 本身就该配 postcondition（否则执行器无法判定动作结果）。一行修：`declared in ("NON_IDEMPOTENT", "UNKNOWN")`，补一条测试。

### R7-3（P2）`cmd_lint` 退出码逻辑重复实现 + stringly-typed 比较

`cli/main.py:78-79` 内联重算了 `lint_exit_code` 已有的逻辑（且该函数 import 了却没用），严重级比较用 `i.severity.value == "error"` 字符串而非 `is Severity.ERROR`（打印前缀同理）。两处逻辑未来一旦分叉（比如 8.4 退出码表扩展），很容易只改一边。建议 `cmd_lint` 直接消费 `max_severity(issues)` 或把 `lint_exit_code` 改成接受 `issues` 参数复用。

### R7-4（P3）`cli/main.py` 未使用的 import

`from testcase.loader import load_testcase`（实际用 `yaml.safe_load` 直读）——删掉即可。

### R7-5（P3·观察项，不需要改代码）

- `_check_sleep` / `_check_active_scope` 在两条正常输入路径下实际**不可达**（dict 路径 schema 先拦后 `continue`；TestCase 路径 Literal/校验器根本放不进 sleep/element+active）。docstring 已如实标注「双保险」且测试通过直调私有函数覆盖——防御姿态成立，保留即可，但后续维护者要理解这不是死代码删除候选。
- `testcase/login_demo.yaml`（P0 旧用例）跑 `mta lint` 会 exit 3（缺 schema_version）——0.1 门禁的正常行为，Task 1.6 会另建 `suites/smoke/*.yaml`。建议在 P0 yaml 头部或 README 加一句「P0 遗留，不走 P1 lint 门禁」，避免被当 bug 报。
- `LintIssue/Severity` 定义的归属：放在 `repository.resolver`，导致 testcase.lint → repository 的 import，而 resolver 又 import testcase.schema——包级双向依赖（无环）。0.2 冻结时建议挪到中立模块（如 `testcase/issues.py`）。
