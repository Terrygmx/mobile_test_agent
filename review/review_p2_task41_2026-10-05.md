## 3. 发现

### P2-1 git commit 失败 → 部分写状态不可恢复，且错误误归因（探针实锤）
- 复现：git 身份缺失（`GIT_CONFIG_GLOBAL=/dev/null`）→ `approve_proposal` 抛 RuntimeError，但此时 **overrides 文件已写入**（exists=True）、proposal 恒 PENDING、promoted 未记账。
- **重试被自己的部分写挡死**：再 approve → `overrides 已存在同 id 元素定义…人工写过的 override 只能人工处置，工具不代改`——把**工具自己写了一半的文件**误报成「人工 override」，操作者按报错指引（人工处置）会陷入两难：删文件违反「不代改」的字面，留着则 proposal 永远无法 approve。
- 修复建议（任选或组合）：①写文件**前**做 git 预检（`git commit --dry-run` 或 user.email 存在性）；②git 失败时回滚文件写（恢复原内容/删除新建文件）——`approve_proposal` 里 write 与 commit 之间没有事务性，最小修复是 except 分支还原；③同 id 检查对「与 proposal.diff 逐字节相同的既有文档」幂等放行（重试即续传）；④至少把报错改准：「git 提交失败且 overrides 已写入——手动恢复：`git checkout -- <file>`（或删除）后重试」。

### P2-2 promoter 的 replace 语义丢弃 source 链——与设计 §9.2 明文相反，commit 声称不实
- 探针：generated（source: username_field）+ promoter 写入的 overrides（experience: u_v2）→ `resolve` 链 = `[('experience','u_v2')]`，**source 策略被元素级 replace 丢弃**。
- 设计 §9.2 明文：「manual/source 的策略在运行时失败，Locator Chain 会**继续尝试** promoted experience 策略——它是链里排序**最后**的一条，而不是被直接丢弃」。`test_experience_strategy_survives_replace_mode` 的 docstring 承认了 replace（「replace 语义」）并只断言 experience 自身存活——测试诚实，但设计无修订记录，而 **commit message 声称「排链尾不丢弃」**（那只在手写三源单文档时成立，promoter 的真实产出永远不是这个形态）。
- 影响评估：漂移场景（改名）replace 合理——旧 source locator 在运行时已死，保留只浪费一次 find；但「元素未变、experience 是补充回落」的场景（flaky 元素的备选定位）会丢掉仍在工作的 source 主策略，且 9.4「promoted 后是 P1 find 的一条普通 Locator」的叙述在 replace 下变成「唯一 Locator」。
- 修复三选一并回填设计修订记录：(a) 登记 replace 语义 + 理由（漂移场景 source 已死；备选回落场景由 resolver 的 warning 提示人工并链）；(b) promoter 写入时**合并** generated 链（source 策略一并写进 override doc，experience 排尾——真正满足 9.2 原文）；(c) override doc 用 `mode: append` 让 merge 层保链（需确认 loader mode 对 strategies 的语义）。倾向 (b)：把 9.2 的承诺留在写入口，而不是靠使用方手拼文档。

### P3-1 H15 与设计 §9.1 的 supersede 关系未注记
- P1 硬约束 H15「工具不自动写 repository/overrides」——设计 9.1 的 promote 写入是**人工 APPROVE 后**的明文写入，精神上不冲突（这正是 H15 防的「静默固化」的人工闸门版本），但约束清单没注记。后人拿 H15 字面质疑 promoter（或反过来拿 promoter 当 H15 例外的口子）都会困惑。建议设计硬约束表加一行：「H15 注记：P2-09 promote 在人工 APPROVE 后写 overrides（9.1），非自动写入」。

### P3-2 同 id 检查的正则不容忍行尾注释
- `^id:\s*{target}\s*$` 对 `id: login_button  # 备注` 不命中 → 漏检 → 追加后同 id 双文档（loader 后者胜，静默）。放宽为 `^id:\s*{re.escape(target)}\b` 更稳。

### P3-3 E10 的「PR 流程」口径
- 实现直接 commit 到当前分支。E10 原文「工具辅助生成 commit，但 commit 本身走正常 PR 流程」——PR 化是团队过程约定，工具无法强制；建议 docstring/记账注明「commit 落当前分支，PR 化由流程负责」，避免宣称越界（H18 同族）。

### P3-4 杂项
- `_render_diff` 产物实为完整 YAML 文档而非 diff（9.3 说「供人工 review 的 YAML 补丁文本」——语义可接受，命名可注记）。
- `approve_proposal` 的 `committer` 默认 "promoter"——CLI 侧若不传真名，审计留痕会统一成机器名（与 3.4 revalidate 的 getpass.getuser() 口径不一致，建议对齐）。

## 4. 值得肯定

- **两条审计红线都做进了函数形状**：没有「跳过 proposal 直写 overrides」的入口（approve 必须持 PENDING proposal_id）；REJECTED 连 9.5 人工路径都不开——红线不靠调用方自觉。
- **record_promotion 的 from==to 事件**：9.4「不改状态但可审计」用状态机自己的语言表达（REVALIDATION_REQUIRED 同款），而非发明新的记账形态——Experience 的状态时间线因此始终完整可复算。
- **接线前置两条都有回执且落在正确位置**：ORIGINS 与写入同批（plan 预警的「一上线就 fail-loud」没有发生）；type 省略定档写进 docstring 并说清了 Guard 类型校验不受影响的理由。
- **测试用真 git 仓库**（17 例含真 commit、真 sha、二次 approve 冲突）——subprocess 边界不 mock，git 语义被真实验证（也正因如此，我的失败路径探针才能立刻暴露 P2-1 的部分写问题）。
