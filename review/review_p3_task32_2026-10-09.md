### P2-1 `wait_for screen:X condition=not_exists` 被当成「到达过 X」——真 gap 静默塌成 0

**位置**：`generator/coverage.py:150-156`

```python
wait = getattr(step, "wait_for", None)
if wait is not None:
    tgt = getattr(wait, "target", None)
    if getattr(tgt, "type", None) == "screen":     # ←:153 只看 type，不看 condition
        out.append((tgt.id, pending or ""))
```

**问题**：`WaitSpec.condition` 有 8 个取值（`exists / not_exists / visible / enabled / disabled / text_equals / text_contains / active`，实测 `WaitSpec.model_fields["condition"].annotation.__args__`），其中 **`not_exists` 是对「屏**不存在**」的断言**（`executor/wait.py:135-137`：「`not_exists` 的『满足』形态就是找不到」）。把它登记成「到达过 X」，会**凭空造出一条覆盖**，让一条真 gap 被吞掉——正是 MEMORY §5.A 定义的「错误落在看不见那一侧」。模块 docstring `:130-134` 论证的是「用例文本里无法判**成败**，按声明算」，那是针对 wait 的**成功与否**；`not_exists` 是**极性**，不是成败，这句论证盖不住它。对照面：`graph/builder.py::is_screen_wait` 在 runtime 侧对 `wait_for` 有完整的 status 过滤，`_arrivals` 这边一个都没有。

**复现命令**：

```bash
env PYTHONPATH=. .venv/bin/python - <<'EOF'
from generator.coverage import coverage_gap, _arrivals
from graph.models import RuntimeGraph, ScreenTransition, RUNTIME
from testcase.schema import parse_testcase_dict
g = RuntimeGraph(app_id="a", app_build="b", source_of=RUNTIME, transitions=(
    ScreenTransition("BView","CView","tap:BView.go", source_of=RUNTIME, count=3),))
tc = parse_testcase_dict({"schema_version":"0.2","id":"n","name":"n","steps":[
    {"action":"tap","target":"AView.to_b"},
    {"wait_for":{"target":"screen:BView","condition":"active","timeout":5}},
    {"action":"tap","target":"BView.go"},
    {"wait_for":{"target":"screen:CView","condition":"not_exists","timeout":5}}]})
print("arrivals:", _arrivals(tc))                       # ('CView', 'tap:BView.go') ← 断言 CView 不存在
print("gap =", len(coverage_gap(g, [tc])))              # 0 ← 期望 1，被吞掉了
EOF
```

**实测输出**：`arrivals: [('BView', 'tap:AView.to_b'), ('CView', 'tap:BView.go')]` / **`gap = 0`（期望 1）**。

**这不是纯理论**：`suites/account/login_negative_002.yaml`（全量 20 个用例之一）的 step 4 就是
`wait_for: {target: screen:HomeView, condition: not_exists}`，文件自己的注释写着「**不进 Home**（not_exists screen 的否定判定走 wait not_exists）」。今天真语料 gap 恰好仍为 0，**是巧合**——我把 `_arrivals` 改成排除 `not_exists` 后跑真语料，`covered` 集合与 `gap` 数**逐条不变**（`patched − baseline = []`，`baseline − patched = []`），因为该屏恰好与它前一个到达点相同而被自环折叠吃掉了。**换一条用例就暴露**。

**建议修法**（一行）：

```python
            if (getattr(tgt, "type", None) == "screen"
                    and wait.condition != "not_exists"):
```

并在 `tests/unit/test_coverage_gap.py` 补一条：图上有 `BView→CView`、用例用 `not_exists screen:CView` 断言**没去** → `assert gap`（探针 N 已证明去掉到达点识别会红 5 条，但那是**另一侧**的判据，钉不住本条）。

### P3-5 `getattr(graph, "transitions", ())` 把「入参形态坏了」伪装成「零 gap」——MEMORY §5.A 的第 5 次同形

**位置**：`generator/coverage.py:204`（另见 `:171` 的 `existing_tests or ()`、`:139` 的 `getattr(tc, "steps", []) or []`）

### P3-8 runtime 侧 trigger 的取值域比 coverage 侧宽（结构分歧，非经验巧合）

**位置**：`generator/coverage.py:112-114` 的 docstring + `:156` 的 `continue    # wait 不是触发`

**问题**：runtime 侧 `build_runtime_graph` 用 `_trigger_of(prev)`，`prev` 是**上一步、不限类型**（`graph/builder.py:178-183`），所以只要 trace 里出现「`wait_for screen:X` 之后紧接一个观测到另一屏的步骤」，图上就会有一条 `trigger="wait_for:screen:X"` 的转移；而 coverage 侧的 `_arrivals` **结构性地**排除 wait 作为触发。docstring :112-114 写「与 runtime 侧同款：真 trace 里 8 条转移的 trigger 全是动作步骤（实测 `tap` 7 / `back` 1，无 wait/assert）」——**这是对当前那 8 条的实测，不是构造性保证**。

**复现**：

```bash

from generator.coverage import coverage_gap, covered_transitions

tc = parse_testcase_dict({'schema_version':'0.2','id':'x','name':'x','steps':[
  {'wait_for':{'target':'screen:HomeView','condition':'active','timeout':5}},
  {'wait_for':{'target':'screen:DetailView','condition':'active','timeout':5}}]})
print('covered:', covered_transitions([tc]), '→ gap =', len(coverage_gap(g,[tc])))"
```

**实测**：图上 `HomeView -> DetailView @ 'wait_for:screen:HomeView'`，覆盖集 `{('HomeView','DetailView','')}` → **gap = 1**。用例**确实到过** Home→Detail，图上**确实有**这条，只是 trigger 形状不同域 → **假 gap（误报）**。

**当前无影响**（实测）：真 trace 里「观测屏的前一步是成功的 `wait_for`」出现 **0 次**；trigger 动作分布 `{tap:7, back:1}`；真语料 20 个用例里也没有「连续两个不同屏 wait、中间无动作」的形态（有两次重复屏 wait：`login_again_001` = `[HomeView, ProfileView, LoginView, HomeView]`、`detail_back_001` = `[HomeView, DetailView, HomeView]`，都被自环折叠吃掉）。

**判定**：**P3（潜性），注明「Task 3.4 生成器写出这类用例时升级为 P2」**。方向与 P2-1 相反（P2-1 是假覆盖→漏报，本条是假 gap→误报），两者同源：**两侧 trigger 的取值域没有被同一个原语约束**。

**建议修法**（二选一）：① 让 runtime 侧与 coverage 侧走**同一个**「转移形状」原语（把「哪些步骤能当触发」也抽成 `_trigger_of` 的邻居，如 `graph/builder.py::trigger_source(prev)`），从根上收口；② 至少把 docstring :112-114 的「实测」限定词改成**带条件的将来时**（「当前语料的 8 条转移 trigger 全是动作步骤；一旦 trace 里出现连续屏 wait，本函数会报出 trigger 不同域的假 gap——已知形态，Task 3.4 接线前要么收口要么标注」），别让它读起来像构造性保证。
