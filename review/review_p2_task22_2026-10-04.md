## 3. 发现

### P3-1 `effective_risk is not Risk.LOW` 的恒等比较是 Task 2.4 的类型地雷
- 探针实锤：传**字符串** `"LOW"`（而非 `Risk.LOW` 枚举）→ `RISK_BLOCKED`。方向是 fail-closed（安全侧），但 Task 2.4 接线时 `RuntimeContext.effective_risk` 的来源字段若 carries 字符串（P1 `RecoveryContext.effective_risk` 系字符串域），全部 Experience 候选会被**静默**拦成 RISK_BLOCKED——不炸、不报错、只掉成功率。建议：①guard 入口 `isinstance` 断言（Risk | None 之外 raise）；或 ②Task 2.4 的接线测试必须含一条「真实 Risk 枚举流经全链」的正向 EXECUTE 用例。同时保留旧语义说明（原 `candidate_risk_allowed` 同款 `is` 比较，行为无回归）。

### P3-2 链序变更（screen 先于 find）与 P1 设计 §9.3 修订记录脱节
- P1 设计 9.3 修订记录写的是「confidence → **数量 → 类型 → Screen** → risk+Guard」；本次按 P2 设计 5 节改为「confidence → **Screen** → 数量 → 类型 → risk」且 docstring 已记录合并依据（未登记 fail-closed 不消耗 find）。单故障注入下两者不可区分（矩阵 24/24 全绿佐证），多故障时 failure_type 会变（如「未登记且会 NOT_FOUND」从 NOT_FOUND 变 SCREEN_MISMATCH）——这是有意定档，但 **P1 设计侧的 9.3 修订记录没有回填**，两份设计文档现在描述两个链序。建议 P1 设计 9.3 补一行「链序以 P2 设计 5 节共享实现为准（Task 2.2 起）」。

### P3-3 生产 Executor 没有 `find_all`——Task 2.4 的接线缺口
- `experience_runtime_guard` 硬编码 `executor.find_all(exp.strategy)`；生产 Executor 只有 `find`（0 匹配抛 ElementNotFound、≥2 抛 AmbiguousElement——与 find_all 的「返回列表」语义不同构）。测试用的 FakeFindExecutor 自带 find_all 所以现在全绿。Task 2.4 必须二选一：给 Executor 加 `find_all`（真实 WDA 树上返回全部匹配），或提供适配器把异常语义翻成计数。建议现在就在 plan Task 2.4 记一笔（与上篇 P3-3 的键语义问题并列）。

### P3-4 `policy_check=(self.guard is not None and eff is not None and _policy_check or None)` 的 AND-OR 惯用法
- 当前正确（函数对象恒真值），但可读性差且脆弱：将来若 `_policy_check` 改成可能为假值的形态会静默变 None（跳过 10.1 Guard）。建议显式 `policy_check = _policy_check if (self.guard is not None and eff is not None) else None`。

### P3-5 杂项
- LLM 路径的 `repo.resolve`（取 candidate_screen/risk）现在发生在 confidence 检查之前——纯内存操作不违「confidence 先于任何**设备**操作」定档，但严格讲低置信候选多付一次 resolve；可忽略，记录备查。
- `phase0/verify_p1_m4.py:257` 注释仍引用已退役的 `candidate_risk_allowed`（指向语义未变，顺手更新为指向 runtime_guard）。

## 4. 值得肯定

- **E1 红线第一天就咬到了真缺陷**：commit 明写「红线测试当场抓到重构缺陷：validate 段曾双 append」——红线的价值（防两套规则漂移）在落地当天兑现，且修复+钉住+如实记账，这正是这条设计红线存在的意义。
- **未登记场景的诚实单侧断言**：`_experience_guard_outcome` 对空 repo 返回 None，测试只断言引擎侧映射——不为了「对称」伪造一个不存在的 Experience 对照物。测试的诚实度就是它未来可信度的上限。
- **P1 词汇表与 P2 词汇表的隔离**：Guard 的 reason 枚举不携带 `LLM_` 前缀，P1 的 failure_type 经 `GUARD_REASON_TO_LLM_FAILURE` 单向映射——两套语义各自演进时不会互相渗透，映射表单一真值源。
