## 三、发现

### P3-1 `test_copy_contributes_only_the_new_path` 的断言**恒真**，而 `C` 在 shipped flags 下**不可达**

**现象.** `tests/unit/test_git_diff.py:227`：

```python
assert cs.added == ("copy.txt",) or cs.renamed == ()
```

`_RENAMED = frozenset({"R"})`，而 `C` 不在其中；更要紧的是——下面的探针证明 shipped 的
`git diff --name-status -z -M` **永远不会输出 `C`**。于是 `cs.renamed` 恒为 `()`，右分支恒真，
**整条断言不可能失败**。

**探针（反证 + C 可达性）.**

```
① 复刻该测试的场景（diff.renames=true，无 -C）
   raw 输出        : A|copy.txt|
   cs.added=('copy.txt',)   cs.renamed=()
   左分支 added==('copy.txt',) : True     右分支 renamed==() : True     断言 True
   → 把 _ADDED 换成 frozenset({'C'})（A 不再是新增）：
     左分支 False，右分支 True，断言 **仍为 True**   ← 这一行不可能失败

② C 可达性（同样的 copy 场景，换 flag）
   extra=()                        → A|copy.txt|
   extra=('-C',)                   → A|copy.txt|      ← 单档 -C 只看「被修改的文件」作复制源
   extra=('-C','-C')               → C100|edit.txt|copy.txt|
   extra=('--find-copies-harder',) → C100|edit.txt|copy.txt|
   用户配置 diff.renames=copies    → A|copy.txt|      ← 用户配置也逼不出 C
```

**连带问题.** `_ADDED` 里的 `"C"`（`git_diff.py:49`）与 `_parse_name_status_z:158` 的
`status == "C"` 分支因此是**防御性死代码**（写得对，但没人跑过）；而模块 docstring 决定 3
「复制（`C`）只收新路径」、提交信息「复制（C）只收新路径（源文件内容没变）。**专测**」、
审计文档「有专测」——**声称超出验证范围**。这是 MEMORY §5「文档声称的能力必须有落点」的
第 4 次（`--agent-db` / `args.policy` / 「都经 `agents/tools.py`」之后）。

**为什么现在要修.** M2 的 `planner/impact.py` 要消费 `changed_files`；「提高影响面召回」最自然的
下一步就是给 `run_git` 补 `-C` / `--find-copies-harder`——**那一刻 C 分支从死代码变成活跃代码，而它
唯一的守卫是一条恒真的断言**。（测试里第二行 `assert "edit.txt" not in cs.changed_files` 是有效的，
所以这条是「半空转」，不是全空转。）

**修法（二选一，各 ~6 行）.**

- **加真测（推荐）**：`_parse_name_status_z` 是**纯函数**，不必依赖 git 产出 `C`——直接喂
  `"C100\0edit.txt\0copy.txt\0"`，断言 `FileChange(status="C", path="copy.txt", old_path="edit.txt")`
  且 `GitChangeSet(...).changed_files == ("copy.txt",)`（旧路径不进）；同时删掉 `or cs.renamed == ()`。
- **别声称**：把 docstring / 测试名 / 提交与审计文档里的「复制（C）」改成「新增（A）」，删掉
  `_ADDED` 的 `"C"` 与解析器的 C 分支——将来真要 `-C` 时一并加回并加测。**别留一条自己都不信的声称。**

### P3-2 `test_rename_detection_is_independent_of_user_config` 自称钉的是 `~/.gitconfig`，实际只钉了**仓库本地** config

**现象.** `source/vcs.py:43` 的 `run_git` 用 `subprocess.run(...)` **不传 `env=`**（探针读源码确认：
`"env=" in inspect.getsource(run_git)` → `False`）→ 被测代码继承 `os.environ`，看到的是
**真实的 HOME / 真实的 global gitconfig**。而测试 fixture 的 `HOME=tmp_path`（`_BASE_ENV`）只
作用于测试**自己的** `_git` helper（它显式传了 `env=`），**管不到被测代码**。测试里那句
`git config diff.renames false`（:189）写进的是**仓库本地** `.git/config`。

**探针（真造一份 global 配置）.**

```
临时 HOME/ 下写 ~/.gitconfig: [diff] renames = false（仓库本地不设）
   无 -M 的 raw : D|keep.txt|A|moved.txt|
   带 -M 的 raw : R100|keep.txt|moved.txt|
   把 os.environ['HOME'] 指到该目录跑 changed_files → renamed=(('keep.txt','moved.txt'),)
```

→ **结论本身完全正确（`-M` 确实压住 global 配置）**，但**它不是这条测试证出来的**：这条测试走的是
另一条配置通路。它的 docstring 写「**有人在 `~/.gitconfig` 里关掉**…故显式传 `-M`」——名实不符。

**为什么现在要修.** 这是全模块**唯一**在钉「用户配置不该改变结论」的地方，而它钉的是另一个机制。
后果有二：① 后来者以为 global 路径已被覆盖；② 一旦有人为了隔离给 `run_git` 加上 `env=`（很常见的
改动），这条测试会**静默失去意义**——仓库本地 config 还在、`-M` 也还在，它既红不了也绿不了那个点。

**修法（2 行，实测可行）.**

```python
monkeypatch.setenv("GIT_CONFIG_GLOBAL", str(tmp_path / "gitconfig"))   # 内容 [diff]\n\ trenames = false
```

git **2.54 实测生效**：`env GIT_CONFIG_GLOBAL=… git diff --name-status HEAD~1..HEAD` → `D a.txt / A b.txt`，
加 `-M` → `R100 a.txt b.txt`。生产子进程继承 `os.environ` 就能看到它，global 路径才算真被走过；
docstring 里的「`~/.gitconfig`」也随之名副其实。（顺带：这恰好把「`run_git` 不传 `env=`」从缺点
变成了可用的注入点。）

  1 failed。这是「**固化必须是一条会自动失败的测试**」的正面样本（MEMORY §5 记过「我手工跑过一次」
  不算固化的反面教材）。
- **git 的三条实测行为写进了 docstring / 测试 docstring**：`git -C dir` 会**向上找 `.git`**（第一版测试
  `DID NOT RAISE` 被作者自己写出来并附修法 `GIT_CEILING_DIRECTORIES`）/`-z` 而不是按行 + `\t` 切/
  `diff.renames` 是**用户配置**。「踩过一次就写下来」是本项目最值钱的习惯——这三条会让 M2 少踩三次。
- **`GitError` 刻意继承 `RuntimeError`**：让「抽一个函数」这件重构**不改变任何既有 `except` 的语义**，
  并且有落点（`test_git_error_is_a_runtime_error`）。P2 回归保证是**被钉住**的，不是被声称的。
- **翻译而不是吞**：`GitError(RuntimeError)` → `GitDiffError(ValueError)`，消息带 git 自己的 stderr
  （`unknown revision` / `Not a git repository` 都在那，**不自己编诊断**）；且**不静默返回空 changeset**，
  理由写在 docstring 里（「影响 0 个用例」与「ref 拼错了」在结果上长得一模一样）。
- **范围诚实**：`source/vcs.py` 与审计文档都写明「只收敛 promoter 那一条，另两处 P1 存量不顺手改、
  是否收敛由后续任务显式决策」——沿用 `review_p3_task11_final` 肯定过的边界做法（见 P3-3，只有首句
  措辞需要对齐）。
- **`FileChange.status` 只留单字母**（`R100` 的相似度分数丢弃，「没有消费者，不留投机字段」）——
  与本项目「不留投机字段」的取向一致。
- **P2-1 的修法形状值得复制**：「静态逐字对账 + 行为面」**两条钉子各挡一种失效**（名单被改 / if 被挪走），
  并在门禁文件的表头写清**为什么必须有**。
