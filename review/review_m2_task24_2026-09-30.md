## 2. 问题清单

### R14-1（P1）`_duration_ms` 时区错位：UTC 字符串被本地 mktime 解析，duration 多 8 小时

`_now()` 用 `gmtime` 写 **UTC** 字符串，`_duration_ms` 却用 `time.mktime(time.strptime(...))` 按**本地时区**解析。本机 UTC+8 实测探针：

```
actual sleep: ~1200ms | recorded duration_ms: 28801728   # 8h + 1.7s
```

Report 的用例耗时、run 总时长全部失真（每条 +28,800,000ms）；后续若用 duration 做慢用例分析直接废。**修法一行**：`calendar.timegm(time.strptime(...))` 替代 `time.mktime`（或统一 datetime UTC）。`test_duration_ms_computed` 只断言 `d >= 0`——抓不到 8 小时偏差，建议补一条用固定 start/end 时间对的精确断言（`end-start` ≈ 已知毫秒数，容差 2s）。

### R14-2（P2）TraceStore 零消费且未记账——平行实现第三次出现

runner / 旧 Recorder / gate 脚本 / verify_p1_m1 全部无 TraceStore 引用；`p1_schema_review.md` 记账停在 §8（R13），**没有 2.4 节**。计划原文是「Modify recorder.py 新表写入接口」，实现改成了平行 `TraceStore`——接口本身比在旧 Recorder 上叠更干净（enum fail-loud、redact 前置、逐列具名），方向可，但接线顺延 2.5 **必须显式记账**（§8 先例），否则就是 R11-4（implicit_wait 死接线）、R13-2（manager 零消费）之后第三个「实现存在、链路不通」。

### R14-3（P2）R12-3/5「落地」表述过强：接口就绪 ≠ 链路打通

commit message 写「R12-3/5 记账落地：断言结构化结果经 detail_json 落库（kind=assertion_target）」，但本 commit **runner 零改动**，实测 runner 里 assertion/detail_json 零命中——旧链路 steps.error 仍是格式化异常字符串，端到端并没有通。实际状态是「TraceStore.record_step 的 detail 参数具备承载能力 + 单测自证」。随 R14-2 的 2.5 接线一并核销，但账面表述应修正为「接口就绪，接线 2.5」，避免下轮复盘误判。

### R14-4（P3）`failure_attribution` 无任何写入入口

不自动归因是对的（8.2），但 `end_testcase`/`record_step` 均无 attribution 参数，列恒 UNTRIAGED——手动 triage（`mta review`，2.6）落地前归因数据流是断的。记账 2.6 即可。

### R14-5（P3）`aggregate_status` 的 ABORTED/SKIPPED-only 分支无专项测试

只剩 ABORTED/SKIPPED 时 `return seen[0]`（依赖输入顺序）没有专项用例，只在混合场景数据里被顺带覆盖。补一条钉住语义即可。
