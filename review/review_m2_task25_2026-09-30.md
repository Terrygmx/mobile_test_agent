## 4. 问题清单

### R15-1（P1）P0 Recorder 兼容回退是坏的，测试替身失真掩盖了它——探针实锤

`StepRunner._record` 用 `except TypeError` 区分新旧 Recorder。对新调用（带 `detail/effective_risk/...`），真实 P0 `Recorder.record_step` 签名是 `(run_id, step_index, action_type, ...)`——**`run_id` 是必填第一个位置参数**。而回退调用只传了 `step_index/action_type/status/error/latency_ms`，**漏了 `run_id`** → 回退自身必然 TypeError → 外层 `except Exception` 兜住 → 只剩一条 RuntimeWarning，**steps 表一行都写不进去**。

探针（真实 `tracer.recorder.Recorder` + StepRunner 跑一步 SUCCESS）：

```
RuntimeWarning: trace write failed (P0 fallback):
  TypeError("Recorder.record_step() missing 1 required positional argument: 'run_id'")
# steps 表 0 行
```

为什么测试没抓到：`test_old_p0_recorder_still_works` 的替身 `_OldP0Recorder` 签名是 `(step_index, action_type, status, error, latency_ms)`——**没有 run_id**，与真实 Recorder 不符（测试替身失真）。这正是 R2-0（verify_stage7 mock 走旧 schema 导致假绿）的同款模式：**替身保真度不足，测的是想象中的接口**。

附带风险：`except TypeError` 同时会吞掉新调用自身未来的真实 kwarg 拼写错误，把它们静默降级成"旧 Recorder 回退"。

**修法建议**（一个小 commit）：
1. 回退调用补 `run_id`（StepRunner 需要知道 run_id——构造参数或 ctx 带上）；
2. `_OldP0Recorder` 替身改成与真实签名一致（含 run_id 必填），让测试真实回放；
3. 区分"签名不匹配"与"其他 TypeError"：检查异常 message 或改用 inspect 签名探测，别把编程错误吞成兼容路径。

### R15-2（P2）"四条全部核销"口径过强——新管线生产链路仍为零消费

实测引用关系：`StepRunner / Lifecycle / SuiteRunner` 只被 `tests/` 引用；`runner/testcase_runner.py`（计划明确列了 Modify）、gate 脚本、`cli/main.py`、demo **零引用**。即：

- TraceStore 的真实写入路径只存在于测试；真实执行链（verify_p1_m1 → TestcaseRunner → P0 Recorder）原样未动；
- `lifecycle.py` docstring 称"这里把 **TestcaseRunner** 的执行结果写进 TraceStore"——TestcaseRunner 并不使用 Lifecycle，表述与事实不符；
- §10 说"这是 R11-4 / R13-2 / R14-2 之后第四个『实现存在、链路不通』，本轮终于闭合"——**模块级完成 + 测试级接线属实，但『链路闭合』要到 2.6 `mta run` 把 SuiteRunner 接成入口才算数**。

不是要求本任务就接生产链路（计划本意就是逐步替换、2.6 CLI 才是入口），而是要求记账口径诚实 + 把验收钉死：**2.6 必须让至少一次真实套件跑完整走新管线（SuiteRunner + Lifecycle + TraceStore），并在 trace.db 里看到新字段（effective_risk/failure_phase/failure_type/detail）——否则这就是第五个"存在但没接通"**。建议把这句话写进 §10，替换"全部接通"。

### P3（不阻塞，建议随手收）

1. **policy.py `keywords` 参数是死的**：`table = ...keywords` 后紧跟 `del table`，自定义关键词表被静默忽略——要么实现透传给 `keyword_heuristic_hit`，要么删掉参数，别留"可配置"的假象；
2. **suite.py:89 `aggregate_status([result.status]) or result.status` 是无操作**：单元素聚合恒等原值，疑似想合并前次 attempt 状态的残迹，删掉或补语义；
3. **suite.py `run_id=f"suite_{len(self.results)}"`**：跨套件必碰撞（与 gate 固定 run_id 同款问题），2.6 接 CLI 时用 uuid/时间戳；
4. **`_classify` 把 AssertionTargetDrift 归 `FAIL/ELEMENT_NOT_FOUND`**：suite 层不做 recovery 可接受，但 8.2 的 failure_type 枚举里本来就没有 ASSERTION_TARGET_DRIFT（spec 缺口），漂移信息在这一层彻底丢失——建议 2.6 前在 8.2 补枚举或 detail 里保留 kind；
5. **SECURITY_BLOCKED 的 retry_decision 是 PRE_DISPATCH/allowed=True**：被安全闸拦的步骤"允许重试"语义不通（guard 判定是确定性的，重试必然再拦），建议 security 分支给 `allowed=False` 或独立 reason；

7. **Guard 的 `@dataclass` + 手写 `__init__` 冗余**、`GuardContext.data_class` 字段无人消费——删一个；
8. **result.py `llm_calls=llm_calls or attempts`**：两个参数互为 fallback 的别名关系容易被误读，建议二选一。

## 5. 亮点

- **单一事实来源意识**：result.py 刻意不复写 8.1 优先级（复用 aggregate_status），docstring 点名"两处各写一份就是 R13-1 那种双源分叉"；
- **`_resolve_defaults` 默认 None 的论证**：给默认值会让关键词启发永远失效——这是设计直觉反直觉的地方，用测试抓到并写进注释；
- **R14-5 顺带挖出顺序依赖真 bug**：修 P3 修出 P2 级发现，且修法（显式兜底链）比"加个测试"更进一步；
- **SuiteRunner 不把未跑用例算进 total**（稀释 pass_rate 的坑提前避了）、中止时保留已跑结果（不伪造"没跑过"）；
- **异常分类 fail-loud**：`_classify` 和 `_classify_find_error` 都拒绝把编程错误伪装成 ELEMENT_NOT_FOUND；
- V1 随机 FAIL 的诚实记账（定位到外部 reader 可见性，未假装修好）。
