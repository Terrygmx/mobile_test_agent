## 三、发现

### P3-1 `reasons` 的「非空」校验能被**一个空串**绕过 —— F13 的落点留了个洞

**现象.** `planner/models.py:124-131`：

```python
@field_validator("reasons")
@classmethod
def _reasons_must_not_be_empty(cls, v: list[str]) -> list[str]:
    if not v:
        raise ValueError("reasons 不能为空——可解释性是 F13 的落地：…")
    return v
```

只判**容器**非空，不判**元素**。`reasons=[""]` 通过校验，而它给出的可解释性**恰好为零**——
`TestPlanTask(testcase_id=…, priority=70, reasons=[""])` 与「裸分数」在人对账时没有区别。

**探针.**

```
reasons=[]          （有专测）  → ✅拒   (reasons)
reasons=[""]        （空串）    → ❌接受  TestPlanTask(… reasons=[''] …)
reasons=["   "]     （纯空白）  → ❌接受  TestPlanTask(… reasons=['   '] …)
reasons=["ok", ""]  （一真一空）→ ❌接受  TestPlanTask(… reasons=['ok',''] …)
```

**为什么现在要修.** 这条校验是 plan Task 2.1 Steps 唯一点名的校验（「可解释性是 F13 的落地，
不是裸分数」），而它**拦不住最容易被生产者写出的那种值**：Task 2.2 的 `priority_score` 与
LLM 解释（Task 2.3）都会在字符串拼接 / 模板渲染里产出空串（`f"{impact}"` 在 impact 为空时
就是 `""`）。等到 `mta plan` 渲染出一个「有 reasons 但读不出任何理由」的 Plan 再来补，那时
`test_plans` 里已经有行、报告里已经有输出——**错的是已落库的数据**。

**修法（~2 行）**：校验改成「容器非空 **且** 每条非空（strip 后）」——
`if not v or not all(r.strip() for r in v)`，并在消息里写明「空串不算理由」；
补 3 条参数化断言（`[""]` / `["   "]` / `["ok",""]`）。

### P3-2 分层守卫只扫 `agents/storage.py`，而声称是「`agents` 侧对 `planner` 的依赖为**零**」

**现象.** `planner/models.py:55-57`：

> 把转换留在本模块，`agents` 侧对 `planner` 的依赖为**零**——这是**结构上的保证**，不是
> 「我们小心一点」。`test_planner_models.py::test_agents_storage_does_not_import_planner` 钉住它。

而 `test_agents_storage_does_not_import_planner`（:187-204）读的是**一个文件**：
`_ROOT / "agents" / "storage.py"`。

**探针（两次 A/B，各插一行 `from planner.models import TestPlan`）.**

```
插进 agents/storage.py → 1 failed（test_agents_storage_does_not_import_planner）  ✅ 守卫真会红
插进 agents/models.py  → 14 passed（全绿）                                        ❌ 声称的范围没被覆盖
```

**为什么现在要修.** 「结构上的保证，不是我们小心一点」这句是本轮最重的一句声称，而它的落点只
覆盖**会成环的那一个文件**。诚然成环只对 `storage.py` 成立（`planner.planner` 只 import 它）——
但**最可能在未来 import `planner` 的恰恰不是它**：M3 的 `agents/tools.py`（工具层要返回 plan
结果、要声明参数类型）与 `agents/models.py`（想把 `TestPlan` 加进资产模型）都是自然落点。
一句「依赖为零」配上只扫一个文件的守卫，属于**声称宽于守卫**（与上一轮 P3 同族）。

**修法（1 行）**：把守卫的扫描面从 `_ROOT / "agents" / "storage.py"` 扩到
`_ROOT / "agents"` 下的 `*.py`（`rglob` + 逐文件 AST），并把失败的断言消息带上**文件名**
（现在是「`agents/storage.py 不该 import planner`」硬编码，扩面后要指名哪个文件）。
或者反过来——**把声称收窄**成「`agents/storage.py` 对 `planner` 的依赖为零（成环只可能经由它）」，
docstring 里那句「agents 侧」改成「store 侧」。两者选一，别让声称宽于守卫。

### P3-3 `test_empty_reasons_is_rejected` 的两条参数化是**同一个输入**

**现象.** `tests/unit/test_planner_models.py:77-84`：

```python
@pytest.mark.parametrize("bad", [[], ()])
def test_empty_reasons_is_rejected(bad):
    with pytest.raises(ValidationError, match="reasons"):
        TestPlanTask(**_task(reasons=list(bad)))
```

`list(())` 与 `list([])` 都是 `[]` —— 两条 test id（`bad0` / `bad1`）喂进去的是**同一个实参**
`reasons=[]`，测试数 +1，覆盖面 +0。

**探针.** `bad=[] → list(bad)=[] (list)`；`bad=() → list(bad)=[] (list)`。

**为什么现在要修.** 它是本任务**唯一**钉 F13 那条校验的测试（P3-1 正在说这条校验有洞），
而它给出的「两种形态都测了」的印象是假的——**在一条保护性测试上虚报覆盖面**，比在普通测试上更贵。
（同理 `test_priority_must_be_within_design_range` 的 `(-1, 101, 300, -5)` 里 `300`/`-5` 与
`101`/`-1` 是同一越界方向的两个样本，属于便宜冗余，不必动。）

**修法（1 行）**：要么去掉 `()`（只留 `[]`），要么**别转换**、让 `[]` 与 `()` 各自直接作为
`reasons` 传入并都断言被拒（那时两条才是两种不同的输入形态）。

### 小观察（不建议单独立项）

1. **lax 模式下的接受面**（与 `agents/models.py::_Strict` **同款**：只有 `extra="forbid"`、
   没有 `strict=True`）：探针实测 `priority="70"` → 70、**`priority=True` → 1**、
   `priority=70.0` → 70（`70.5` 拒）、`schema_version="香蕉"` 接受、`testcase_id=""` /
   `plan_id=""` 接受。`True→1` 正是 MEMORY §4 记过的「配置错误表现为功能退化而不是报错」
   的同一形态（这里表现为「排序掉到最低」）。**但它与仓内另两个 `_Strict` 完全一致**——要收紧是
   **三个包一起动**的单独立项，不是本任务的缺口，登记即可。
2. **`test_saved_tasks_json_is_the_model_shape` 里 `json.loads(json.dumps(x))` 是恒等**：
   `get_plan` 已经 `json.loads(tasks_json)` 过（:211），再 `dumps`/`loads` 一遍不改变任何东西
   （若它返回的是字符串，这个组合也**不会**把它变成列表）。断言强度没被削弱，但那两个调用是噪音
   → 一行可删（`raw = store.get_plan("plan_1")["tasks"]`）。
3. **`schema_version` 的登记还差一句**：审计文档与 `TestPlan` docstring 给了两条修法（迁移 002
   加列 / `tasks_json` 换信封），但都没提**`from_store_dict` 要跟着读**（现在它把 `schema_version`
   完全忽略、永远取默认值）。加列之后不改 `from_store_dict`，旧行仍会被静默当成新版本——
   「谁 bump 版本谁先处理这一条」补上这一点。
4. **`review_p3_task11` 的小观察「重存是否算新计划」已部分闭环**：`test_save_plan_upserts_same_plan_id`
   钉住了「同一 `plan_id` 重存 → 覆盖、不新增行」。但 **`plan_id` 从哪来仍未定**（Task 2.3/2.4）：
   若每次 `mta plan` 随机生成，upsert 永不发生；若由 `app_build + git_commit` 派生，upsert 才有意义
   ——**语义依赖 plan_id 的稳定性**，建议在 Task 2.3 一并拍板（见第五节）。

  `agents` 侧依赖为零；**A/B 验证插一行 import 就真红**。「不是『我们小心一点』」这句有落点。
- **`planner/__init__.py` 的禁令写给后来者**：「**不要**在这里 re-export `planner.planner`」并
  画出成环路径——Task 2.3 最容易踩的就是它，提前写比事后 debug 便宜得多。
- **`schema_version` 是 TestPlan 自己的版本线**，并用一条测试钉住「与 TestCase 的 `0.2` 不同」——
  两个常量撞名的高风险点被显式否定。
- **「校验什么 / 不校验什么」逐条对着设计原文定**（`reasons` 非空、`priority` 值域、`source` 两值、
  `extra=forbid` 是「拒」；`changed_files` 空 / `tasks` 空是「不拒」），且理由都写了「混淆了哪两种
  情况」（把空当错误 → 「这次真没改什么」与「git diff 失败了」混为一谈，后者在 `git_diff.py` 已
  fail-loud，这里不该再兜一层）。这正是本项目要的那种校验理由。
- **`TestPlan` 没有 `created_at` 是刻意的**：它是**行**的元数据（§11 的表有），由 DB 拥有、
  由 store 的 dict 携带，`from_store_dict` 明确忽略（不塞进模型，也不假装模型有）。
- **「名字以 `Test` 开头」的问题被自己发现并写下来**：pytest 会把它当测试类收集 → `__test__ = False`
  沿用仓内既有手法，并用 `-W error::pytest.PytestCollectionWarning` **复跑确认清零**（不是「加了就当好了」）。
- **落库形状有专测**（`test_saved_tasks_json_is_the_model_shape`）：下游（报告 / `mta plan --json`）
  读的是**库里的 JSON**，不是内存里的模型——这条防的是「往返恰好相等但落库形状漂移」。
