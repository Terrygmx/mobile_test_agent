## 三、发现

### P2-1 `drift_targets` 的 docstring 要求「**必须**写进 `reasons`、不能只记在日志里」，调用方写进了**不落库的** `notes`

**现象（实测）**：

| 位置 | 原文 |
|---|---|
| `planner/impact.py:190-192`（`drift_targets` docstring） | 「调用方**必须**把这一点写进 Plan 的 `reasons`（open question #2 的原文要求），**不能只把它记在日志里**」 |
| `planner/planner.py:247-251`（`_resolve_targets`） | `notes.append("metadata 缺文件级归属（…）→ 回退 build 间 drift 面（base_metadata）；⚠️ 精度损失：…")` |
| `agents/storage.py:189`（`save_plan` 的实际签名） | `save_plan(plan_id, *, app_build, git_commit, tasks)` → 只写 `tasks_json` |

`notes` 属于 `PlanResult`（**过程产物**），`save_plan` 只收 `TestPlan`——所以这条「精度损失」**不会随 Plan 落库**。
CLI 那一眼能看见，但 `test_plans` 行里没有。

**为什么是现在**：drift 面产出的影响面**比本次 commit 宽**（它是 build 之间的元素变化，不知道哪些变化来自这次改动）。
落库的 Plan 里每个任务的 `reasons` 都写「impact: 命中改动影响面」，却没有任何一处说明「这个『命中』来自回退面」。
等人回头复核一份**已落库**的 Plan 时，「影响面是精确的」与「影响面是宽的」长得一模一样——正是本任务自己在
`unmatched_changed_files` 上写下的那条理由（「两种成因在结果上长得一样，而后者会让 planner 长期产出空 Plan 却没人发现」）。

**为什么不是「已登记的偏离」就算了**：提交信息把它写在偏离登记 ② 里（「精度损失写进 reasons 落在 notes 里」），
但落点**弱于** `drift_targets` 自己写下的硬要求（MUST + 明确排除「只记日志」这一档）。契约与落点差一格，而
判定标准正是「口径与实测不符」。

**两个候选修法（建议 M2 Gate 前二选一）**：

1. **进 `reasons`**：`_resolve_targets` 除了 `notes`，再把同一句话追加进每个任务的 `basis`
   （`rule_basis` 之后再拼一条）。缺点：plan 级结论在 N 个任务里重复 N 次。
2. **承认不落库，但把契约改成一致的**：`drift_targets` 的 MUST 改成「写进 `PlanResult.notes`（CLI 可见，
   **不落库**），并在 M6 写 `agent_trace` 时带上」，同时把「`notes` 不落库」这条限制**写进 `planner/planner.py`
   的偏离登记**——现在那三条里没有它。

我倾向 (1)：F13 要的是「落库后可复核」，而 drift 回退一旦发生，Plan 的所有分数都建立在那个宽影响面上。

### P3-1 `failure_rate` 的 `getattr` 兜底：传错形态 → 失败率静默塌成 **0.0 或 1.0**

```python
# planner/planner.py:148-149
run_id = getattr(step, "testcase_run_id", None)
failed = getattr(step, "status", None) == _FAILED_STEP
```

**探针实测**：传两个缺 `testcase_run_id` 的 FAILED 步骤 → `failure_rate` 返回 **1.0**（不是报错，也不是 `2/1`
之类的异常值）；反过来缺 `status` → 全部 `failed=False` → **0.0**。两个方向都不报错。

**危险方向**：失败率占 30 分权重。塌成 `0.0` → 有失败史的用例**沉底**；塌成 `1.0` → 无失败史的用例白拿
30 分挤掉别人。两侧都是「看不见」那一侧。

**为什么现在修**：这是**同一个形状在本包里第三次出现**——

1. 上一轮 `planner/risk.py` 的 `getattr(tc_meta, "element_ids", ())` 刚被判 P3-2 并修掉（改直接取属性）；
2. 本任务自己在 `planner/impact.py::_paths` 为「单个字符串」写了同一条纪律（「传错 → 表现为『空 Plan』
   而不是『你传错了』」）；
3. 本函数却没有用这条纪律对待自己的入参。

**修法（一行）**：`run_id = step.testcase_run_id` / `failed = step.status == _FAILED_STEP`
（`TraceStep` 两个字段都在，Task 2.2 才把它们读出来）。要保留宽容就在**调用方**显式处理，而不是在纯函数里
默认兜底。**潜性**：当前唯一生产者是 `knowledge.trace_history`，形态正确，所以今天不会触发。

### P3-2 `plan_id_for` 缺兄弟函数刚加上的单字符串闸门

`planner/impact.py::_paths` 有一句显式拒绝（`isinstance(changes, (str, bytes))` → `TypeError`），理由是
「`for p in "a.swift"` 会安静地逐字符迭代出 7 个『路径』」。同一个包的 `plan_id_for` 没有这条：

```python
parts = [app_build, git_commit, *sorted(str(p) for p in changed_files)]
```

**探针实测**：`plan_id_for("1026", "abc", "a.swift")` **不报错**，返回的 id 与
`plan_id_for("1026", "abc", list("a.swift"))` **完全相同**，且长度与前缀（`plan_` + 16 hex）与正常 id 无从区分。

**危险方向**：`plan_id` 是 `test_plans` 的**主键 + upsert 键**。一个「看起来完全正常」的错误 id 会让两次
plan 落到两个互不相干的行（或覆盖到错误的行），而全程无报错——正是 `_paths` 那条注释写下的同一句话。
**风险面是公开导出**：`planner/__init__.py` 已导出 `plan_id_for`，`plan()` 内部经 `PlannerInput`（pydantic
`list[str]`）是安全的，但 Task 2.4 的 CLI 与 M6 的自主闭环有可能直接调它。

**修法（一行）**：开头加 `if isinstance(changed_files, (str, bytes)): raise TypeError(...)`
（消息可照抄 `_paths`，或干脆复用 `_paths`）。

### 小观察（不建议单独立项）

1. **`rule_basis(hit=…)` 在编排路径上恒真**：`candidates` 的过滤条件（`getattr(c, "id", "?") in impact`）与
   `hit=cid in impact` **同源**，所以 `reasons` 的「不在影响面内」这一支在生产**不可达**，且 `IMPACT_WEIGHT`
   的 +40 在候选集内**区分度为零**（设计 §5.2 的 +40 本是用来区分命中/未命中的）。这是口径 1 的正确推论，不是
   bug——建议在 `rule_basis` 的 docstring 里写明「候选集 == 影响面，故编排路径上 `hit` 恒真」，或把参数去掉。
2. **`trace_history` 在候选循环里按用例调用**（`planner/planner.py:342`）→ 每个候选用例触发一次**全库**
   `read_trace_steps` + Python 过滤，即 O(用例数 × 全库步骤数)。M2 Gate 规模无所谓，M6 自主闭环会疼。
   修法：循环外一次 `trace_history({})`，按 `testcase_id` 分组（`TraceStep` 上就有这个字段）。
3. **`test_plan_result_exposes_tasks` 名实不符**：docstring 钉「`PlanResult.tasks` 是 `plan.tasks` 的只读视图
   （CLI 用）」，函数体只构造 `Unrankable` 并断言 `r.testcase_id == "x"`。（`PlanResult.tasks` 本身在 10+ 条
   e2e 里被间接用到——A/B 删掉它 → **15 failed**，所以是**冗余 + 名实不符**，不是没覆盖；
   `Unrankable` 另有 `test_unresolvable_case_is_listed_not_silently_dropped` 覆盖。）
4. **`test_planner_e2e.py` 用真 sqlite**（`TraceStore` / `SQLiteExperienceStore` 落 `tmp_path`），而 plan 的
   Files 写的是「纯内存 fixture，不依赖真实 git」。理由写在文件 docstring（替身 SQL 会让「列名/字段写错」
   静默通过——Task 2.2 的教训）且成立，「不依赖真实 git」也满足；只是没进提交信息的「偏离登记」三条。
5. **`plan()` 的 `cases` / `knowledge` / `repository` / `llm` / `budget` / `metadata` 无类型标注**（`Any`），
   与 `priority_score(tc_meta: TestCaseMeta, …)` / `case_risk(tc_meta: TestCaseMeta, …)` 的标注强度不是一个量级。
6. **`from source.build_diff import diff_builds` 是按需导入**（理由「只有回退面才需要」），而同包的
   `planner/planner.py` 已在顶层 import `source.coverage`。两条风格不一致（不是错）。
