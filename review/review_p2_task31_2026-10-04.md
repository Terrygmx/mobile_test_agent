## 3. 发现

### P2-1 `revalidate` 没有任何状态护栏：零样本 Candidate 可直推 VERIFIED，REJECTED 可被复活

- **实测**（探针 D，真库真表真事件）：

  | 调用前状态 | `revalidate(store, exp, fingerprint=...)` 之后 | `experience_state_events` |
  |---|---|---|
  | `CANDIDATE`（0 样本） | **`VERIFIED`** | 写入 `CANDIDATE → VERIFIED / reason=REVALIDATED` |
  | `REJECTED` | **`VERIFIED`** | 写入 `REJECTED → VERIFIED / reason=REVALIDATED` |
  | `VERIFIED` | `VERIFIED`（无新事件） | 事件数 2 → 2（真 no-op） |

- **docstring 写了一条不存在的安全承诺**（`experience/verifier.py:270`，原文）：

  > 调用前若 `exp.status` 不是 DEGRADED，`update_status` 会按同状态 no-op 语义处理——不会伪造出一条跳变事件。

  这句话**只在 `status` 恰好已是 VERIFIED 时成立**。`update_status` 的 no-op 判据是「新旧状态相同」，而 `revalidate` 硬编码目标 `VERIFIED`：`CANDIDATE` / `REJECTED` 都不是 `VERIFIED`，所以不只**会**写跳变，写的还是一条**规则不允许**的跳变。

- **为什么是 P2 而不是 P3**（两条都是设计红线，不是编码风格）：
  1. **绕过 E4 + 4.5**：`VERIFIED` 是「这条经验可以自动使用」的信任档位，E4 明文「不满足资格 → 永远停留在 CANDIDATE，不管样本和成功率多高」。一条**零样本**、**未过资格判定**的 Candidate 被这一步直接抬进 VERIFIED，正是 E4 要挡的那件事。
  2. **复活终态**：`evaluate` 自己的注释写着「REJECTED 是终态……要复活只能人工重新 ACCEPT 一条新 Candidate（E5 的重新学习路径）」。`revalidate` 提供了一条**绕过 E5 重新学习**的捷径——不做新种子、不积累样本、不改 `status` 之外的任何东西，一行就把 REJECTED 变回 VERIFIED。

- **当前不可达，但接线即生效**：全仓 grep 确认 `revalidate` 现在**只有测试调用**（`experience/__init__.py` 导出 + `test_verifier.py`）。风险窗口是 Task 3.4（`mta experience revalidate`）——那正是 plan 里要接 CLI 的任务，而接线者最可能信任的恰恰是这句 docstring。**建议按「接线前必修」处理**，而不是塞进延后项。

- 建议（二选一，别选「只改文档」）：
  - **fail-loud（推荐，与本项目一贯做法一致）**：`revalidate` 开头加 `if exp.status is not ExperienceStatus.DEGRADED: raise ValueError(...)`，指名「显式重验证只用于 DEGRADED」；或
  - **fail-closed**：非 DEGRADED 直接 `return False`（不写任何东西），与 `apply_outcome` 的返回值语义对齐。
  两个方向都必须**先改掉那句 docstring**——错误的安全承诺比没有护栏更危险。同时建议补两条钉子测试：CANDIDATE 上调用 → 拒绝且 events 不变；REJECTED 上调用 → 拒绝且 status 仍为 REJECTED。

### P3-1 `evaluate` 内联了一份没有守卫的窗口计数——4.6 的第二套实现

- `sliding_window_degrade`（`verifier.py:110`）有 `if window <= 0: raise ValueError`，是 4.6 规则的**唯一**权威实现；但 `evaluate`（`:180`）为了填 `detail["window_failures"]` 又写了一遍 `runs[-policy.degrade_window:]` 的裸切片。
- 实测（`degrade_window=0`）：CANDIDATE 分支 `detail["window_failures"]=3`——`runs[-0:]` 在 Python 里等于**整个列表**，于是「最近 0 条里的失败数」被算成了「全部历史里的失败数」，`detail` 静默失真；VERIFIED 分支则在 `sliding_window_degrade` 处抛 `ValueError`，同一份配置在两条分支上给出**两种形态**（一个静默错、一个炸）。
- 这不违反测试（用例只测 window=5），但违反本项目「同一概念只许一处实现」的硬纪律——`sliding_window_degrade` 已经存在，判据明细应当复用它或抽一个 `recent_failures()` 共用谓词，而不是在 `evaluate` 里重写切片。
- 建议：`evaluate` 的 `window_failures` 改成调用共享谓词（例如 `sliding_window_degrade` 拆出 `recent_failure_count(runs, window=...)` 供两处调用），守卫随之单点到一处。

### P3-2 两个 Policy 模型没有任何取值校验（配置写错即静默失真）

- 实测：`VerificationPolicy(degrade_window=0)`、`(degrade_window=-1)`、`(min_samples=-5)`、`(min_success_rate=2.0)` **全部被接受**；`StalenessPolicy(max_idle_days=-1)` 同样被接受，实测「闲置 0 天 + `max_idle_days=-1`」→ `sweep` **把当天刚建的候选全清了**。
- 这两个类的 docstring 都写着「默认值即设计值——改动即设计变更，测试拦住」，但**只有默认值被保护，传入值没有下界**。设计 §4.5/§8.2 的 policy 来自 YAML/CLI，一个手误的 `max_idle_days: -1` 会静默清库（且 `update_status` 无 undo）。
- 建议：给 `VerificationPolicy` 加 `degrade_window ≥ 1` / `degrade_max_failures ≥ 1` / `min_samples ≥ 1` / `0 ≤ min_success_rate ≤ 1`，`StalenessPolicy` 加 `max_idle_days ≥ 1`；pydantic `Field(ge=...)` 一行一个，符合本项目 fail-loud 的一贯做法（`CandidateSeed` 就是这么干的）。

### P3-3 §4.3 的 `DEGRADED ──(持续失败 / 人工判定)──► REJECTED` 无实现，`REJECT` 在状态机内不可达

- 探针穷举（4 状态 × 2 资格 × 5 种历史形状 = 40 例）：产出分布 `NO_CHANGE 26 / KEEP_CANDIDATE 9 / DEGRADE 4 / PROMOTE 1`，**`REJECT` 0 例**。`VerificationDecision.REJECT`、`_DECISION_STATUS[REJECT]`、`apply_outcome` 对 REJECT 的落库全部在位，唯独触发侧没有。
- 「人工判定 → REJECTED」走 9.5 人工 Promotion 流程可以理解不在 `evaluate` 里；但「**持续失败** → REJECTED」是样本驱动的，与设计 §4.3 的转换表有真实缺口：一条 DEGRADED 经验在窗口里反复失败，`evaluate` 只会一遍遍返回 `AWAITING_REVALIDATION`，**永远不收敛**（既不会自动清，也没有自动的 REJECTED 出口；目前唯一的自动出口是 sweeper，而 sweeper 只清 CANDIDATE——见下一条）。
- 建议：明确这属于 Task 3.4 还是单独立项。若不动，把「DEGRADED 的自动 REJECTED 出口**暂无**」写进模块 docstring 的偏离清单（现在只写了「DEGRADED 无自动出口」，没写「也没有自动的 REJECTED 出口」），避免下个里程碑把它当回归重查。

### P3-4 `apply_outcome` 是裸接缝，不校验 `exp.status` 与决策是否匹配

- 实测：对一条 **CANDIDATE** 施加手工构造的 `VerificationOutcome(DEGRADE, "SLIDING_WINDOW")` → `apply_outcome` 返回 `True`，库里写下 `CANDIDATE → DEGRADED / reason=SLIDING_WINDOW`。而 §4.3 的转换表里**没有** CANDIDATE→DEGRADED 这条边。
- 现有测试恰好利用了这一点（`test_apply_outcome_reject_uses_outcome_reason` 手工造 `REJECT` 断言落库），说明「裸接缝」是**有意**设计——`apply_outcome` 只是「决策 → 落库」的搬运工。但它同时是 Task 3.4 唯一的落库入口，届时任何调用方的状态/决策错配都会安静地写进时间线。
- 建议：不要求 `apply_outcome` 变复杂，但把「**本函数不校验当前状态，调用方必须保证 outcome 来自本条 exp 的 `evaluate`**」写进 docstring（现在只说了 `run_id/app_build/operator` 的语义）；或加一个可选 `expect_status` 断言参数，由 CLI 传入。

### P3-5 设计 §4.4 的签名偏离未登记（模块 docstring 说「三处有意偏离」，实际是四处）

- 去掉 `exp` 我同意（设计伪代码里那个参数在函数体内也没用到，留着只会诱导调用方以为状态参与资格判定），**但它是签名级偏离**，而模块 docstring 明写「三处有意偏离」，审计也照抄「三处」。下一轮评审会按「三处已登记」放行，这一处就成了无人认领的漂移。
- 顺带记一笔：**字段名与伪代码不同**——伪代码用 `element.effective_risk`，实现用 `element.risk`。实测 `EffectiveElement` 的真实字段是 `risk`（无 `effective_risk`），所以实现是对的、伪代码是随手的；但 `executor.policy.Risk` 与 `testcase.schema.Risk` 是**同一枚举对象**（已实测 `PR is TR → True`），两处 import 名字不同源却同体——这个巧合值得在 docstring 点一句，否则将来有人改成 `from testcase.schema import Risk` 会以为换了枚举。

### P3-6 `test_sweep_honours_policy_max_idle_days` 的第二条断言是空命题

- 该测试先 `sweep(StalenessPolicy(max_idle_days=29))` 把 exp 清成 REJECTED，再 `sweep(StalenessPolicy(max_idle_days=90))` 断言 `== []`。此时 exp 已不是 CANDIDATE，第二条断言**无论 90 天逻辑对错都成立**——它测的是「REJECTED 不再被清」，不是「30 天闲置在 90 天口径下不清」。
- 建议：第四条断言改成先 `_seed` 一条**新的** 30 天候选（或直接断言 `is_stale(exp, runs, now=NOW, max_idle_days=90) is False`），让「策略值真的被读取」这件事被考到。

## 4. 未验证 / 存疑

1. **Gate M3 未跑**：Task 3.1 的 plan 未指定真机 gate（纯函数任务，符合 E13 预期），故本次没有真机判据可复核；`out/p2_m2_gate/summary.json` 仍是 M2 的产物。

3. **`revalidate` 的「验证证据由调用方提供」契约**：实现只写状态 + 更新 fingerprint，不校验调用方是否真跑过验证。这在人工流程里合理（人是证据），但 CLI 化后需要一个「谁主张重验证通过」的留痕——目前 `operator` 参数已经能承载，只是没有强制。未深究。

## 5. 值得肯定

- **`auto_verify_eligible` 做成必填关键字，是本次最有价值的决策**。设计伪代码是 `evaluate(exp, runs, policy)`，作者识别出「E4 的资格是目标元素的属性，而三者里都没有它」，并且给出了一条**能被证伪的论证**：`ExperienceRun.effective_risk` 恒为 LOW（4.7 表规定风险未过的尝试不写样本）→ 拿它判 E4 必然恒真 → 假绿。更关键的是**必填无默认值**：忘了传是 `TypeError` 而不是「默认 False 默默不升级」——而且理由写得极准：「做成可选默认 False 会让『忘了传』与『确实不合格』不可区分」。这是 E13 精神的正确落地方式。
- **判定与落库劈成两半、中间无共享规则**。`evaluate` 全纯、`apply_outcome` 只做搬运，两者之间没有第二份判据——这正是「两套实现必然漂移」的反面教材的正确写法。
- **截断守卫（`len(runs) != sample_count → ValueError`）** 是超出 plan 要求的防守。静默失真的方向是「样本看起来更少 → 不升级」，报告上完全看不出原因，属于最难查的那类 bug。
- **DEGRADED 不提供自动出口**的判断是对的，并且给了能被复核的理由：「E6 的滑动窗口是**安全阀，不是健康探针**」——窗口恢复就自动转回会把降级变成抖动。
- **E8 标记的三选项取舍写得很实**：放宽 schema / 借事件名 / `from==to`，逐条给了否掉的理由，最后选最保守那个，并说明「不动 schema 就不破坏既有的『跳变必有终态』不变量」。幂等判据选「最近一次跳变之后」而不是「历史上有没有过」，也给了可验证场景（DEGRADED→VERIFIED 后指纹又变，必须能重新标记）。
- **矩阵 #5 的数字矛盾被主动识别**：设计原文「100 次 98 成功、最近 5 次 3 失败」自相矛盾（3 次失败意味着总体最多 97%），测试改用自洽的 97%（仍 ≥ 门槛 0.95），**并且说明了为什么这样才真的考到「窗口优先」**——只看总体它会一直 VERIFIED。这种「照抄设计会写出假绿测试」的警觉值得记一笔。
- **STALE 的三条边界（严格大于 / 零样本退回创建时刻 / 只清 CANDIDATE）每条都给了反例理由**，特别是「因为『没有 last run』就豁免会让建出来没人碰过的候选永远留在库里」——直接命中 §8.2 的靶心。
- **顺带核销的三个未评审提交全部站得住**：`186bfbc` 把终审 6×P3 逐条处置且各有落点（P3-2 有指名报错、P3-3 有同形 detail 且不盖 `recovered_kind`、P3-4 把「有意」写进 docstring 并加断言钉住、P3-5 改了共享规则体那句、P3-6 阈值单点）；`d5c4a42` 的 `_current_screen_id` 是本次最见功力的一处——**识别出「识别跑过」与「识别没跑」必须分开**，否则一律收紧会打掉 29 个「无 repo」的既有测试（P1 矩阵全过），而一律回落会让屏校验**自比自**（`current_screen` 与 `exp.screen_id` 都等于 `ctx.screen_id` → 永远相等 → Guard 第一环从不触发）。这个「自比自」的发现是真正的安全洞察。
