## 2. 问题清单

### R13-1（P1）reset 能力矩阵双源分叉：lint 放行 RESET_STATE，runner 运行时炸

三处事实拼起来：

1. **新矩阵**（`capabilities.py`）按 11.1 表把 `RESET_STATE` 标为两端支持；
2. **lint 11.2 预检**基于新矩阵 → 写 `reset: RESET_STATE` 的用例**过 lint**；
3. **runner 实际执行路径**（`runner/testcase_runner.py:88`）仍是 P0 的 `self.app.reset_state(reset, ...)`，而 P0 的 `SUPPORTED_STRATEGIES = {RELAUNCH, TERMINATE, REINSTALL}` **不含 RESET_STATE** → 运行时直接抛 `UnsupportedResetError`。

这正好击穿 11.2 的核心承诺——「mta lint 在预检阶段就报错，**而不是运行到一半才失败**」。当前没炸只因 5 条 smoke 恰好全用 `reset: RELAUNCH`（实测 `grep reset: suites/smoke/*.yaml` → 5×RELAUNCH），是碰巧不是防线。更糟的是 `capabilities.py:25` 注释声称「两处策略名必须一致（**有单测钉住**）」——`test_environment.py` 里没有任何跨源一致性测试，空头支票。

**修法**：正解是 R13-2（runner 切到 ResetExecutor，RESET_STATE 由它自己处理不落 P0 matrix）；若 2.5 前要过渡，最低成本是加一条跨源一致性测试钉住「RESET_CAPABILITIES 声称支持的策略在执行路径必须可达」。

### R13-2（P2）EnvironmentManager/ResetExecutor 平行实现，runner 零消费

runner 的 reset 仍走 P0 路径；`prepare()` / `cleanup()` 无任何调用方——CleanupError 的 H10/ABORT_SUITE 语义立住了但没人能触发。与 R10-2（postcondition 声明零消费）同构。Task 2.5「Runner 重构」马上开始，接线点就在那里——**必须在 2.5 的验收清单里显式列上**，否则又是「实现存在、链路不通」。

### R13-3（P2）LOGOUT 的 App 侧 hook 未实现，Python 侧假装做了

`reset.py:39` 发送 `-UITestLogout` 启动参数，但 ios_demo 全目录 **grep 零命中**——App 不识别该参数。当前登录态是内存 `@State`、重启即回未登录，**碰巧**等价于 LOGOUT 语义；一旦引入持久化 session（11.1 注释里 RESET_STATE hook 明确为此兜底），LOGOUT 变成静默无操作。11.1 说 LOGOUT 是「App 内测试 Hook」、A4 只定义了 `-UITestReset`——App 侧至少要识别参数并执行/日志，或 Python 侧注释「hook 未实现，当前依赖进程重启碰巧等价」，不留静默缺口。

### R13-4（P3）端到端验证证据未落盘

commit message 说做了 `-UITestWriteMarker` 写 → reset → 读回的设备端验证，但 `out/` 下无 task23 产物目录（对比 task15/16 的落盘惯例）。临时验证无法事后复核。建议下次把 marker 写入/读取的验证脚本与产物落 `out/p1_task23/`。

### R13-5（P3）卫生项

- `EnvironmentManager.cleanup(tc=None)` 的 `tc` 参数未使用；
- `_coerce` 把未知设备字符串静默归一为 REAL_DEVICE——「最受限」语义合理，但 `real-device`（连字符）这类 typo 会被静默按 real_device 处理且无提示；
- pbxproj 补 DEBUG 的历史副作用：本工程此前无 `#if DEBUG` 代码，无实际影响（commit 已记录）。
