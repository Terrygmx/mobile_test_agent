## 3. 发现

### P1-1 seed 脚本四缺陷叠加——冒烟必然失败，Gate M1 的「≥1 条全链」无法达成
脚本从未跑过（无 CSV），但缺陷不需要跑就能钉死：

- **(a) 新名未登记 → 9.3-3 fail-closed，永远出不了 RECOVERED**。脚本不传 `--generated/--overrides`，默认 Repository = `repository/overrides`（只有旧名）；LLM 候选（如 `signin_button`）`repo.resolve` 不到 → `LLM_TARGET_SCREEN_MISMATCH` → run exit 1 → 脚本按「非 RECOVERED」记 FATAL。**M4 Gate 已实证的解法缺失**：漂移候选必须预登记别名且带 risk 声明（`verify_p1_m4.py` 的 overrides 副本模式）。脚本注释的「漂移前提链」三步只论证到「runtime find 必然失败」，第 4 步（候选要通过 9.3 全链）漏了——这正是 M4 Gate 用 5 个真机 round 换来的教训，没有进脚本。
- **(b) 轮间不还原源码 → 轮换表第 2 轮起全灭**。ACCEPTED 分支（:134-139）不 `git checkout`，源码保持 round 1 的漂移态；round 2 的 `grep -c "accessibilityIdentifier(\"login_button\")"` 命中 0 → FATAL。7 场景轮换实际只有第 1 轮可能走通。每轮注入前应 restore + 重编。
- **(c) `$WARN_PASS` / `$FAILED` / `$NO_REVIEW` 未赋值**（:110/:114/:129——与 :141 的字面量 `SKIPPED` 写法不一致），`set -u` 下这三个异常路径一进来就 `unbound variable` 崩溃：CSV 行丢失、退出码非预期（trap 能还原源码，但失败轮连账都记不上）。
- **(d) `$PY="python"`**：本机 `python` 解析到无关 venv（agent-reach-venv）的 python3，无项目依赖 → 第一个 `$PY -m cli.main run` 直接 ImportError。项目自己的教训（M5 记账：「必须用 .venv/bin/python（系统 python 无 appium）」）没进脚本。应默认 `"$ROOT/.venv/bin/python"`。

### P2-1 场景表 5/7 的漂移目标 risk=MEDIUM——修完 P1-1 这些场景也永远产不出 ACCEPT
`repository/overrides/elements/LoginView.yaml`：`username_field` LOW，`login_button`/`password_field` **MEDIUM**。9.3-4 只放行 `effective_risk == LOW` 的候选（fail-closed 是**正确行为**）——`login_button→signin_button` 等 5 个场景的候选即使登记了也过不了 risk 门。且**不许**用「别名声明 risk: LOW」绕过（把 MEDIUM 字段的漂移别名降级成 LOW 是风险作弊，Guard/审计都拦得住但语义已坏）。修法：场景表换成 override 里 LOW 目标的轮换（`username_field` / `go_search` / `go_profile` / `search_field` 等足够 7 个），MEDIUM 目标的漂移可作为**预期拒绝**的负例轮单独标注（验证 fail-closed 仍有价值，但不算种子产量）。

### P3-1 plan 五维度缺「(screen, target) 去重对」
审计脚本没有该维度的查询。数据为空时看不出，但补齐 50 条后它是 Experience 主键 `(app_id, screen_id, target_id)` 去重的直接依据（M2 Store 的 lookup 语义）。补一个 `screen_target_pairs()`（GROUP BY screen, expected_target, candidate_target）即可。

### P3-2 种子清单缺 app_id 输出列
`seedable_accepts` join 出了 `ru.app_bundle_id AS app_id` 但 `render_markdown` 不输出——而它正是 Candidate 主键的第一段。顺手补列；50 行到位后建议 `--out` 同时落一份 JSON/CSV（M2 Task 2.3 消费方便，markdown 只给人看）。

### P3-3 杂项
- seed 脚本 preflight 的 `xcrun simctl` 依赖环境 `DEVELOPER_DIR`（M5 review P3-5 同族，脚本开头显式 export 一次即可）。
- 「Review 分布」空表没有 `|（无）|` 占位行（其他空表都有），风格不一。
- 收尾提示 `python scripts/p2_audit_recoveries.py` 同样用了系统 `python`（P1-1d 同源）。

## 4. 值得肯定

- **审计结论是实查出来的，且敢报坏消息**：存量 49 条恢复数据 0 条可用（42 悬空 / 0 review / result 全空）——「50 条需从零补齐」把 E5 的真实成本在 M1 第一天就显形，而不是让 M2/M5 演示前才发现。我逐项 SQL 复核全部成立。
- **seed_ready 判据严格且为 M2 留对了接口**：三件套 + screen/target 齐全才 True；悬空行**保留并标 False**（注释点名「M2 的 create_candidate 会因 E5 校验拒绝」）——审计暴露缺口而不是静默过滤，这个方向感是对的。
- **测试 fixture 用真实 TraceStore 建库**：raw SQL 钉口径的同时不怕 storage 演进把测试弄假；悬空/REJECT/PENDING 的边界都覆盖了。
- **漂移前提链的自文档质量高**：repo-generate 只在原始态、漂移不 commit 保 12.5、绝不漂移态重扫——F5/M4 的教训写进了脚本注释，只可惜链条少推了一步（P1-1a）。
