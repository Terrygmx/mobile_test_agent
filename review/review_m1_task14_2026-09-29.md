## 3. 问题清单

### R8-1（P2）marker 跨 Screen 重复：loader 不查，current_screen 静默选边

实测：两个 Screen（LoginView/page、HomeView/modal）声明**同一个** `marker: screen.LoginView` → loader 照单全收（只查 id 重复，不查 marker 重复）→ `current_screen` 返回 `FOUND, screen=HomeView`——`_visible_marker_nodes` 的 marker→id dict 构建 `.update()` 顺序后写者赢，**静默选边，无任何告警**。

marker 是 `current_screen` / `marker_visible` / Reconciliation local scope 的身份锚点，全局唯一性是整套判定的隐含前提。Task 1.5 要给 App 铺 5 个页面的 marker，正是 marker 面扩大的时候，建议在进 1.5 前于 loader `_validate_screen_semantics` 加 marker 唯一性校验（重复 → `RepositoryLoaderError`），补一条测试。几行改动。

### R8-2（P2）对设计 13.2 的实质偏离未回写文档

设计原文：「markers = visible elements whose id **startswith "screen."**」；实现收紧为「repo 登记的 ScreenDef.marker 且 visible」。docstring 论证充分（防 App 侧误挂 id 干扰），专项测试到位，方向我认为是对的。但这是实现与设计文本的契约分歧，设计文档没有回写——R5-1 的教训重演。且两个语义有真实行为差异：App 新增页面未登记 repo 时，全扫描语义给 `FOUND(未登记 screen)`，收紧后给 `CURRENT_SCREEN_UNKNOWN`（会触发 Recovery/Reconciliation 路径）。需要在设计层确认收紧语义正是想要的（我倾向是：未登记 screen 无法做 local reconciliation，UNKNOWN 更诚实），确认后把 13.2 原文改为「repo 登记的 marker」。

### R8-3（P3·M3 前记账）override 改 marker 后，新旧 marker 同时映射同一 Screen

`marker_to_screen` 合并时 generated 旧 marker 保留：树里若新旧 marker 同时 visible（改名的过渡期/缓存页），同一 screen 计两次 → 多 marker 分支可能误判 AMBIGUOUS。M1 overrides-only 不可达（generated 恒空），M3 generated 接入后出现。修法：override marker 取代 generated marker（旧映射不保留）或 hits 按 screen_id 去重。建议先加 TODO 注释记账（同 R6-4 处理方式）。

### R8-4（P3·卫生）

- marker→id 映射构建在 `_visible_marker_nodes` 与 `marker_visible` 重复，抽 `_marker_to_screen(repo)`；
- `source.screen` 跨模块调 `repo._screen()` 私有方法（可用公开接口或让 Repository 暴露 kind_hint 查询）；
- `test_single_page_marker`/`test_page_plus_modal_picks_modal` 用 `"FOUND"` 字面量，常量已导出却没用于断言（另两处状态用了常量）；
- docstring「不拉整棵树判定」略有夸大——`marker_visible` 仍全量解析 XML，省的是完整判定分支与后续处理，不是解析成本（措辞问题，非行为问题）。

### 观察项（不改代码）

- `visible` 属性缺省视为 true——XCUITest page_source 通常都带该属性，缺省兜底合理；
- `ScreenResult.visible_markers` 带上参与判定的全部 marker，调试友好；
- R8-1 修复后建议给 `test_screen.py` 补一条「双 modal + 一 page + 一 overlay 同屏」的 4-marker 组合用例（当前逻辑上覆盖了，但组合场景没显式测）。
