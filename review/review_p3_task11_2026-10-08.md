## 3. 发现

### P2-1 `trace_history` 的 `app_build` 过滤键被**静默忽略**（`4cea731` 的 P3-2 修订引入的回归）

**现象**：`experience/knowledge.py:104` 仍照旧算出 `app_build = filters.get("app_build", self._app_build)`，但第 105 行改成了 `self._read_steps()`——而 `_read_steps()`（:88）写死 `read_trace_steps(self._trace_db, app_build=self._app_build)`。**第 104 行算出的值再也没被读过**。

AST 取证（只赋值未读取）：

```text
赋值(stored): ['unknown', 'app_build', 'limit', 'steps']
读取(loaded): ['ValueError', 'dict', 'filters', 'int', 'isinstance', 'limit', 'list', 'self', 'set', 'sorted', 'steps', 'unknown']
只赋值未读取: ['app_build']
```

**探针证据**（真 `TraceStore` + 真管线产的 trace）：

| 场景 | 实测 |
|---|---|
| 底层原语（对照组）`read_trace_steps(db, app_build='1026'/'1025'/None)` | `3 / 0 / 3` steps → **原语过滤正常** |
| 单 build 库，`trace_history({"app_build": "1026"})` | 3 steps（恰好对，掩盖了问题） |
| 单 build 库，`trace_history({"app_build": "999"})` | **3 steps** ← 库里没有 999，过滤生效应为 0 或报错 → **静默返回了 1026 的数据** |
| 双 build 库（1025 + 1026），`trace_history({"app_build": "1025"})` | `ValueError: trace 里有多个 (app_id, app_build) 范围：[…'1025', …'1026']；图必须限定在单一范围（用 app_build= 过滤或分开建图）` |
| 同库，底层原语 `read_trace_steps(app_build='1025')` | 3 steps, build=`'1025'` ✓ |

**为什么现在报**：
1. 这是**本模块自己写在注释里的反面教材**——:100 行原文：「过滤键是接口契约的一部分：静默忽略拼错的键会把「想过滤没过滤」伪装成「结果恰好都对」」。现在 `app_build` 成了那个「静默忽略」的键，而白名单还留着它。
2. 单 build 库下**恰好返回正确数据**，所以现有测试全绿；只有双 build 库才暴露，而双 build 正是 `graph diff` / build-to-build 的日常形态。
3. 后果有两个方向，都误导人：单库时**给错数据不报错**；多库时**报错信息叫你去用 `app_build=` 过滤**——而调用方正是这么做的。
4. P3 的规划能力（M2）就要消费这个接口，`changed_files → targets` 的链路会按 build 取历史。

**修法（一行 + 一条测试）**：让 `_read_steps` 接受覆盖值，或让 `trace_history` 直接调原语：

```python
def _read_steps(self, app_build: str | None = None):
    try:
        return read_trace_steps(
            self._trace_db,
            app_build=self._app_build if app_build is None else app_build)
    ...
# trace_history 内：
steps, _app_id, _build = self._read_steps(app_build)
```

测试：双 build 库中断言 `trace_history({"app_build": X})` **只**返回 X 的 steps（现有集成测试只覆盖了 `{}` / `limit` / 未知键——这正是漏网原因）。

### P2-2 `agents/storage.py` 的单写者事务在异常路径上**泄漏进程锁** → 该 store 此后所有写永久挂死

**现象**：`_Tx.__enter__`（:59-63）把 `BEGIN IMMEDIATE` 放在保护区间**之外**：

```python
def __enter__(self):
    store._write_lock.acquire()          # ← 先拿锁
    store._conn = store._connect()
    store._conn.execute("BEGIN IMMEDIATE")   # ← 这里抛异常，锁永远不还
    return store._conn
```

`acquire()` 无超时，`__exit__` 不会被调用（异常发生在进入 `with` 之前）→ **该 store 实例之后每一次写都阻塞在 `acquire()` 上，永久**。

**A/B 探针证据**（另一条连接持 `BEGIN EXCLUSIVE`，让 `BEGIN IMMEDIATE` 在 `busy_timeout` 后失败）：

| | agents/storage.py（本提交新增） | experience/store.py（P2 既有，对照） |
|---|---|---|
| 写结果 | `OperationalError: database is locked` | `OperationalError: database is locked` |
| 失败后锁仍被持有 | **True** ❌ | **False** ✅ |
| 释放外部锁后再写一次 | **3s 仍未返回（永久阻塞）** | 正常 |

差异根源：`experience/store.py` 的 `@contextmanager` 版把 `BEGIN IMMEDIATE` 放在 `try` 内（:143-157），失败时 `finally` 释放；新代码手写 `_Tx` 类时把它挪到了保护区间外——**而它的 docstring 写的是「沿 experience/store.py 同款」**。

**为什么现在报**：
1. 触发路径不是构造出来的——`experience/store.py` 的 docstring 原文就记载过这类事故（「曾致『database is locked』连坐后续操作」），也就是说这类失败在本项目**真实发生过**。
2. 后果是**活性丢失且不可自愈**：agent.db 写不进去 → 审计留痕（`agent_trace`，F1 的审计根基）从那一刻起整段丢失；M4/M6 的长循环里没有任何机制能发现「我卡住了」。
3. 本提交是 P3 首个 commit，`SQLiteAgentStore` 会成为所有 Agent 主线的写入口；样板复制得越早，后面越难改。
4. 现有并发测试（`test_concurrent_appends_no_lost_update`）只跑 happy path，异常路径零覆盖。

**修法（一行 + 顺带消重）**：把 `_connect()` 与 `BEGIN IMMEDIATE` 挪进 `try`；更好的做法是**别再复制第三份**——单写者样板现在有三处形态（`experience/store.py` 的 `@contextmanager`、`agents/storage.py` 的手写 `_Tx`、`graph/storage.py` 的 `with conn:` **无锁无 BEGIN IMMEDIATE**），与项目「同一概念只许一处实现」的硬纪律相悖，建议抽成 `source/sqlite_tx.py` 由三处共用。
