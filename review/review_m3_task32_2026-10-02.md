## 3. 发现

### P2-1 CLI 默认把 dynamic 判红，与同提交 G6 判据自相矛盾
- 位置：`cli/main.py` `cmd_source`——`uncovered = dynamic + unknown + ambiguous + missing`，非空即 exit 3
- 探针实锤：在本仓库金标准数据上（正是提交信息的实测数据），`mta source coverage` 不带参数 exit 3，被卡的恰是 3 个 dynamic（`HomeView.cell_alpha/cell_beta`、`SearchView.cell_beta`）——而 G6 注释自己写着「dynamic 是 12.2 预期形态，判红会逼人猜值」。Gate 与 CLI 语义分裂：G6 只卡 unknown/missing（连 ambiguous 也不卡），CLI 却连 dynamic 一起卡。
- 影响 CI 化：若 Gate 流程直接接 `mta source coverage`，在设计预期的 dynamic 形态上**永远红**；带 `--allow-partial` 才能过，那「Gate 语义」名不副实。
- 修复建议：默认只对 unknown/ambiguous/missing 卡 exit 3（与 G6 对齐），dynamic 归 informational 但必须可见；或显式文档化「CI 必须带 --allow-partial」并解释为何 Gate 判据与 CLI 不同。补测试断言新语义。

### P2-2 任务顺序偏离计划：Gate 曾在缺判据的情况下宣告通过
- 时间线实锤：计划顺序 3.1→3.2→3.3→Gate M3；实际 3.1（`bdfb4a9`→`963f307`）→ 3.3（`305882a`）→ **Gate 5/5 PASS** → 3.2（`0067363` 补 G6 重跑 6/6）。即 M3 Gate 第一次「验收」时缺了设计 Gate M3 明文要求的 coverage 判据，靠 3.2 自查兜回。
- 结果无害（重跑产物属实、判据正确），但暴露流程口子：Gate 判据清单不是从设计 Gate 条款机械生成的，而是随任务进度手写——设计明文要求的条目可能漏。下次里程碑 Gate 验收前，建议先把设计 Gate 原文逐条映射成 G 编号再写探针，而不是等任务补。
