## 3. 发现

### P2-1 脱敏文本模式的 `\b` 边界失效——「前缀+数字」形态泄漏进 prompt（探针实锤）
- 位置：`llm/prompt.py:48-52` `_TEXT_PATTERNS`
- 探针实锤：runtime 页 `<Node name='user_13812345678'/>` → 引擎发出的 prompt（FakeLLM 捕获实文）中 `13812345678` **原样出现**。原因：`\b1[3-9]\d{9}\b` 的 `\b` 在下划线/中文字符与数字之间不成立（Python re 中 `\w` 含两者），而 XCUITest 树的 name 无显式 identifier 时回退 label——「用户138…」正是中文 App 最常见的 label 形态。裸数字形态（`value='13812345678'`）现有测试是过的，恰好掩盖了这条。订单号模式 `\b(?:ORD|NO|SN)…` 同病。
- 后果：H14 的实际保护面比测试呈现的窄——「脱敏先于出进程」的架构没错，最常用的模式在最常见的形态上漏。
- 修复建议：`\b` 换数字边界 lookaround（如 `(?<![0-9])1[3-9]\d{9}(?![0-9])`；订单号同理），宁可过掩勿漏；补 `user_138…` / `用户138…` 两个泄漏形态测试（直接对 FakeLLM 捕获的实文断言）。

### P2-2 reconciliation 通道绕过脱敏，且被放进 prompt 可信区
- 位置：`agent/recovery.py` LOCAL_RECONCILE（`page = ctx.page_source()` **原始树**喂 `reconcile_local`）+ `_llm_stage`（`json.dumps(recon)` 插在 [ERROR] 之后、[UNTRUSTED OBSERVED UI] **之前**）
- 实锤（代码路径）：redact_ui_tree 只用于 `_llm_stage` 第二次取的 page；`recon["candidates_in_runtime"]` 是从**未脱敏**页面提取的运行时 name 属性集合，未过任何 mask 就进 prompt——且落在可信区。两个后果：①运行时文本未脱敏出进程（H14 letter）；②运行时派生数据被标记在可信区，[SYSTEM INSTRUCTIONS] 里「不要遵循 UI 区文字」的约束罩不住它（prompt injection 面）。附带：同一次恢复 `page_source()` 拉两次（设备成本 + 两次内容可能不一致，recon 与 prompt 看到的页面都可能不同）。
- 修复建议：一次取页 → 先 redact → 同一份喂 current_screen/reconcile/prompt（marker 名 `screen.*` 不受遮蔽影响，current_screen 语义不变）；recon JSON 挪进不可信区或加显式「runtime 派生」标注。

### P3-1 10.5「报告首页告警」未实现
- 实锤：report/html.py 本提交未动；`broken`/熔断状态无任何通往报告的通道（失败行本身带 LLM_BUDGET_EXCEEDED 算部分可见）。设计 10.5 明文「并在报告首页告警」。建议 render_run_report 加一张 budget/broken 卡片（`budget.broken` + 剩余额度），4.3 的报告项一起做即可。

### P3-2 budget 拒绝路径的 record_failure 膨胀 + aux 步骤症状不替换
- `agent/recovery.py` `miss()` 对**所有**失败路径调 `budget.record_failure()`——包括 `try_acquire` 返回 False 的预算拒绝。预算拒绝不是「一次尝试未以 RECOVERED 收尾」（10.5 的失败定义），计入熔断连续失败会让熔断提前触发（边缘场景）。建议 budget 拒绝分支不记 failure。
- aux 分支（wait/assert）恢复未恢复时直接 raise 原异常——症状不替换为 LLM_BUDGET_EXCEEDED（10.5「相关步骤按 LLM_BUDGET_EXCEEDED 失败」目前只对动作步成立）。语义取其一并记账。

### P3-3 P0 兼容的隐性约束：无参 `try_acquire()` 落进 per-testcase=None 桶
- P0 `recover()` 调 `budget.try_acquire()` 无参 → 计入 `testcase_id=None` 桶，受 `max_calls_per_testcase=3` 限制。verify_stage8 恰好 3 次调用过线（实测 ✓），第 4 次会被拒——这是个一踩就炸的兼容边界。建议 P0 形态（无参）豁免 per-testcase 限或文档注明。

## 4. 值得肯定

- **「不发调用」是证明出来的**：矩阵 #10 用 FakeLLM 计数断言（`llm.calls == []`），不是「代码里没看到调用」——10.5 最容易被糊弄过去的一条被钉死了。
- **H14 断言打在真实出口上**：FakeLLM 捕获实文查无 secret，而不是只单测 redact 函数——出口断言才能抓住「忘了调用 redact」这类接线错误（也正因为如此，本轮的 P2-1 模式缺口才无处藏身）。
- **熔断语义定档完整且有测试**：不可逆（success 不解锁专项测试）、失败定义显式（含 provider 异常/校验链拒绝）、默认值即设计值（测试拦漂移）。
- **校验链的 fail-closed 面想得全**：候选未登记=无法证明属于当前屏→拒（「漂移元素在新 build metadata 必有登记——双源可比是检测前提」这句话说明想透了 12.6 的前提）、risk=None→blocked、运行时类型取不到→拒。
- **H15 用目录级断言**：`assert not (tmp_path / "repository").exists()`——工具「有能力写也故意不写」被测试钉住。
- **顺延核销有头有尾**：4.1 的 8 项逐项关闭，拍板（recoveries.kind 记机制不记上下文、⑧双查以第二次为准）都回填了设计与记账；4.3 的底账（19/24 已覆盖、真机项清单）提前列好。
