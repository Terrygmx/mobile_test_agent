## 3. 问题清单

### R11-1 (P1) TAP_SETTLE_SECONDS 已删但未真机复跑 Gate，screen→tap 落在 settle 豁免面

时间线实证：`out/p1_m1_gate/gate_summary.json` 停在 **14:38**，wait engine 提交于 **16:36**——commit message 声明的"复跑全绿"是 P0 离线脚本 + 单测，**M1 Gate 套件没有在删除固定缓冲后跑过设备侧验证**。

风险链条：5 条 smoke 用例全部是 `wait_for screen active → tap` 模式（10 处 active wait），而 runner 对 `target.type == "screen"` **明确跳过 settle**（7.3 廉价路径约束）。也就是说：TAP_SETTLE 1.0s 当初就是为 Task 1.6 probe4/5 的「screen active 成功后 tap 被 SwiftUI 转场吞掉」加的；现在保护删了、替代机制（settle）又不覆盖这个模式——原始事故面回到无保护状态。schema_review §3 诚实地记了账（→M3 gesture-ready），但 M1 套件接下来要当 M2 的回归基线用，稳定性不能只靠"应该没事"。

**建议**：
1. 进 Task 2.2 前真机复跑 `verify_p1_m1.py`（建议连跑 2-3 轮看抖动）；
2. 若吞 tap 复现：给 screen target 做「marker 级静止判定」——连续 N 次 `find marker + is_displayed` 结果不变，不拉 page_source，保住廉价路径约束——作为 M3 gesture-ready 信号落地前的过渡。

### R11-2 (P2) `wait_for_settle` 无超时上限

树持续变化（进度条/时钟文本/动画/轮播）时 streak 永远到不了 `stable_polls` → **无限循环**，且每 0.2s 一次全量 page_source 拉取（真机单次 0.5~2s，成本不小）。需要 settle cap（如 10s：超时放行 + 记 warning，或作为失败上抛——语义你定），否则一条带动态内容的页面能把整条 run 挂死。

### R11-3 (P2) `_check` 的元素属性读取无 stale 防护

`find` 成功后的 `el.is_displayed()/is_enabled()/.text` 在转场期（恰恰是 wait 最常发生的时刻）可能抛 stale element 类驱动异常，直接冒泡出 `wait_for`——不是 WaitTimeout、不在 recovery 白名单内 → run 直接 FAIL。语义上「本轮属性读取失败」应当作 `(False, reason)` 继续轮询。修法：`_check` 属性读取段加一层宽 except → 当作本轮未满足。

### R11-4 (P2) `apply_implicit_wait_zero` 死接线

docstring 承诺"当前无 driver 时跳过，connect 后由再次调用补上"，但全库只有 `Executor.__init__` 一个调用点；gate 脚本是 `Executor(ds)` → `ds.connect()` 顺序 → 构造时 driver 为 None 跳过，**connect 后 implicit wait 从未被设置**。当前 Appium 默认就是 0 所以无实际故障，但 H11 的保证靠的是巧合不是代码。修法：`DeviceSession.connect()` 成功回调里调用，或文档改口。

### R11-5 (P3) 不阻塞杂项

1. `WaitConfig` 无生产者——`mta.yaml` 不存在也无 loader（设计 15 只完成默认值集中，没有配置入口），目前所有构造点都用默认值；
2. `_do_assertion` 仍是 Task 1.6 的内联轮询（interval 硬编码 0.5s），与 WaitEngine 并存——Task 2.2 Assertion Engine 时统一，届时 `not_exists` 断言语义（7.3：目标找不到即成功）也在那边；
3. `spec.timeout > 0 else config.default_timeout` 的 fallback 语义没写进 WaitSpec 字段文档（timeout 是否 required、0 值含义）。
