## 发现

### P0-1 `cli/pipeline.py` 真机分支引用未导入的 `os` → `mta run`（真机）100% 装配失败
- **位置**：`cli/pipeline.py:211`（`os.environ.get("APPIUM_URL", ...)`）；import 区无 `import os`
  （旧实现 `c766caf:cli/main.py:11` 有）
- **复现**：直接调 `wire_device_stack(..., fake_driver=False)` → `NameError: name 'os' is not defined`；
  端到端 stub 后走真 `cmd_run` → `PREFLIGHT ERROR: 设备会话建立失败：name 'os' is not defined` / exit 3
- **为什么测试没抓到**：`test_r16_2_no_fake_driver_exits_3_not_fail` 把 `DeviceSession.connect` 换成
  必抛异常，装配在 `os.environ` **之前**就失败；断言文案 `"设备会话建立失败" in out or "build identity" in out`
  **恰好被 NameError 文案命中** → 测试绿、真机路径死。**守卫空转的教科书形态。**
- **影响**：`mta run` 真机/真模拟器路径完全不可用（`--fake-driver` 不受影响）；P1/P2 全量绿证明不了
  （实测：`repo=repo`→`repo=None`、删 `postcondition_checker` 回填，相关套件均全绿）

### P1-1 `validate_semantic` 短路 → 已知矛盾被同一条候选里的「零观测」转移**掩蔽**（fail-open）
- **位置**：`generator/validator.py:183-201`（`sorted(declared)` 内 `if not landings: return UNKNOWN`）
- **复现**：两条候选声明的 `MidView->ProfileView@tap:MidView.x` 完全相同（图里实测落点是 `DetailView`，
  是**已知矛盾**）；只把**第一条**转移的屏名从 `HomeView` 改成 `ZHomeView`（两者都零观测），
  判定就从 **拒绝翻成放行**
- **生产影响**：真语料 20 例里 13 例有声明转移，其 `sorted-first` 实测**全是 `HomeView` 打头**
  ——即真实形态天然命中这条短路
- **口径偏差**：口径登记 1 明写「有观测且没有一条落在声明的 to → 拒绝」；docstring 的「⚠️ 推论」
  只登记了**误拒**方向，**漏放**方向没登记

### P1-2 `parse_candidate_steps.ignored_fields` 在生产路径**零消费** → H4 空转
- **位置**：`llm/parser.py:214-219`（声称「忽略但必须可见」）；`generator/generator.py:217-227` 从不读它
- **实测**：模型声明 `risk: CRITICAL` → `ignored_fields` 正确算出 5 个键，随后**彻底消失**
  （notes 无、留痕表无、候选表无对应列）。对照 P2 侧 `planner` 把它落成审计行
- **为什么是 P1**：不是措辞问题，是**声称的安全属性不成立**——模型越权的痕迹恰好静默消失

### P2-1 迁移 002 docstring 声称 `save_candidate` 有 Python 侧「必有指纹」闸门——**不存在**
- **位置**：`002_test_candidates.sql:33-35`；`agents/storage.py:236-266`（`fingerprint` 无校验）
- **实测**：`save_candidate(..., fingerprint=None)` 入库成功 → 该候选被 `generator.py:182-184` 的
  `if cand.get("fingerprint")` **静默跳过** → **永久不参与去重**（同一用例可反复生成入库）

### P2-2 `DryRunResult.detail` **不落库**——docstring 声称它进「`dry_run_status` 旁边的审计面」
- **位置**：`generator/dry_run.py:64`；`generator/generator.py:283-287` 只传 `dry.status`；迁移 002 无对应列
- **实测**：候选行只有 `dry_run_status='FAIL'`，`failure_type` 消失 → 人工看到 FAIL 却不知道**为什么**失败

### P2-3 `wire_device_stack` 在 `ds.connect()` 成功之后抛错时**泄漏 Appium 会话**
- **位置**：`cli/pipeline.py:211-241`（`connect()` 在 `:214`，其后装配抛错绕过 `DeviceStack.close()`）
- **实测**：`EnvironmentManager` 抛错 → `driver.quit() calls: 0`（泄漏）
- **判定**：旧实现同形（非本次回归），但抽出成「唯一实现」后继续留着这个洞就是选择了它

### P2-4 嵌套 spec 不做白名单：`wait_for`/`assertion`/`postcondition` 里的 `risk` **不被忽略**
- **位置**：`llm/parser.py:304-313`（`return {key: spec}`，spec 是模型原 dict）
- **实测**：`{"wait_for": {..., "risk": "HIGH"}}` → `ignored_fields` **为空**，spec 原样穿过；
  拦得住是**巧合**（P1 schema `extra="forbid"` 兜住），且 H4 的「可见」在嵌套层不成立

### P3-1 4 处未使用的 import；`validator.py` 的 `max_severity` re-export 注释与实现不符
### P3-2 `candidates/test_case.py::utcnow()` / `to_store_dict()` 是零生产消费者的新 API
### P3-3 `wire_device_stack` 的真机分支**零测试覆盖**（三条变异 0 red）
