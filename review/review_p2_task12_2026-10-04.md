## 3. 发现

### P3-1 `success_rate` 构造期无一致性校验（旁路值可持久化）
- 探针实锤：`Experience(success_rate=0.9)` 在全零计数下**建得起来**。`_counters_consistent` 校验了 `sample == success + failure` 与 `promoted → commit`，漏了 `success_rate == success/sample`（0 样本时 == 0.0）。M2 Store 落库是 `model_dump` 全量字段——旁路构造的 rate 会原样进 `experiences.success_rate`，与计数列矛盾。修法：validator 里补一条（与计数校验同风格），一行测试。

### P3-2 `CandidateSeed.review_id` 与 `seed_recovery_review_id` 冗余且无交叉校验
- 两个字段语义上恒指向同一条 ACCEPT review（构造时可填不一致的值，模型不拦）。要么删掉 `review_id`/`recovery_id` 之外的一个，要么 `model_validator` 断言 `review_id == seed_recovery_review_id`。同族问题：M4 时 recoveries 的冗余列教训（重复字段无一致性检查 = 未来对不上的坑）。

### P3-3 `EXPERIENCE_SCHEMA_VERSION` 恒值与版本链无一致性绑定
- 常量硬编码 `"p2-002"`，链尾才是真实状态；将来加 `003_*.sql` 忘 bump 常量 → `migrate()` 返回值撒谎。且测试第 70 行把 `== "p2-002"` 钉死，反而把「两处维护」固化成契约。建议：常量从链尾派生（`current_version` 的别名）或补一条「链尾脚本号 ↔ 常量」一致性测试。

### P3-4 迁移与设计 §11 的差异清单不全
- SQL 头注释列了三条差异（strategy_json 单对象 / screen_fingerprint 同名 / result CHECK），实际还有：`origin` CHECK、`status` CHECK、`seed_step_id > 0` CHECK、`promotion_proposals.status` CHECK + DEFAULT、`experience_state_events.to_status` NOT NULL 化。修订记录纪律（12.6 同款）：差异要么列全，要么写「其余与设计一致」。

### P3-5 杂项
- 默认库路径 `out/experience.db` 目前只存在于文档——Task 2.2/2.x 接 CLI 时建议单点定义常量（两处 task 各写一份字面量必漂移）。
- `_applied_seq` 对**无数字前缀**的 version 行静默忽略（`_VERSION_RE` 不匹配即跳过）——手工插入垃圾行不会触发 fail-loud。低风险，遇 `version NOT NULL` 且不匹配正则的行直接 raise 更符合 fail-loud 纪律。

## 4. 值得肯定

- **泛化迁移执行器是真泛化**：不 import experience 模型、只认「目录 + 版本链」、支持 zipapp 打包形态（importlib.resources 兜底）——我核对了 import 面，graph/M5「零改动复用」的承诺可信。这是把 tracer 的机制抽象成可复用资产而不是复制一份，P1 复盘教训的正确消化方式。
- **模型层闸门 + DB 层 CHECK 双层兜底**：E5 三件套、`seed_step_id>0`（P0 写 0 的教训）在 pydantic 和 SQLite 两处同时成立——「模型建不出来 + 库进不去」，比单层防线多一个真实故障面。
- **`extra="forbid"` 全模型**：schema 漂移 fail-loud（`test_seed_extra_field_rejected` 还点了 H4 的名——「不留后门」的纪律延续到 P2）。
- **9.4 的语义翻译忠实**：「Promotion 后 DEGRADED 不自动撤销已进 Git 的策略」被表达成字段平级 + 无联动 setter + promoted 必带 commit，模块 docstring 把理由写透——设计意图→代码语义零损耗。
- **版本链记脚本名不记版本串**：「幂等判定的基准是哪个脚本跑过」这个决策带注释落了码，配合 fail-loud，是 tracer 迁移机制教训的正确泛化。
