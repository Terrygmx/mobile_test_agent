## 3. 发现

### P2-1　aux（wait/assert）Experience 命中**永不落样本** → aux 目标的知识永不积累
- **证据**：`agent/recovery.py:572-577` —— aux（`ctx.redispatch is None`）标 `not_dispatched` 且不 `_queue_sample`；管线 `cli/pipeline.py::_record_aux_recovered` 虽调 `_write_experience_runs`，但 `rec.detail["experience_runs"]` 为空 → 无操作。全管线探针（矩阵 #15）：`experience_runs` **0 行**。原测试 `test_p2_15_aux_hit_writes_no_execution_sample` **固化了该行为**。
- **影响面**：§4.7 明文「通过 Guard，执行成功 → 写 SUCCESS」。aux 的重跑由调用方执行且**结果可观测**，却未回填。后果：仅经 aux 命中的 Candidate `sample_count` 恒为 0 → 永达不到 4.5 的 `min_samples` → **永不能 VERIFIED**；报告读成「这条经验从未被使用」。不破坏已有数据，但直接削弱 P2 的「知识积累」目标。
- **修法（已落收口提交）**：引擎产出 `result=None` + `pending_observation` 的**待定**样本，由调用方观测后经 `agent.recovery.resolve_deferred_sample()` 回填；重跑失败同样回填 FAILURE（含 aux 步骤落 steps 行）。

### P2-2　`SCREEN_UNKNOWN` 在引擎层不可达 —— 屏识别失败时用「登记屏」冒充
- **证据**：`agent/recovery.py::_current_screen_id` 在识别失败（`screen_res.screen is None`）时回落 `ctx.screen_id`；Experience 路径要求 `ctx.screen_id` 非空（否则 `incomplete_key`），故 `current_screen` 永不为 None → §5 的 `SCREEN_UNKNOWN → MISS` 分支对该路径是死代码。探针：页面无任何已登记 marker 时，Experience 候选仍 `outcome=EXECUTE`；LLM 路径同款放行（E1 一致）。
- **影响面**：§5/E11 要求「证明不了当前屏就 MISS 且不记样本」。回落后，若异常页面恰好存在同名唯一元素，会在**未确认屏**的情况下执行 Experience。触发条件窄（需屏识别失败 + 同名唯一元素）。
- **注**：该回落**继承自 P1**（父提交 `_llm_stage` 同款），本提交只是抽成共享函数并复用到 Experience。代码注释已显式声明「收紧要单独立项」。
- **处置（本次不修）**：收紧会**同时改变 P1 的 LLM 路径行为**，与 plan 的「P1 行为保留」硬约束冲突 → 单独立项。本次已补 `test_screen_recognition_failure_falls_back_to_registered_screen` **钉住现状**：谁改这条口径，测试先红。

### P3-1　`experience_runtime_guard` 注释与实际不符：dispatch **不过** 10.1 Guard；且生产两条路径的 `policy_check` 都是 None
- **证据**：`experience/runtime_guard.py` 原注释称「EXECUTE 后的动作执行走正常 dispatch，其处自会过 10.1 Guard」。实际 `runner/runner.py::_dispatch_action`（及 `dispatch`）**不含任何 `guard.check`**；`guard.check` 全仓只在 `runner/runner.py:166`（对**原步骤的原元素**跑一次）与 `agent/recovery.py::_llm_stage` 的 `_policy_check`。即「同一候选策略经 LLM 得 vs 经 Experience 得」，`blocked_targets` 复检**不对称**。
- **更深一层（reviewer 未及）**：`cli/main.py` 装配 `RecoveryEngine` 时**没有传 `guard`**，于是 `self.guard is None` → **两条路径**的 `policy_check` 在生产中都是 `None`、10.1 复检**从未生效**（LLM 路径自 P1 起即如此）。
  > ⚠️ **本节该论断已被证伪（2026-10-04 后续探针）**：`cli/main.py:508` 有一句
  > `pipeline.recovery.guard = runner.guard`（在 runner 装配之后），两条路径共用
  > 同一个 Guard 实例——**10.1 复检在生产中一直是生效的**。原文的错因是只看了
  > `RecoveryEngine(...)` 的构造参数，没看后续的属性注入。更正详见
  > `docs/p2_data_audit.md` 的「清延后项（2/2）」记录。
- **修法（已落收口提交，部分）**：① 改正注释；② `experience_runtime_guard` 增 `policy_check` 参数、`_try_one_experience` 经新的 `RecoveryEngine._policy_check_for()` 传入（候选解析到登记元素后用**登记的** risk/screen/id 过 Guard），与 LLM 路径同源——`guard` 一旦接上引擎，两条路径同时生效。③ **把 guard 接进引擎本身不在本任务做**：它会新拦下 CRITICAL / blocked_targets 候选，改变 P1 的 LLM 路径行为 → 已记入 §5 延后项。

### P3-2　`--exp-db` 惰性构造的注释与行为不符
- **证据**：`cli/main.py` 注释称「`mta run --no-llm` 之类不碰经验的 run 不会在工作区里留下一个空库」。但 `_try_experiences` 在正常恢复场景会 `lookup`，`_LazyExperienceStore` 随即构造真 Store（`__init__` 即 migrate 建文件）。而「Experience 命中不需要 LLM」正是 P2 的目标——`--no-llm` 恰恰会查经验库（Gate M2 的 G6 实测 stages 含 `miss`）。
- **修法（已落收口提交）**：注释改为「真正不建库的是『恢复流水线根本没进』的 run」。

### P3-3　`_queue_sample` 因缺 `run_id` 静默丢样本
- **证据**：原 `agent/recovery.py::_queue_sample` 中 `if not ctx.run_id: return`，无任何痕迹。与「每一处做不了都留 stage」的自我纪律不一致。
- **修法（已落收口提交）**：追加 stage `{"stage": "experience_sample", "outcome": "no_run_id", ...}`。

### P3-4　E7 的 build 集合被硬编码 `"local"` 稀释（继承 P1）
- **证据**：`cli/pipeline.py` 两处 `app_build="local"`；Gate summary 亦为 `validated_builds=['local']`。父提交同样。E7 的 `validated_builds` 本应是「哪些真实 build 验证过」的集合，恒为 `["local"]` 时集合语义退化。
- **处置**：非本提交引入，但正是本提交让它首次真正生效 → 记入延后项（需把真实 build id 贯通 `RecoveryContext.app_build`）。

### P3-5　`EXPERIENCE_EVENT_TYPES` 半接（§11.1 的 12 事件只接了 1 个）
- **证据**：`tracer/storage.py` 定义 12 事件；唯一消费点是 `agent/review.py` 的 `candidate_created`。recovery 期的 `experience_lookup/hit/miss/guard_block/execution` 无写入点。作者已在审计中显式记为「有意不接」（半接的埋点比不接更坏）。
- **处置**：已挂 plan Task 4.1；保持「要么全接、要么不定义」的纪律，勿长期停留半接。
