## 3. 发现

### P3-1 数据基线的双口径需要一行「拍板入档」（已诚实披露，判定权在评审）
- 事实：设计 §1.2 原文口径是「50+ 条**真实 Recovery 事件**」——80 条达标；plan Task 1.1 演化出的更严口径「50 条**人工 ACCEPT**」实为 7 条。demo record 没有瞒报，反而把口径演进讲透了：Experience 接管后重复漂移不再产生新 review（S2 的 llm=0 正是证据）——**「越跑越少依赖 LLM」是设计目标本身，重复 ACCEPT 变少是成功态不是缺口**。
- 评审判定：接受「事件口径」作为 1.2 的达标口径（这是设计原文），ACCEPT 数降级为经验库丰富度的过程指标。但这个拍板必须**写进修订记录**（设计 §1.2 或 plan Task 1.1 一行），否则 P3 的规划能力消费基线、或下次 Gate 复核时，口径会再吵一轮。
- 附带观察：若将来确实要扩充 ACCEPT 多样性，机制上需要 50 个**不同的漂移场景**（seed脚本现有 7 场景轮换，同场景重复跑只会被 Experience 吃掉）——即场景表的宽度才是 ACCEPT 数的真实上限。

### P3-2 KnowledgeSources 对「无表 trace 库」裸抛 OperationalError
- 探针亲历：`trace_db` 指向未初始化的空文件 → `graph_query`/`trace_history` 直接 `sqlite3.OperationalError: no such table`。生产中 trace.db 恒由 TraceStore 初始化，概率低；但 P3 规划能力会远程消费这个接口，域错误（或空结果契约）比裸 sqlite 异常可诊断。构造时一次 `PRAGMA table_check` 或捕获转域错误即可。

### P3-3 `graph_query` 返回类型标注为 `object`
- 为了避免循环 import 用了 `object`——P3 消费方拿到的实际是 `RuntimeGraph`。建议 `TYPE_CHECKING` 下标注真实类型（experience/graph 已有同款手法：runtime_guard 对 Experience 的处理）。

### P3-4 Gate M5 的「KnowledgeSources 四接口可查」由集成测试满足
- gate summary 里没有独立的四接口判据行（G1 全量 pytest 含 6 例集成测试）。可接受的口径——记录备查即可；若想让 Gate 产物自证，verify_p2_final.py 加一步对 P2KnowledgeSources 的只读查询即可。

## 4. 值得肯定

- **10 步演示的每一步都是库事实，不是打印**：S2 的 llm=0、S3 的 11/11 样本（E11「实际被尝试」口径全记）、S7 的 status 不变（9.4 两条时间线）、S8 的 promoted 记账原样——「演示」与「断言」在这份 gate 里是同义词。
- **步骤 5/6 的诚实降级**：真机两匹配注入是脆弱操作，用共享 Guard 的矩阵判定覆盖并明说「✅（矩阵）」——E13（判定离设备）的正确用法，宣称边界（H18）守住了。
- **基线双口径的诚实记账**：没有把 80 条硬说成 50 条 ACCEPT，也没有悄悄把标准改成已达标的样子——口径演进的理由（Experience 吃掉重复漂移是设计目标本身）讲得成立，判定权留给评审。这是整个 P2 记账纪律的收尾样本。
- **两起事故的披露与自纠**：LLM 供应商路由失败（查 provider_request_logs 定位 → 改回路由 → 探针恢复）与 Gate 脚本时序错误（漂移态重扫描——seeder 教训原文在仓库里，本次真踩并修正）都进了 demo record。「教训写在仓库里」这个机制第一次被证明能防住一部分错误、也能在防不住时加速定位。
- **KnowledgeSources 的只读纪律**：接口上无任何写形方法（可用 `dir()` 机器验证）——P3 的规划能力消费知识不生产知识，写路径仍归各自的闸门（Runner / review accept / promoter）。这是 P2→P3 交接时最重要的安全属性。
