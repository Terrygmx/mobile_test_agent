## 发现

### P1-1 `mta generate` 在 `--bundle-id` 缺省/app_id 不一致时抛**未捕获** `ValueError`（违反 exit-3 契约与自身 help）
- **位置**：`cli/main.py:1171-1172`（`app_id = args.bundle_id or ""` → `knowledge.graph_query(app_id)`）；help 文本 `cli/main.py:425`（`真机路径的 App bundle id（--fake-driver 时不需要）`）
- **缺陷形态**：声称的「前置错误 → exit 3、零副作用」在此路径不成立；异常穿透到用户面前是一段 traceback（`experience/knowledge.py:86` 的 fail-loud，**正确行为**被**错误的调用方前置**放大成崩溃）
- **复现**：预置 trace（`app_bundle_id="com.demo"`），跑
  `mta generate --gap-from plan_test --fake-driver --suite smoke`（**不给** `--bundle-id`）
  → `ValueError: trace 的 app_id 是 'com.demo'，与查询的 '' 不一致——graph_query 不跨 app 混图`（**未捕获**，无 `generate: exit 3`）；给 `--bundle-id WRONGAPP` 同形
- **为什么测试没抓到**：`test_cli_generate.py::_argv` **恒**带 `--bundle-id com.demo`；`--fake-driver` 分支被注释宣称「不需要」bundle-id，于是**没人构造过缺省那份输入**
- **影响**：`--fake-driver`（无真机冒烟，最常用的本地路径）在 trace 含 app_id 的真实工程里**默认崩溃**；CI 拿到的不是退出码 3 而是 traceback——工具契约破。真实工程里 `mta run` 写的 trace 必有非空 app_id，故这条**不是边缘**。
- **建议修法**：把 `app_id` 的解析做成**前置闸门**（与 `--bundle-id` 的「真机必填」同一段）：`--fake-driver` 且未给 `--bundle-id` 时，从 `read_trace_steps(args.db)` 归一化的 app_id 取（或显式报「trace 的 app_id=X，请用 --bundle-id X」并 return 3）；`graph_query` 的 `ValueError` 一律 `except ValueError → PREFLIGHT ERROR + return 3`。

### P2-1 ACCEPT **非原子**：commit 成功后写库失败 → 文件已提交 + 行仍 PENDING，重试被自己挡死
- **位置**：`candidates/review.py:127-149`（`run_git commit` 在 `:130`，`store.decide_candidate` 在 `:145`，**不在同一个 try 内**）
- **缺陷形态**：`写了一半` —— 外部可见的 commit 已落，但库状态没跟上；且**没有回滚**（commit 不可逆）
- **复现**：注入 `store.decide_candidate` 抛 `RuntimeError`（模拟 commit 后的 DB 故障）
  → 结果：文件**存在**、`review_status` 仍 `PENDING`、`git log` 已含 `promote: candidate cand_search_001`；
  重试 `accept`（无论是否把落盘文件算进 `existing_case_ids`）→ `id ... 与正式用例冲突` / `目标文件已存在`，**永远卡死**
- **为什么测试没抓到**：`test_git_failure_rolls_back_the_file_and_keeps_pending` 只测「git 失败」（异常在 try 内），**没有**「commit 成功、后续写库失败」这条更毒的顺序分支
- **口径偏差**：模块 docstring（`:23-25`）明写选这个顺序是为了**避免「先改状态后落盘」导致永远卡死**——但它在反方向复制了同一种卡死，`修复 git 后重试即续传`（`:25,141`）对这条路径**不成立**
- **建议修法**：commit 后包一层 `try/except`：写库失败时输出「已提交 `<sha>`，库状态未更新——用 `mta candidate review accept <id> --resume-commit <sha>` 或手工 `UPDATE`」并 return 3（至少**可续传**）；或把「改状态」提前到 `rev-parse HEAD` 之前、失败则用 `git reset --soft HEAD~1` + 删文件真回滚。二者都需一条**新钉子**。

### P2-2 「`review_status` 的唯一写路径是 `decide_candidate`」是**过度声称**（同一事实有两处写者）
- **位置**：`agents/storage.py:264`、`:352`（docstring）；`tests/unit/test_candidate_store.py:342`（测试名/文案）
- **实测**：`SQLiteAgentStore.save_candidate(id, ..., review_status="ACCEPT")` → 行是 `ACCEPT`（`reviewer=NULL` / `reviewed_at=NULL`）。这不是理论可达：既有测试 `test_list_candidates_filters_pending_set:216-217` **就在用**这条路造 ACCEPT/REJECT 行
- **判定**：AE 的设计推理（`storage.py:259-264`）建立在「只有一条写路径」上；实际有两条（INSERT 分支）。它没被 `decide_candidate` 的领域校验（`_require_kind` / note / 二次决策）覆盖，可产出**无 reviewer / 无 reviewed_at 的已决行**，与「审核留痕」语义冲突
- **建议修法**：`save_candidate` **删掉** `review_status` 形参（默认写 `'PENDING'`，交给 DDL 的 `DEFAULT`），或把它改成 `assert review_status=="PENDING"`；测试改用 `decide_candidate` 造已决行。

### P2-3 F7 的 AST 守卫（`test_p3_matrix_m1.py`）**可被 docstring/注释文本满足** → 真调用被架空仍绿

### P2-4 `to_store_dict()` 的 docstring 撒谎（声称是 `save_candidate(**...)` 的形状，且 3.5 并未复用）
- **位置**：`candidates/test_case.py:88-89`（`→ SQLiteAgentStore.save_candidate(**...) 的关键字实参形状`）；`tests/unit/test_candidate_store.py:263`（`P3-2：to_store_dict 是 Task 3.5 落盘要复用的形状`）

- **建议修法**：二选一——(a) 删掉这两条 docstring/注释里「→ save_candidate(**...)」的断言（改成「行模型 ↔ store 行的字段快照」），(b) 真让 `save_candidate` 接受 `review_note/reviewer/reviewed_at`（但那与 P2-2「唯一写路径」又要一起收敛）。
